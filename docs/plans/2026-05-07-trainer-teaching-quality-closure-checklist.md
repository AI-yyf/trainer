## 0. 这份清单到底约束什么

这不是灵感草稿，不是阶段备忘，也不是某一轮 UI 想法。

它是 Trainer 的唯一总规范，用来同时约束：

- 产品定义
- VS Code 扩展形态
- 五个一级视图的信息架构
- 交互设计与视觉分层
- 计划治理边界
- 训练闭环
- 卡片训练与题目产生机制
- 资料闭环
- 依赖库 / API 掌握闭环
- 对话 / 计划 / 资料 / 训练之间的学习联动
- AI 行为边界
- 前后端实现边界
- 验收口径与发布门槛

这份清单的目标只有两个：

1. 让产品、设计、AI、前后端、测试只看这一份就知道 Trainer 最终必须长成什么。
2. 防止 Trainer 在继续开发时退化成“把网页塞进 VS Code webview 的聊天插件”。

### 0.2 本清单的使用方式

后续推进必须按以下顺序使用本清单：

1. 先按 `10.2 发布禁飞线` 排除不能发布的反模式。
2. 再按 `11 最终验收清单` 判断每个一级视图是否达标。
3. 再按 `7 产品闭环` 验证数据、计划、资料、卡片是否能回流。
4. 再按 `9 工程与实现硬约束` 检查 schema、职责边界和测试。
5. 再按 `13.21-13.31` 检查事件账本、不变量、权限分级、失败恢复、实施追踪矩阵、单一事实源、路由算法、掌握度、跨视图一致性、威胁模型和 DoD。
6. 最后按 `12 分阶段执行顺序` 输出 `已实现 / 半实现 / 未实现` 状态矩阵。

任何任务如果无法映射到本清单中的验收项，不能被视为完成。

### 0.3 设计理论优先于功能堆叠

Trainer 的设计理论必须先成立，功能实现才允许推进。
如果理论闭环不成立，功能越多越危险。

设计理论的优先级顺序固定为：

1. `学习闭环`：用户是否真的从理解、记忆、动手、验证、迁移中成长。
2. `教练边界`：Trainer 是否只带练，不替用户做。
3. `信息架构`：五个一级视图是否职责清楚、互不吞并。
4. `状态机`：计划、资料、卡片、掌握度是否有可追踪状态流。
5. `证据链`：任何判断是否能追踪到对话、计划、资料、训练或复习证据。
6. `侧边栏形态`：是否先适配 VS Code 280px-420px 窄栏。
7. `视觉表达`：是否在不增加理解成本的前提下显得高级、克制、可长期使用。

任何实现如果跳过前六层，只做第七层视觉 polish，必须判为失败。

## 1. 必须钉死的产品定义

### 1.1 Trainer 是什么

Trainer 不是普通 AI 聊天插件，不是网页应用的缩小版，不是代写代码机器人。

Trainer 必须同时是：

- `代码教练`
- `代码陪练`
- `项目感知型长期训练伙伴`
- `VS Code 侧边栏工作台`

它的主目标不是“显得功能很多”，而是长期稳定地帮助用户：

- `看得懂`
- `做得出`
- `记得住`
- `迁得走`
- `持续进步`

### 1.2 Trainer 的本体首先是 VS Code 侧边栏扩展

最关键的新约束：

`Trainer 首先是 VS Code 侧边栏扩展，其次才是一个拥有复杂能力的训练系统。`

这句话的含义是：

- 默认形态必须先服从 `VS Code 侧边栏`
- 不能先按网页设计，再勉强压进窄栏
- 不能把“响应式网页”误当成“合格的侧边栏扩展”
- 不能把宽视口才成立的布局当成默认方案

### 1.3 五个一级视图必须固定

Trainer 的一级视图必须稳定为：

- `对话`
- `计划`
- `资料`
- `训练`
- `设置`

明确禁止：

- 回退成三视图
- 把 `训练` 藏回对话附属区
- 把 `资料` 藏回上传附件区
- 把 `设置` 做成一堆散乱弹窗
- 把 `计划` 伪装成聊天变体
- 为了“功能多”再新增第六个一级视图

### 1.4 `计划` 是内容视图，不是聊天变体

`计划` 必须是一个可以随时查看、随时审计、随时比较的内容视图。

它不能承载普通聊天输入。

计划只能在以下三类场景发生正式结构变化：

1. `对话中明确进入计划回合`
2. `计划页中触发显式计划动作`
3. `用户明确要求修改计划`

以下行为绝不能改计划：

- 打开 `计划`
- 切换 tab
- 普通问答
- 普通调试
- 普通训练反馈
- 普通资料学习
- 普通会话恢复
- 普通浏览历史

### 1.5 Trainer 是跨项目统一主体

`Trainer 是跨项目统一主体，不是按项目文件夹切碎的多个 Trainer。`

必须同时成立：

- 用户只有一个 `Trainer identity`
- 用户只有一个 `长期能力画像`
- 用户只有一个 `跨项目总计划`
- 每个项目只有自己的 `项目子计划` 与 `项目资料/训练沉淀`
- 不同项目的训练结果必须回流到同一个总计划

### 1.6 计划体系必须是总计划 + 项目子计划

必须分层为：

- `跨项目总计划`
- `项目子计划`

每个项目都可以有自己的子计划。

每个项目推进过程中产生的：

- 阶段推进
- 训练结果
- 薄弱点
- 复习点
- 错误模式
- 依赖掌握度
- 迁移能力证据

都必须能结构化回流到总计划。

总计划不能只按“完成了多少任务”评估，而要按综合能力增长弹性评估。

### 1.7 Trainer 只做教练，不替用户改代码

这是硬边界。

Trainer 必须负责：

- `看清项目与场景`
- `讲清概念与工程判断`
- `拆最小动作`
- `安排验证、复盘、复习`
- `把薄弱点回流成训练与闪记`

Trainer 不能默认负责：

- 直接替用户写完功能
- 直接替用户改项目代码
- 直接替用户提交补丁
- 直接给用户可无脑贴入的大段成品 diff

但必须严格区分两类空间：

- `用户工程空间`：用户正在开发的项目代码、配置、测试、脚本、数据和版本库。
- `Trainer 资料沙箱`：Trainer 用来沉淀资料、网页、PDF、Markdown、HTML、代码文档、知识原子、索引、派生笔记和 skill 工作产物的隔离空间。

硬边界是：

- [ ] Trainer 不能替用户修改 `用户工程空间`。
- [ ] Trainer 可以在 `Trainer 资料沙箱` 内自主管理资料内容，包括下载、整理、解析、重命名、生成派生笔记、更新索引、隔离过期资料和维护知识原子。
- [ ] Trainer 在资料沙箱内的任何写入都必须有 `source_chain`、操作日志、可回滚版本或回收站，不允许无痕硬删。
- [ ] 资料沙箱内执行解析、转换、索引、skill 处理等动作时，工作目录必须锁定在沙箱根目录，不得越权写用户项目。
- [ ] 资料沙箱产物可以作为卡片、计划证据和依赖掌握依据，但不能被伪装成用户已经完成的工程实现。

真正闭环必须是：

`Trainer 负责带、压、验、纠偏；用户自己实现。`

### 1.8 `闪记` 不是新视图，是 `训练` 的组成部分

必须固定：

- `闪记` 属于 `训练`
- `训练` 内必须稳定承接 `练习 / 闪记 / 复盘 / 复习队列 / 理论题`
- 不允许把 `闪记` 升成第六个一级视图
- 不允许把 `闪记` 退化成对话里散落的文本题

### 1.9 依赖库 / API 掌握是第一类教学目标

Trainer 必须正式承担：

- 帮用户掌握依赖库的核心能力结构
- 帮用户记住 API 用法
- 帮用户理解参数、返回值、边界与误用
- 帮用户把“看过文档”变成“能在工程里用”
- 帮用户把知识迁移到新的模块、新的项目、新的场景

如果当前项目没有合适落点，Trainer 必须能指导用户先搭一个最小场景，再迁回真实工程。

### 1.10 训练默认形态是卡片流，不是任务大页

`训练` 的默认产品模型必须是 `卡片训练流`。

必须固定为：

- `实战卡片`
- `闪记卡片`

核心规则：

- 一次只显示一张当前卡片
- 卡片像 `不背单词 / 百词斩` 那样低理解成本
- 用户不需要理解训练系统架构，也能立刻知道当前要做什么
- 卡片完成、跳过、切换、回到对话、进入复盘都必须是明确动作
- 历史、恢复、治理、依赖图、复习队列必须退到次层，不得抢占当前卡片

训练页不能再默认呈现为：

- 多个训练模块平铺
- 多张功能卡同时争抢注意力
- 恢复路线大段展开
- 管理后台式训练资产列表
- 教学说明书

### 1.11 实战卡片必须是定制化工程题

实战卡片不是普通任务摘要。

每张实战卡片都必须回答：

- `为什么现在做这题`
- `题目是什么`
- `建议用户自己新建或打开哪个文件 / 目录 / 模块`
- `需要用到哪些 API / 方法 / 依赖能力`
- `API 的关键提示是什么`
- `用户必须自己交付什么`
- `完成后先怎么验证`
- `做完把什么带回对话或复盘`

如果需要新文件，Trainer 可以写：

`建议你自己新建 <path>，用于完成这张实战卡。`

但 Trainer 不能替用户新建文件、不能替用户写文件、不能替用户改项目代码。

### 1.12 闪记卡片必须覆盖多种知识类型

闪记不是只背 API。

闪记卡片必须覆盖：

- `算法理论`
- `数学理论`
- `公式理解`
- `工程概念`
- `场景判断`
- `API 方法`
- `参数语义`
- `返回值语义`
- `错误用法辨析`
- `依赖库选型`
- `验证方式`
- `跨场景迁移`

闪记题型必须至少支持：

- 选择题
- 简答题
- 场景问答
- API 方法选择
- 参数 / 返回值判断
- 公式含义解释
- 算法步骤排序或关键步骤追问
- 常见误用纠正

每张闪记卡必须尽量短，但必须足够具体，不能变成泛泛概念问答。

### 1.13 卡片必须与对话、计划、资料、训练深度关联

卡片不能是孤立题库。

每张卡片都必须有明确来源链，至少能说明来自：

- `对话中的用户目标 / 卡点 / 追问`
- `当前总计划或项目子计划阶段`
- `资料库中的文档、API、笔记或知识片段`
- `实战卡片中的错误、验证结果、阻塞或复盘`
- `依赖掌握图中的薄弱层`
- `复习队列中的到期项`

卡片必须服务一个明确学习目的：

- 补一个计划阶段所需能力
- 修一个实战错误
- 记一个 API / 参数 / 返回值
- 建一个最小场景
- 准备一次真实工程落地
- 支撑一次跨项目迁移

如果卡片无法解释“为什么现在出现”，就不能出现。

### 1.14 实战卡片必须有完整工程题规格

实战卡片不是“任务标题 + 鼓励语”。
它必须是一张能把用户带进真实动手的工程训练卡。
更准确地说，实战卡片必须是 `代码训练题`，不是普通学习建议。

Trainer 必须自己负责设计实战卡片的题目、标准、提示层级和验证方法。
用户负责按题目亲手实现。
Trainer 不能把“请你自己想一个练习”当成实战卡。

每张实战卡片至少必须包含：

- `card_id`
- `card_type = practice`
- `project_scope`：全局练习、当前项目、指定项目子计划或空项目最小场景
- `plan_link`：关联的总计划阶段与项目子计划阶段
- `source_chain`：来自哪段对话、哪份资料、哪个计划阶段、哪次训练反馈或哪个依赖薄弱点
- `why_now`：为什么现在练这题
- `target_skill`：本题训练的最小能力点
- `scenario`：真实工程场景或需要用户构建的最小场景
- `problem_statement`：清晰题面，不能只写“实现某功能”
- `suggested_workspace_action`：建议用户自己打开/新建哪个文件、目录或模块
- `api_hints`：相关 API、参数、返回值、边界、常见误用
- `constraints`：用户必须遵守的实现边界
- `deliverable`：用户需要亲手交付什么
- `self_check`：用户完成后先如何自检
- `expected_answer_shape`：正确实现应满足的结构、行为或接口形态
- `validation_method`：Trainer 设计的验证方式，可以是测试、运行结果、静态检查、人工核对或现象观察
- `grading_rubric`：Trainer 评估答案是否合格的标准
- `trainer_review_input`：用户需要把什么带回对话供 Trainer 评估
- `stuck_recovery`：卡住时先降到哪个更小动作
- `reflection_prompt`：做完后复盘什么
- `feedback_targets`：结果回流到哪些能力、闪记、资料、复习或计划证据

实战卡片必须遵守 coach-only 边界：

- [ ] 可以建议“你自己新建 `<path>`”
- [ ] 可以建议“你自己打开 `<path>`”
- [ ] 可以告诉用户应该观察哪段代码
- [ ] 可以解释 API 用法、参数、返回值和误用
- [ ] 可以给伪代码、局部示例、接口形状或验证思路
- [ ] 不得替用户创建文件
- [ ] 不得替用户写入文件
- [ ] 不得替用户修改项目代码
- [ ] 不得默认给完整可粘贴成品补丁
- [ ] 不得在用户还没动手前把最终答案铺满

如果当前是空项目，实战卡片必须能指导用户构建最小场景：

- [ ] 先说明为什么需要这个最小场景
- [ ] 再建议用户自己创建最少文件
- [ ] 再给出最小依赖、最小输入、最小输出
- [ ] 再让用户亲手把 API 或知识点放进场景里
- [ ] 最后把这个场景映射回真实工程可迁移能力

实战卡片必须是计划实施脚手架：

- [ ] 每张实战卡必须关联一个总计划能力或项目子计划阶段
- [ ] 题目必须服务当前计划阶段的具体实施，而不是随机刷题
- [ ] 题目必须把计划中的抽象目标压成“用户现在亲手写什么”
- [ ] 完成标准必须能回写为计划证据
- [ ] 验证失败必须能反向生成闪记、资料标注或更小实战卡
- [ ] 实战卡不能脱离计划长期目标独立刷题

### 1.15 闪记卡片必须有完整知识题规格

闪记卡片不是单纯背诵，也不是把资料切成问答。
它必须把“理论认知、API 记忆、场景判断、误用纠正、实践迁移”压缩成可重复训练的最小卡片。
更准确地说，闪记卡片必须是 `理论知识点掌握卡`。

Trainer 必须自己负责设计闪记卡的问题、标准答案、评分规则、提示层级、错因解释和复习节奏。
闪记不能只显示资料摘录，也不能只让用户“自己总结一下”。

每张闪记卡片至少必须包含：

- `card_id`
- `card_type = flash`
- `knowledge_type`：算法、数学、公式、工程概念、API、参数、返回值、误用、场景、验证、迁移
- `source_chain`：来自对话、计划、资料、实战反馈、依赖掌握图或复习队列
- `why_now`：为什么现在复习或学习它
- `target_skill`：卡片服务的能力点
- `question`：一眼能读懂的问题
- `context`：必要但极短的场景上下文
- `answer_mode`：打字、单选、多选、排序、填空、判断、场景选择
- `expected_answer` 或 `rubric`：标准答案或评分规则
- `verification_method`：如何判断用户答案正确、部分正确或错误
- `knowledge_coverage`：这张卡覆盖理论体系中的哪个节点
- `hint_ladder`：逐级提示，不能一上来暴露答案
- `feedback`：答对、答错、模糊时分别怎么解释
- `common_mistakes`：常见误解或误用
- `related_practice_card`：必要时回到哪张实战卡
- `review_schedule`：何时复习
- `mastery_delta`：本次回答如何影响掌握度

闪记卡片必须覆盖以下知识类型：

- [ ] 算法理论：复杂度、边界、数据结构、递推、剪枝、稳定性、正确性直觉
- [ ] 数学理论：定义、条件、推导直觉、适用边界、单位或维度
- [ ] 公式理解：变量含义、前提条件、什么时候不能用、工程解释
- [ ] 工程概念：抽象边界、状态流、错误处理、幂等、并发、缓存、权限、可观测性
- [ ] API 方法：方法名、调用时机、参数、返回值、异常、异步行为
- [ ] 依赖库用法：核心能力图、常见组合、版本差异、替代方案边界
- [ ] 参数 / 返回值：类型、默认值、副作用、失败模式
- [ ] 场景判断：这个问题该不该用某 API、某模式或某算法
- [ ] 误用辨析：看似能跑但长期会错的写法
- [ ] 验证方式：如何证明实现真的满足要求
- [ ] 跨项目迁移：同一知识点换项目后如何识别落点

闪记必须覆盖理论知识体系，而不是随机知识点：

- [ ] 每个计划阶段必须能拆出本阶段必须掌握的理论知识点
- [ ] 每个依赖库必须能拆出概念、核心 API、参数、返回值、错误、验证、迁移等知识节点
- [ ] 每个算法主题必须能拆出定义、复杂度、边界、正确性、适用场景、误用点
- [ ] 每个数学 / 公式主题必须能拆出变量、条件、推导直觉、单位、适用边界和工程解释
- [ ] 每个工程主题必须能拆出概念、风险、判断条件、验证方式、真实落点
- [ ] 闪记卡组必须能说明当前理论覆盖率，而不是只显示剩余卡片数
- [ ] 理论知识点必须能回流到实战卡验证，不能只停留在答题

闪记交互必须像学习卡片，而不是像阅读文章：

- [ ] 先展示问题，不先展示长解释
- [ ] 用户必须打字、选择、排序或判断
- [ ] 提示分层出现
- [ ] 反馈短、准、可纠错
- [ ] 答错后必须说明错因，而不是只标红
- [ ] 答对后必须指出可迁移场景
- [ ] 连续答错必须降级成更小闪记或转成实战卡
- [ ] 连续答对必须进入更长复习间隔或转入迁移题

### 1.16 卡片产生必须有路由器，不允许随机出题

Trainer 必须有 `card_generation_router`。
它负责把对话、计划、资料、训练结果、依赖掌握和复习队列转成候选卡片。

卡片产生来源必须至少覆盖：

- `conversation_gap`：对话中暴露的目标、误解、卡点、追问、用户自述薄弱点
- `plan_requirement`：总计划或项目子计划当前阶段需要的能力
- `resource_knowledge`：资料库里的 API 文档、算法材料、公式说明、工程案例、笔记片段
- `practice_feedback`：实战卡中的错误、阻塞、验证失败、复盘结论
- `dependency_mastery`：某依赖库 / API 的薄弱层、误用频率、迁移失败点
- `review_due`：到期复习项、低掌握度能力、重复错误

候选卡片进入训练前必须经过筛选：

- [ ] 有明确来源链
- [ ] 有明确 `why_now`
- [ ] 有明确目标能力
- [ ] 不与近期卡片重复
- [ ] 难度适合当前用户状态
- [ ] 服务当前计划、当前项目、当前依赖掌握或当前错误恢复
- [ ] 能在窄侧边栏一张卡内被理解
- [ ] 实战卡可以拆成 20-45 分钟内可推进的最小动作
- [ ] 闪记卡可以在 30-120 秒内完成一次回答

卡片优先级必须综合评估：

- 当前计划阶段必要性
- 当前项目阻塞程度
- 用户近期错误频率
- 资料可信度与新鲜度
- 依赖库掌握度缺口
- 距离上次复习时间
- 是否能带来跨项目迁移收益

### 1.17 卡片回流必须有明确去向

卡片完成不是结束。
卡片结果必须进入 Trainer 的长期学习闭环。

实战卡片结果必须回流到：

- [ ] `practice_review`：用户做了什么、哪里卡住、怎么验证
- [ ] `evidence_item`：只作为计划证据，不自动改正式计划
- [ ] `flash_candidates`：暴露出的概念、API、参数、公式、算法薄弱点
- [ ] `dependency_mastery`：相关依赖库 / API 掌握度变化
- [ ] `resource_annotations`：资料中需要补充、标注或复查的知识片段
- [ ] `master_plan_rollup`：跨项目能力画像的增量证据

闪记卡片结果必须回流到：

- [ ] `mastery_score`：目标知识点掌握度
- [ ] `review_queue`：下一次复习时间
- [ ] `practice_candidates`：需要通过实战验证的知识点
- [ ] `conversation_hint`：下一轮对话中需要补解释的地方
- [ ] `plan_evidence`：只作为能力证据，不自动改正式计划

回流硬规则：

- [ ] 单次答对不能证明掌握，只能提高掌握度
- [ ] 单次答错不能直接改变总计划，只能产生证据或恢复动作
- [ ] 重复答错必须触发降级解释、闪记拆分或实战最小场景
- [ ] 重复答对必须触发间隔拉长、迁移题或真实工程落点
- [ ] 计划变更必须仍然经过显式计划动作或用户明确要求

### 1.18 五个视图必须形成低理解成本联动

用户不应该理解 Trainer 的内部架构才能学习。
五个一级视图必须用最简单的心智模型解释：

- `对话`：教练与用户交互的超级入口，负责回答、教学、追问、压缩下一步、触发候选动作并解释后台正在做什么
- `计划`：只负责看总目标、当前主线、子计划、证据和显式计划动作
- `资料`：只负责像知识库一样查、看、沉淀、引用和治理资料沙箱，不像后台
- `训练`：只负责一张一张地练，默认实战卡或闪记卡
- `设置`：只负责能不能用、卡在哪、怎么配置

跨视图联动必须轻量：

- [ ] 对话里只出现“生成了训练候选 / 查看卡片 / 加入资料证据”的轻提示，不嵌入完整训练工作台
- [ ] 对话里的轻提示必须解释“形成了什么候选、为什么形成、不会自动改什么、建议去哪个视图继续”
- [ ] 对话必须让用户低成本看见教练当前在做什么，例如查资料、整理资料、绑定项目、对齐计划、编排卡片或评估结果，但只能显示轻量人话状态，不能显示底层日志墙
- [ ] 会话信息流必须以消息为中心：用户发送的是消息，Trainer 回复的主形态也必须是消息，不能把回复主体做成后台面板、控制台或表单墙
- [ ] Trainer 回复允许像 `图 1 / 图 2` 那样在消息内部轻量展示动作过程，例如 `正在查资料 / 正在对齐计划 / 正在编排训练 / 已形成下一步`，但这些过程只能附着在消息内，不能长驻成独立管理区
- [ ] 动作过程展示必须服务于读懂当前消息，不得压过消息正文；用户应先读懂回复本身，再选择是否展开过程状态
- [ ] 对话可以发起即时追问、即时小测、单张卡片预告、调用已有卡片或实时设计一张卡片，但仍必须以消息形式呈现，不把训练页搬进消息流
- [ ] 如果需要连续刷卡、沉浸式作答或连续复盘，必须把主战场交给训练页
- [ ] 计划里只展示训练证据摘要，不把训练页搬进计划页
- [ ] 资料里只展示可转卡片或可转证据的入口，不把训练流程搬进资料页
- [ ] 训练里只展示当前卡片必要来源，不把完整资料库或计划治理搬进训练页
- [ ] 设置里不展示训练、资料、计划的业务内容
- [ ] 对话可触发资料检索、网页抓取或资料沙箱处理，但只能给轻量状态提示，不把资料后台塞进消息流
- [ ] 对话可接收文件、文件夹和链接作为上下文输入，但消息流里只展示轻量附件摘要、处理状态和去向
- [ ] 打开项目文件夹或附加 folder 后，必须先给轻量项目判断和 first-look 摘要，再把详情交给资料/项目理解视图 drill-in
- [ ] 资料沙箱处理完成后，只以知识条目、卡片候选、计划证据候选或风险提示回到其他视图

### 1.19 训练是计划页的具体实施脚手架

`计划` 定义“为什么学、学到哪、用什么证据证明”。
`训练` 负责把计划拆成用户每天可以刷、可以做、可以验证的卡片脚手架。

必须成立：

- [ ] 计划页不直接承载训练工作台
- [ ] 训练页不脱离计划随机刷题
- [ ] 总计划能力必须能拆到训练目标
- [ ] 项目子计划阶段必须能拆到实战卡
- [ ] 计划阶段所需理论必须能拆到闪记卡
- [ ] 训练完成结果必须回到计划证据
- [ ] 计划证据必须等待显式采纳，不能自动改正式计划

计划到训练的映射必须固定为：

- `计划目标` -> `训练目标`
- `阶段能力` -> `实战卡题目`
- `理论缺口` -> `闪记卡组`
- `依赖/API 缺口` -> `API 闪记 + 最小实战场景`
- `验证要求` -> `实战卡验证方法`
- `完成证据` -> `计划证据队列`

训练页的核心产品隐喻是：

`像不背单词一样刷卡，但刷的是理论知识点和代码实战题。`

这意味着：

- [ ] 用户一次只面对一张卡
- [ ] 每张卡必须能作答或动手
- [ ] 每张卡必须有标准答案、验证方法或评分规则
- [ ] 刷完一张才能进入下一张、转实战、回对话或复盘
- [ ] 卡片不是内容展示，而是计划实施动作

### 1.20 Trainer 是跨项目统一的定制化教练 Agent

Trainer 的本质不是五个页面，也不是资料库、计划表、训练器的拼装。
Trainer 的本质是一个 `跨项目一致统一的定制化教练 Agent`。

五个一级视图只是这个 Agent 的五个工作表面：

- `对话`：Agent 与用户共同诊断、解释、追问、压缩下一步的表面
- `计划`：Agent 对长期目标、项目子目标、证据和节奏进行治理的表面
- `资料`：Agent 与用户共同管理跨项目知识库、资料沙箱、来源可信度和知识原子的表面
- `训练`：Agent 把计划和资料转成闪记卡、实战卡并评估结果的表面
- `设置`：Agent 保证模型、运行时、权限和数据边界可用的表面

必须成立：

- [ ] Agent 身份跨项目唯一
- [ ] Agent 的长期能力画像跨项目统一
- [ ] Agent 的教学风格、边界和记忆策略跨项目一致
- [ ] Agent 能区分“用户当前项目子目标”和“用户长期综合目标”
- [ ] Agent 能把任一项目中的证据回流到统一能力画像
- [ ] Agent 能维护一个跨项目统一资料库，并把资料按项目、计划、训练和依赖能力建立绑定
- [ ] Agent 能在资料沙箱内自主管理资料内容，但不能越界写用户工程空间
- [ ] Agent 不能因为切换项目而忘掉用户理论薄弱点、依赖库掌握度或长期目标

用户使用闭环必须简单：

1. 用户在 `对话` 中说目标、问题、卡点或带回训练结果。
2. 用户在 `资料` 中放入文档、笔记、API、案例或项目材料，也可以让 Trainer 检索网页并下载到资料库。
3. 用户在 `计划` 中查看总目标、当前阶段、项目子计划和证据。
4. 用户在 `训练` 中一张张刷闪记卡和实战卡。
5. 用户把实战结果、答题错误、验证输出或疑问带回 `对话`。

Agent 使用闭环必须强大：

1. Agent 从 `对话` 中识别目标、误解、卡点、情绪、计划意图和训练反馈。
2. Agent 从 `资料` 中抽取知识原子、API 语义、理论点、工程案例和可信度，并在资料沙箱内维护可追踪派生资料。
3. Agent 从 `计划` 中读取当前阶段、目标能力、项目子计划和证据缺口。
4. Agent 在 `训练` 中生成闪记卡、实战卡、标准答案、验证方法和评分规则。
5. Agent 从训练结果中更新掌握度、复习队列、资料标注、计划证据和总计划画像。

Agent 触发规则必须明确：

- [ ] 对话暴露概念不清 -> 生成闪记候选或解释回合
- [ ] 对话暴露工程卡点 -> 生成实战卡候选或最小场景
- [ ] 对话暴露计划意图 -> 生成计划候选提示，但必须明确“尚未改正式计划”
- [ ] 对话附加文件、文件夹或链接 -> 生成资料导入候选、项目上下文候选或资料缺口提示
- [ ] 用户上传资料 -> 生成知识原子、闪记候选、实战候选和计划证据候选
- [ ] 对话或训练需要依据 -> 检索全局资料库，必要时浏览网页并下载有用内容到资料沙箱
- [ ] 资料过期或冲突 -> 标注可信度、暂停相关卡片、触发重新检索或派生资料更新
- [ ] skill 可提升资料处理质量 -> 在资料沙箱权限域内下载/启用/运行受控 skill，并记录影响范围
- [ ] 计划阶段推进 -> 生成该阶段训练目标、理论卡组和实战卡组
- [ ] 闪记答错 -> 生成更小闪记、解释回合或实战验证
- [ ] 闪记答对多次 -> 拉长复习间隔，或生成迁移/实战验证
- [ ] 实战失败 -> 生成错因、闪记、资料标注和更小实战卡
- [ ] 实战通过 -> 生成复盘、计划证据和迁移候选
- [ ] 多项目证据积累 -> 更新总计划能力画像

如果一个功能不能说明它服务上述哪条 Agent 触发规则，就不应该进入核心流程。

### 1.21 打开文件夹后的第一判断

Trainer 按项目文件夹管理内容，但 Trainer 本体必须跨项目统一。
因此用户打开任意文件夹时，Trainer 不能默认认为这是“新项目从零开始”，也不能默认沿用上一个项目上下文。

打开文件夹后必须先做 `project_context_classification`：

| 文件夹类型 | 判断依据 | 初始计划策略 | 初始训练策略 | 禁止行为 |
|---|---|---|---|---|
| 空项目 / 新项目 | 文件少、无主要代码结构、无业务 README、无依赖图 | 生成项目子计划候选，先不改正式计划 | 最小场景卡、基础 API 卡、项目脚手架理解卡 | 替用户创建项目文件 |
| 已有工程项目 | 有源码、依赖、测试、配置、业务模块 | 读取当前项目子计划或生成候选 | 项目理解卡、源码阅读卡、局部修改实战卡、验证卡 | 一上来给重构方案或改代码 |
| 算法 / 模型实现仓库 | 有训练脚本、模型文件、算法模块、实验配置或论文材料 | 生成算法/模型掌握子计划候选 | 理论闪记、公式/复杂度卡、实现走读卡、复现实战卡 | 只讲概念不读实现 |
| idea / 草稿文件夹 | 有笔记、PRD、草图、README，但缺少完整代码 | 生成 idea 落地子计划候选 | 需求澄清卡、架构拆解卡、最小切片实战卡 | 直接生成完整项目代码 |
| 学习资料文件夹 | 文档、链接、笔记多，代码少 | 生成知识库与学习阶段候选 | 资料拆解卡、API/概念闪记、空项目最小实战 | 只做文件列表 |
| 混合/不确定 | 信号冲突或材料不足 | 保持只读候选，向用户给最小澄清 | 生成诊断卡或对话澄清 | 强行归类并推进计划 |

必须满足：

- [ ] 文件夹分类只产生上下文和候选，不自动改总计划或正式子计划。
- [ ] 每个文件夹必须绑定一个 `project_id`、`project_type`、`project_subplan`、`project_training_lane`。
- [ ] 同一个用户的 `trainer_identity`、长期能力画像、依赖掌握图和总计划必须跨文件夹共享。
- [ ] 当前项目的证据只能先进入当前项目子计划，再按证据质量回流总计划。
- [ ] 切换文件夹时必须说明“这是新项目、已有项目、算法/模型项目、idea 项目还是不确定项目”。
- [ ] Trainer 必须能给出项目文件夹的基础可视摘要：入口文件、目录锚点、核心模块、风险区、可训练点，而不是只显示路径名。
- [ ] 作为资料导入的 folder 必须保留树状锚点、文件级摘要和来源链，后续可同时服务资料页、项目理解和训练编排。

#### 1.21.1 folder first-look 固定摘要协议

无论 folder 是通过“打开工作区”“对话附带文件夹”“资料导入 folder”还是“切换项目”进入，Trainer 都必须先生成同一套 `first-look summary`。

`first-look summary` 必须固定包含：

- [ ] `folder_role`：当前更像 `project`、`resource_folder`、`mixed`、`uncertain`
- [ ] `project_type_guess`：空项目、已有工程、算法仓库、模型仓库、idea 文件夹、资料文件夹、不确定
- [ ] `confidence`
- [ ] `why_this_guess`
- [ ] `entry_points`
- [ ] `directory_anchors`
- [ ] `core_modules_or_materials`
- [ ] `risk_zones`
- [ ] `training_opportunities`
- [ ] `unknowns`
- [ ] `recommended_next_step`

表现硬规则：

- [ ] first-look 首屏只能是摘要，不得直接展开完整文件树。
- [ ] first-look 必须先回答“这是什么”和“建议先看哪里”，再回答“里面有什么”。
- [ ] `resource_folder` 与 `project` 不能共用完全相同文案，必须明确当前主要用途。
- [ ] `mixed` 必须说明“为什么混合”，并给默认主用途建议。
- [ ] `uncertain` 不能假装判断成功，必须暴露未知点。

folder 双语义协议：

- [ ] 同一 folder 可以同时拥有 `project_context` 和 `resource_scope`，但必须有一个当前主语义。
- [ ] 如果当前主语义是 `project`，训练编排优先服务项目理解和项目子计划。
- [ ] 如果当前主语义是 `resource_folder`，训练编排优先服务知识拆解和卡片候选，而不是直接假设工程修改。
- [ ] 从 `resource_folder` 切到 `project`，必须重新做 project grounding，不能沿用旧判断。
- [ ] 从 `project` 切到 `resource_folder`，不得把工程证据误写入资料知识结论。

### 1.22 四类工作主场景必须成为一等流程

Trainer 必须正式覆盖以下工作场景，而不是只支持泛泛学习。

| 主场景 | 用户可能怎么说 | Agent 第一判断 | 训练编排 | 回流对象 | 禁止行为 |
|---|---|---|---|---|---|
| 掌握已有项目 / 算法 / 模型实现方法 | “帮我看懂这个项目”“我想掌握这个模型怎么实现”“这个算法仓库怎么学” | 这是理解现有实现，不是从零开发 | 项目地图卡 -> 关键模块闪记 -> 源码走读实战卡 -> 复现实战卡 -> 迁移卡 | project_understanding、algorithm_mastery、model_implementation_mastery、plan_evidence | 只总结 README、不生成训练、不让用户亲手走读 |
| 帮助 idea 实现成为代码 | “我有个想法想做成项目”“这个 idea 怎么落地” | 这是需求澄清 + 最小切片训练，不是代写项目 | 需求澄清卡 -> 用户故事/边界卡 -> 架构选择闪记 -> 最小切片实战卡 -> 验证卡 -> 复盘卡 | idea_plan_candidate、practice_card、project_subplan_candidate | 一次性输出完整代码工程 |
| 掌握库的 API 用法 | “帮我掌握 FastAPI/React/某库 API”“这个方法怎么用” | 这是依赖掌握图，不是单次问答 | API 概念卡 -> 参数/返回值闪记 -> 误用辨析卡 -> 最小场景实战卡 -> 当前项目迁移卡 | dependency_skill_map、flash_deck、scenario_lab、mastery_rollup | 只摘要文档或给复制代码 |
| 在现有项目上做深度优化和修改 | “帮我优化这个模块”“我想重构/改这个功能”“性能/架构怎么改” | 这是已有项目改进训练，不是自动修改 | 现状理解卡 -> 风险/测试闪记 -> 修改计划卡 -> 用户自实现实战卡 -> 验证/回归卡 -> 复盘卡 | project_change_candidate、practice_review、risk_evidence、plan_evidence | 直接改代码、跳过现状理解和验证 |
| 工作中单纯对话 | “这个思路对吗”“帮我分析一下”“我只是想讨论方案” | 这是纯对话，不一定进入训练或计划 | 可只回答、追问、比较、解释；必要时只给轻量候选 | conversation_note、optional_candidate | 强行生成卡片、强行改计划、强行跳训练 |

必须满足：

- [ ] 每个主场景都能处理清晰需求和模糊需求。
- [ ] 清晰需求必须快速压缩到下一步，不用做长篇系统解释。
- [ ] 模糊需求必须先诊断意图、给 1-3 个可选方向或最小澄清问题。
- [ ] 任何主场景都必须坚持 coach-only，用户自己改、自己建、自己验证。
- [ ] 任何主场景的训练卡都必须能解释“为什么现在练这张”。

### 1.23 训练卡片编排必须按项目和目标生成

训练不是随机卡片流。
训练必须根据 `project_context_classification`、主场景、计划阶段、资料来源、用户薄弱点和复习队列编排。

卡片编排必须遵守：

1. `先理解，再记住，再动手，再迁移`。
2. `先当前项目，再跨项目总结`。
3. `先最小可验证动作，再复杂优化/架构迁移`。
4. `先用户当前阻塞，再长期复习`。
5. `先一张当前卡，再展开队列和治理`。

不同项目类型的默认训练编排：

| 项目类型 | 默认卡片顺序 | 目标 |
|---|---|---|
| 空项目 / 新项目 | 目标澄清闪记 -> API 基础闪记 -> 最小场景实战 -> 自检卡 -> 迁移提示 | 建立从零动手能力 |
| 已有工程项目 | 项目地图闪记 -> 关键模块阅读实战 -> 局部修改实战 -> 测试验证卡 -> 复盘卡 | 掌握现有结构并能安全修改 |
| 算法项目 | 问题定义卡 -> 复杂度/边界闪记 -> 核心步骤排序卡 -> 实现走读实战 -> 变体迁移卡 | 掌握算法理论和实现方法 |
| 模型项目 | 模型结构卡 -> 数据流/训练流程卡 -> 关键模块走读实战 -> 复现实战 -> 调参/迁移卡 | 掌握模型实现与实验路径 |
| idea 项目 | 需求澄清卡 -> 范围切片卡 -> 架构取舍卡 -> 最小功能实战 -> 验证和复盘卡 | 把想法变成用户亲手实现的最小版本 |
| API 学习项目 | 概念卡 -> 方法/参数/返回值卡 -> 误用卡 -> 最小场景实战 -> 当前项目迁移卡 | 从文档理解走到工程使用 |
| 优化/修改项目 | 现状卡 -> 风险卡 -> 测试/指标卡 -> 修改实战卡 -> 回归复盘卡 | 安全完成深度优化和修改 |

多项目统一与分项目治理必须同时体现在编排中：

- [ ] `project_training_lane` 保存当前项目卡片、结果和证据。
- [ ] `master_training_rollup` 汇总跨项目重复薄弱点、长期掌握度和迁移能力。
- [ ] 项目内卡片优先服务当前项目子计划。
- [ ] 跨项目复习卡优先服务总计划长期能力。
- [ ] 同一 API、算法或模型能力在多个项目出现时，必须提升迁移掌握度，而不是重复当新知识。
- [ ] 当前项目失败不会直接降低总计划结论，只能进入证据并由总计划弹性评估。

### 1.24 资料库是跨项目统一的 Agent 沙箱知识库

资料不是附件区，也不是只读文件预览器。
资料必须是 `跨项目统一知识库 + Trainer 可治理沙箱`。

资料库的定位必须同时满足：

- `跨项目统一`：一个用户只有一个长期资料库，不按项目割裂成多个孤岛。
- `可按项目绑定`：每条资料可以绑定 0 个、1 个或多个项目、子计划、训练卡、API 能力和总计划目标。
- `可被 Trainer 管理`：Trainer 可以在资料沙箱内主动浏览、下载、导入、整理、索引、拆解、标注、归档和生成派生资料。
- `可被用户补充`：用户可以上传 HTML、PDF、Markdown、文本、代码文档、README、API 文档、论文、笔记、网页快照、日志和错误材料。
- `可用于教学闭环`：资料必须能进入知识原子、闪记卡、实战卡、依赖掌握图、计划证据和训练复盘。

资料库与项目的关系必须固定为：

- [ ] `global_resource_library` 保存跨项目统一资料条目、来源、标签、可信度、新鲜度、知识原子和索引。
- [ ] `project_resource_links` 只保存某项目为什么使用某条资料、服务哪个子计划、产生了哪些卡片或证据。
- [ ] 同一资料被多个项目使用时，不复制正文，只增加项目绑定和使用证据。
- [ ] 资料更新后，所有受影响项目必须能看到影响范围、相关卡片和待复查计划证据。
- [ ] 当前项目可以有项目资料视图，但它只是全局资料库的过滤结果，不是另一个资料库。

Trainer 管理资料沙箱必须支持：

- [ ] 网页浏览与检索：当回答、训练或计划需要依据时，Trainer 可以搜索网页、阅读页面并把有用来源保存为资料条目。
- [ ] 下载与归档：Trainer 可以把网页、HTML、PDF、Markdown、代码文档或 API 文档下载到资料沙箱。
- [ ] 格式归一：HTML、PDF、Markdown、代码文档必须被解析为 metadata、正文片段、代码片段、表格、公式、链接和知识原子。
- [ ] 来源治理：每个条目必须记录 URL / 文件路径、导入者、导入时间、抓取时间、许可证或使用限制、可信度、新鲜度和引用链。
- [ ] 派生资料：Trainer 可以生成摘要、术语表、API 表、FAQ、错因说明、版本差异说明、卡片候选和训练提示。
- [ ] 沙箱写入：Trainer 可以在沙箱内创建、改写、重命名、移动、归档派生资料和索引文件。
- [ ] 回滚与审计：任何沙箱写操作必须可查看、可回滚、可归档，不允许不可恢复硬删。
- [ ] 隔离与权限：所有写操作只能发生在资料沙箱根目录或其受控子目录内，不能写入用户工程空间。
- [ ] 跨系统一致：Windows、macOS、Linux 上的路径、换行、编码、权限、文件监听、下载缓存和解析结果必须语义一致。

Trainer 使用或下载 skill 管理资料沙箱必须受约束：

- [ ] skill 只能服务资料解析、网页抓取、格式转换、索引、去重、知识抽取、可信度检查、卡片生成或资料迁移。
- [ ] skill 必须有 manifest：名称、用途、输入输出、允许文件范围、网络权限、命令权限、风险等级和回滚策略。
- [ ] 下载 skill 前必须进入隔离待审状态，只有通过安全检查后才能用于资料沙箱。
- [ ] skill 运行时的工作目录、环境变量、输出目录和网络访问必须被限制。
- [ ] skill 不能读取 VS Code SecretStorage、不能上传用户项目代码、不能写用户工程空间。
- [ ] skill 运行结果必须写入资料操作日志，并能追踪到哪些资料条目、知识原子、卡片或计划证据受影响。

资料库与其他视图的治理关系必须固定：

- [ ] `资料` 跨项目统一，负责知识来源和沙箱治理。
- [ ] `训练` 分项目治理，当前卡片优先来自当前 `project_training_lane`，跨项目复习只服务长期能力。
- [ ] `对话` 统一主体 + 当前项目上下文结合，既能回答全局问题，也能引用当前项目与资料库证据。
- [ ] `计划` 必须总计划 + 项目子计划结合，总计划看长期能力，子计划看当前项目阶段。
- [ ] 资料可以生成计划证据候选，但不能直接改正式总计划或项目子计划。
- [ ] 资料可以生成训练候选，但当前训练卡仍由卡片路由器按项目、计划、薄弱点和复习队列选择。

资料库不能退化成：

- [ ] 只能上传不能被 Trainer 主动管理的附件库。
- [ ] 只能预览不能沉淀知识原子的文件列表。
- [ ] 每个项目一套孤立资料，导致 API、算法、模型知识无法跨项目复用。
- [ ] 无来源、无审计、无回滚的自动下载目录。
- [ ] skill 可以随意碰用户工程代码的伪沙箱。

### 1.25 资料沙箱和 skill 必须跨 Windows / macOS / Linux 统一

Trainer 的资料沙箱不能只在开发者当前系统上成立。
它必须在 Windows、macOS、Linux 三类桌面环境中保持同一套产品语义。

跨系统统一的目标不是“每个平台代码完全一样”，而是：

- 用户看到的资料库能力一致。
- Trainer 管理沙箱的权限边界一致。
- skill 的输入输出、日志、回滚和越权拦截一致。
- 同一份资料在不同系统中解析出的知识原子和卡片候选一致或可解释差异。

必须建立统一抽象：

- [ ] `sandbox_root`：每个平台都有明确、可迁移、可显示的资料沙箱根目录。
- [ ] `workspace_root`：用户工程空间与资料沙箱根目录必须始终分离。
- [ ] `virtual_resource_path`：资料条目对上层暴露统一虚拟路径，不把 Windows 盘符或 POSIX 路径泄漏到卡片核心语义里。
- [ ] `platform_path`：真正文件路径只在 extension / sidecar 边界转换。
- [ ] `path_policy`：路径 join、normalize、resolve、symlink / junction / shortcut 处理必须防止逃逸沙箱。
- [ ] `encoding_policy`：默认 UTF-8，遇到 GBK、Shift-JIS、Latin-1 等必须记录检测结果和转换状态。
- [ ] `newline_policy`：CRLF / LF / CR 不影响资料解析、代码文档切片和知识原子定位。
- [ ] `case_policy`：大小写敏感差异必须被吸收，不能让同一资料在不同系统重复入库或覆盖。
- [ ] `permission_policy`：只读文件、权限不足、workspace trust 不足时必须降级而不是失败白屏。

跨系统 shell 和命令策略：

- [ ] Windows 默认 PowerShell，macOS / Linux 默认 POSIX shell；命令模板不得混用。
- [ ] 资料 skill 必须声明支持的平台：`windows`、`macos`、`linux` 或 `cross_platform`。
- [ ] 任何 shell 命令都必须以沙箱根目录为工作目录，并通过参数数组或安全转义传参。
- [ ] 禁止通过拼接字符串构造删除、移动、下载、解压等危险命令。
- [ ] 不同平台缺少依赖时，必须给出可读降级状态，例如“只能索引 metadata，PDF 深解析待依赖恢复”。

跨系统资料处理必须覆盖：

- [ ] HTML：编码、相对链接、图片资源、代码块、表格、标题层级。
- [ ] PDF：文本层、页码、表格、公式、扫描件 OCR 状态、附件或图片引用。
- [ ] Markdown：frontmatter、代码块语言、相对链接、图片、数学公式。
- [ ] 代码文档：README、docstring、注释、API 示例、类型签名、配置文件和测试样例。
- [ ] 压缩包或批量目录：解压目录必须在沙箱内，防 zip-slip / tar-slip。
- [ ] 网页下载：URL、重定向、缓存、robots/许可提示、抓取时间、内容 hash 必须记录。

跨系统验证必须至少包含：

- [ ] Windows 路径含空格、中文、盘符和反斜杠。
- [ ] macOS 路径含空格、大小写差异和应用沙箱权限。
- [ ] Linux 路径含 symlink、只读权限和大小写敏感。
- [ ] 同一 Markdown / HTML / PDF 样例在三端生成等价 metadata、knowledge_atoms 和 source_chain。
- [ ] skill 在三端都不能越权写用户工程空间。
- [ ] 沙箱回滚、归档、重命名和索引更新在三端都可恢复。

### 1.26 Trainer 必须支持中文 / English 双语闭环

Trainer 的双语能力不是“把 UI 翻译一下”。
双语必须进入 Agent、资料、计划、训练、卡片、评估、搜索和证据链。

必须支持：

- [ ] `中文`：适合中文用户的对话、题面、反馈、资料摘要、计划说明和 UI 文案。
- [ ] `English`：适合英文工作流的 chat, plan, resource, training card, feedback, settings copy。
- [ ] `mixed`：用户资料、代码、API 文档和对话可以中英混合，Trainer 必须稳定处理。
- [ ] 用户可以设置 `preferred_language`，也可以按会话或项目覆盖。
- [ ] Agent 必须跟随用户当前语言回复；引用英文 API 名称、代码标识符和错误信息时不得强行翻译。

双语数据模型必须包含：

- [ ] `language`：条目主语言，例如 `zh-CN`、`en`、`mixed`。
- [ ] `source_language`：原始资料语言。
- [ ] `display_language`：当前 UI 展示语言。
- [ ] `bilingual_title`：必要时保留中英标题。
- [ ] `bilingual_summary`：必要时保留中英摘要。
- [ ] `term_map`：术语映射，例如中文概念、英文 API 名、缩写、别名。
- [ ] `translation_state`：原文、机器翻译、人工修订、待校验、不可翻译。
- [ ] `language_confidence`：语言识别置信度。

双语资料能力必须满足：

- [ ] 英文 API 文档可以生成中文解释、中文闪记、英文术语保留的实战卡。
- [ ] 中文教程可以生成英文关键词索引，方便搜索英文 API 名称。
- [ ] 同一个知识原子可以有中英两种表述，但必须共享同一个 mastery 节点，不能重复计数。
- [ ] 术语翻译必须可追踪，不能把技术名词翻译到用户看不懂。
- [ ] 搜索必须支持中文、英文、拼写变体、API 名、缩写和代码符号。

双语训练能力必须满足：

- [ ] 闪记卡可以用中文问、英文术语答；也可以用英文问、中文解释。
- [ ] 实战卡题面跟随用户语言，但代码标识符、文件名、API 名称保持原样。
- [ ] 评分 rubrics 必须理解中英混合答案。
- [ ] 用户答题语言不同于 UI 语言时，不能误判为错误。
- [ ] 复习队列按知识节点管理，不按语言副本重复刷同一知识。

双语 UI 必须满足：

- [ ] 五个一级视图名称、空状态、按钮、错误、恢复提示都有中文和英文文案。
- [ ] 窄侧栏下中文长句和英文长词都不能溢出、重叠或遮挡主动作。
- [ ] 设置页必须能切换语言偏好，并说明会影响 UI、对话、卡片和资料摘要。
- [ ] 对话页可以显示“按当前语言回答 / 保留术语原文 / 输出双语摘要”等轻量控制。
- [ ] 资料页必须能按语言筛选、查看原文、查看摘要和查看术语映射。

双语禁止项：

- [ ] 把代码标识符、命令、路径、API 名称强行翻译。
- [ ] 中文和英文资料各自形成两套重复知识图谱。
- [ ] UI 只翻译导航，不翻译训练反馈、错误恢复和计划解释。
- [ ] 卡片答案因为语言不同被误判。
- [ ] 英文资料下载后只存英文摘要，无法服务中文训练。

### 2.1 本轮 5 张参考图是形态与气质参考源，不是机械抄图模板

本轮用户指定的 5 张参考图已经固化到：

- `docs/shared/design-references/2026-05-23-trainer-ui/01-overall-vscode-chat-reference.png`
- `docs/shared/design-references/2026-05-23-trainer-ui/02-overall-desktop-reference.png`
- `docs/shared/design-references/2026-05-23-trainer-ui/03-training-card-reference.png`
- `docs/shared/design-references/2026-05-23-trainer-ui/04-resources-list-reference.png`
- `docs/shared/design-references/2026-05-23-trainer-ui/05-resources-grid-reference.png`

这 5 张图的角色必须写死为：

- `图 1 / 图 2`：整体气质与壳层参考，强调窄栏、克制、工具感、留白和对话主导。
- `图 3`：训练页参考，强调单卡沉浸、主任务唯一、反馈后置、操作低干扰。
- `图 4 / 图 5`：资料页参考，强调搜索优先、分组浏览、目录化内容承载和轻量详情进入。

必须明确写死：

- `5 张图都是参考源，但都必须经过 Trainer 定位定向调整`
- `不能把任何一张图原样照抄进 VS Code 侧边栏`
- `不能把移动端返回栏、系统状态栏、iOS tab bar、超大圆角和平台特有控件直接搬进 Trainer`
- `不能把参考图中的审美元素凌驾于 Trainer 的教练定位、单栏主任务和 VS Code 窄栏约束之上`

真正要吸收的不是“长得像”，而是：

- 宽度感与留白节奏
- 顶部 chrome 的克制程度
- 首屏主任务排序
- 单栏结构的稳定性
- 列表和卡片的主次关系
- 搜索优先而不是管理优先
- 沉浸式单卡而不是卡片墙
- 不像网页、像桌面工具的气质

### 2.1.1 5 张参考图对 Trainer 的定向映射

必须固定为：

- `对话`
  - 主要吸收 `图 1 / 图 2`
  - 目标：窄栏、纯对话、底部紧凑输入托盘、顶部超轻、消息区绝对主角
  - 禁止：复制桌面大画布留白过度、复制外部产品的宽对话气泡结构、复制移动端返回栏

- `训练`
  - 主要吸收 `图 3`
  - 目标：一张一张刷、沉浸、层级稳定、辅助信息后置、主动作始终可见
  - 禁止：照搬背词产品语义；Trainer 必须保持 coach-only、代码训练题和回流证据链

- `资料`
  - 主要吸收 `图 4 / 图 5`
  - 目标：像知识库与浏览器的混合体，搜索优先，列表/分组/目录浏览清楚，详情 drill-in
  - 禁止：退化成文件管理器或移动端云盘翻版；Trainer 必须保留来源、可信度、计划绑定、卡片候选与沙箱边界

### 2.1.2 参考图转译后的硬禁令

以下做法都算“抄图失败”而不是“借鉴成功”：

- [ ] 直接复制移动端顶栏、返回按钮、系统状态栏。
- [ ] 直接复制 iOS 风格底部 tab 到 VS Code 侧边栏。
- [ ] 直接复制超大圆角、毛玻璃和大面积移动端留白，导致窄栏有效信息密度下降。
- [ ] 只学到视觉装饰，没有学到单主任务与渐进展开。
- [ ] 把资料页做成真文件管理器，而不是跨项目知识库 + 受控沙箱。
- [ ] 把训练页做成背词产品翻版，而不是代码教练的单卡训练流。
- [ ] 把整体参考图的“安静感”误做成“空白很多但没有推进信息”。

### 2.2 默认宽度假设必须先按窄侧边栏设计

所有视图必须先按以下宽度工作：

- `主设计宽度：280px - 420px`
- `压缩可用宽度：240px - 279px`
- `超过 420px` 只能做增强，不能成为成立前提
- `不得假设 480px+ 才能看懂`

任何一级视图如果必须依赖宽网页宽度才能“正常”，就判定为失败。

### 2.3 默认高度与首屏必须先服务任务，不服务展示

必须满足：

- 首屏先出现当前最重要动作
- 首屏先出现当前最重要判断
- 首屏先出现当前最重要状态
- 首屏不能先被大段介绍、巨型卡片、历史列表、重复摘要占满

### 2.4 Sidebar-first，不是 Web-first

必须写死：

- Trainer 是 `desktop narrow sidebar`
- 不是 `mobile web`
- 不是 `responsive web dashboard`
- 不是 `文档站`
- 不是 `管理后台`

禁止使用“把宽网页压窄”作为设计方法。

正确方法只能是：

`先按窄侧边栏定义主交互，再在更宽状态做可选增强。`

### 2.5 单栏优先，逐层展开，渐进披露

所有一级视图默认必须：

- 以 `单栏` 为主
- 以 `一条主任务线` 为主
- 以 `逐层展开` 为主
- 以 `需要时再看细节` 为主

不能默认：

- 双栏并排
- 三栏并排
- 多块同权大卡片同时争抢注意力
- 把“所有能力都铺开”当首屏

### 2.6 侧边栏的高级感来自克制，不来自堆功能

高级感必须来自：

- 分层清楚
- 动作明确
- 工具感强
- 密度高但不挤
- 状态诚实
- 视觉克制

不是来自：

- 巨量卡片
- 大面积装饰
- 过多边框
- 过多胶囊标签
- 一屏同时塞满所有能力

## 3. 当前 VS Code 扩展已暴露出的严重问题

本节不是建议，是必须写入主清单的 `已知严重问题`。

这些问题要么已经从当前截图中暴露，要么已经从当前实现结构中被确认。

### 3.1 顶部区域过重，严重挤占首屏

- [ ] 顶部导航、标题、状态、动作区在窄宽度下过于拥挤。
- [ ] 顶部固定区过高，吃掉过多垂直空间。
- [ ] 历史条、搜索条、标题条如果长期同时常驻，会把真正任务区压到首屏以下。
- [ ] 用户刚打开时，最先看到的不是“现在该做什么”，而是一堆结构壳层。

### 3.2 当前很多页面仍然是网页式布局，不是侧边栏式布局

- [ ] 存在明显的网页式大卡片堆叠。
- [ ] 存在面向宽屏的多列网格思路。
- [ ] 存在“页面介绍 + 面板 + 次面板 + 详情栏”的网页后台套路。
- [ ] 存在“先解释系统，再让用户操作”的网页 onboarding 思路。

### 3.3 信息层级不对，很多东西同时争抢第一视线

- [ ] 一个视图里经常同时出现多个同权区域。
- [ ] 首屏缺少唯一主任务。
- [ ] 同时展示太多摘要、标签、状态、说明，导致用户第一眼不知道该点哪里。
- [ ] 说明性文案常常比动作更抢眼。

### 3.4 侧边栏宽度被错误地当成“压缩版网页”

- [ ] 许多布局仍隐含假设“再宽一点就好了”。
- [ ] 许多元素的阅读与点击舒适度依赖更宽空间。
- [ ] 许多组件在窄栏里只是勉强塞下，而不是原生适合。
- [ ] 当前不少设计更像“网页缩放失败”，而不是“扩展工具设计成功”。

### 3.5 对话区也存在网页化问题

- [ ] 输入框默认过高，像网页写作框，不像侧边栏快速往返输入区。
- [ ] 历史恢复信息如果以大块列表常驻，会压缩消息区。
- [ ] 对话首屏容易被外层壳层占掉，而不是尽快进入当前对话。

### 3.6 `计划` 页存在过强的仪表板倾向

- [ ] 容易堆叠过多治理卡片、统计卡片、历史卡片，像仪表板而不是内容视图。
- [ ] 当前步骤、为什么现在是这一步、如何验证，可能被太多辅助治理信息挤压。
- [ ] 正式计划、子计划、证据、历史如果同时铺开，窄栏里理解成本会急剧上升。

### 3.7 `资料` 页当前最危险，最容易退化成小型网页后台

- [ ] 列表、沙箱、详情并排的思路是典型网页管理台思路，不是侧边栏思路。
- [ ] 资料详情与沙箱预览如果默认并排，会直接假设宽网页。
- [ ] 上传、过滤、预览、编辑如果全部同时展开，会让侧边栏失去主焦点。

### 3.8 `训练` 页容易被做成“很多功能的大页”，而不是“当前训练工作台”

- [ ] 如果练习、闪记、理论题、复盘、复习队列同时重堆首屏，会直接失控。
- [ ] 如果当前训练任务没有被绝对优先展示，训练区就会变成浏览区。
- [ ] 如果“为什么现在练”与“你要自己实现什么”不够靠前，训练就会变成文本说明页。
- [ ] 如果实战卡片不能清楚给出题目、建议文件、API 提示、交付物和验证方式，训练就只是任务摘要。
- [ ] 如果闪记卡片只背 API、不覆盖算法、数学、公式、工程判断和误用辨析，知识闭环就不完整。
- [ ] 如果卡片无法说明来自哪次对话、哪个计划阶段、哪份资料或哪次实战反馈，卡片就是孤立题库。
- [ ] 如果恢复路线、历史、治理信息默认展开在当前卡片之前，训练交互就失败。

### 3.9 `设置` 页当前最容易显得反人性

- [ ] 在窄侧边栏里再套一层左导航 + 右内容，是典型的“侧栏里再嵌网页设置页”。
- [ ] 表单字段过多时，如果没有分层，会让设置看起来像开发者控制台。
- [ ] 用户真正需要的通常只是“能不能用、先配什么、卡在哪”，不是一上来看到全部高级配置。

### 3.10 视觉噪音过高

- [ ] 芯片过多。
- [ ] 边框过多。
- [ ] 区块切分过碎。
- [ ] 同类信息重复出现。
- [ ] 每个视图都像“想证明功能很丰富”，而不是“想让用户迅速完成任务”。

### 3.11 本轮 5 张参考图转译后必须持续防止的反模式

必须明确写入：

- [ ] 不允许顶部导航、标题、状态在窄栏里互相打架。
- [ ] 不允许一级视图默认以网页式大卡片堆满首屏。
- [ ] 不允许多栏布局成为默认成立方式。
- [ ] 不允许设置页继续像嵌套网页。
- [ ] 不允许资料页继续像小型 CMS 后台，也不允许退化成单纯文件管理器。
- [ ] 不允许训练页继续像说明书，也不允许退化成“背词 App 的代码换皮”。
- [ ] 不允许用“响应式适配”掩盖“默认设计基线错误”。
- [ ] 不允许只复制参考图的审美壳层，却丢失 Trainer 的教练边界、知识库语义和单卡训练闭环。

## 4. 全局布局与交互硬约束

### 4.1 所有一级视图都必须先满足窄栏可用

- [ ] 每个一级视图必须先在 `280px - 420px` 内好用。
- [ ] 每个一级视图都必须在窄栏中有明确主任务。
- [ ] 每个一级视图都必须在首屏给出明确下一步。
- [ ] 任何宽栏增强都不能破坏窄栏主路径。

### 4.2 默认只能是一栏主结构

硬约束：

- [ ] 一级视图默认主结构只能是 `单栏`
- [ ] 详情只能通过 `展开 / 折叠 / drill-in / 临时替换 / 局部展开` 进入
- [ ] 默认不允许 `双栏并排`
- [ ] 默认不允许 `三栏并排`

特别写死：

- [ ] `设置` 禁止默认左导航 + 右内容双栏
- [ ] `资料` 禁止默认列表 + 沙箱 + 详情三栏
- [ ] `计划` 禁止默认多组治理板块矩阵式并排

### 4.3 首屏只能有一个主问题

每个一级视图的首屏必须只回答一个主问题：

- `对话`：现在这轮最该回答什么 / 做什么
- `计划`：当前正式主线是什么
- `资料`：现在最相关的资料或最该处理的资料是什么
- `训练`：现在最该练什么
- `设置`：现在卡没卡住，先配什么

明确禁止：

- [ ] 首屏同时平铺多个主任务
- [ ] 首屏先讲系统结构
- [ ] 首屏先堆统计
- [ ] 首屏先堆说明书

### 4.4 顶部壳层必须极轻

必须满足：

- [ ] 一级视图切换条必须紧凑、稳定、不碰撞
- [ ] 顶部状态必须短、真、低干扰
- [ ] 历史/恢复信息默认必须是紧凑摘要，而不是大列表
- [ ] 任何非关键辅助条默认都应可折叠或延后出现
- [ ] 吸收参考图的克制 chrome：顶部只保留当前视图识别、极少量高价值动作和必要状态，不得为了“像产品”叠加第二层工具栏

### 4.5 输入区必须像侧边栏工具，不像网页写作页

对话输入区必须满足：

- [ ] 默认高度按 `3-5 行` 设计
- [ ] 用户可主动扩展，但不能默认巨高
- [ ] 发送动作始终靠近输入
- [ ] 上下文控制必须轻量，不得挤占主输入空间
- [ ] 不能因为输入框过高而压缩消息区首屏

### 4.6 文案必须先短后深

- [ ] 标题短
- [ ] 状态短
- [ ] 首屏解释短
- [ ] 长解释必须折叠到次层
- [ ] 长说明必须在用户需要时再出现

### 4.7 卡片只能在真的需要时使用

卡片不是默认布局单位。

必须满足：

- [ ] 卡片只用于真正需要边界感的块
- [ ] 同类信息优先合并成清晰列表，而不是拆成很多卡
- [ ] 默认不能一屏堆很多同权大卡片
- [ ] 卡片内必须有清晰动作或明确结论，不能只是装饰容器
- [ ] 参考图里的“安静面板感”只能用于帮助聚焦，不能把所有内容都包进圆角大盒子里

训练页是例外，但例外不是“多堆卡片”。

训练页的卡片必须是 `当前唯一训练对象`：

- [ ] 当前只显示一张实战卡或一张闪记卡
- [ ] 卡片是交互对象，不是装饰容器
- [ ] 卡片必须有作答、完成、跳过、切换、回对话或回实战动作
- [ ] 卡片之外的信息必须服务当前卡片，不能喧宾夺主

### 4.8 芯片只能承担短状态，不能承担主要解释

- [ ] 芯片只适合短状态、短标签、短过滤项
- [ ] 芯片不能承载长句子
- [ ] 芯片不能替代正文说明
- [ ] 芯片数量不能主导一个视图的视觉节奏

### 4.9 滚动行为必须符合窄侧边栏逻辑

- [ ] 主滚动轴必须清晰
- [ ] 不能出现多个同级大滚动区相互争抢
- [ ] 首屏核心信息不能被固定壳层挤出
- [ ] 长历史、长资料、长治理列表必须分页或渐进展开

### 4.10 状态必须诚实、可恢复、可继续

空状态、等待状态、异常状态都必须：

- [ ] 说明当前处境
- [ ] 说明为什么这样
- [ ] 说明现在能做什么
- [ ] 说明系统正在做什么
- [ ] 说明如何回到正常路径

明确禁止：

- [ ] 黑屏
- [ ] 假装正常
- [ ] 只给内部术语
- [ ] 只报错不指导下一步

### 4.11 不允许在侧边栏里再套“局部网站”

任何一级视图如果出现以下特征，直接判为设计错误：

- [ ] 视图内部再有完整二级导航系统
- [ ] 视图内部再有网页式左右分栏主结构
- [ ] 视图内部再有后台式信息管理台
- [ ] 视图内部再有宽屏仪表板

### 4.12 卡片训练交互硬约束

实战卡片与闪记卡片必须共享同一套低理解成本交互原则：

- [ ] 当前卡片必须有清晰题面
- [ ] 当前卡片必须有来源说明
- [ ] 当前卡片必须有为什么现在出现
- [ ] 当前卡片必须有一个主动作
- [ ] 当前卡片必须有完成后的去向
- [ ] 当前卡片必须能明确标记 `会 / 模糊 / 不会` 或 `完成 / 卡住 / 跳过`
- [ ] 当前卡片必须能把结果写回复盘、复习队列、依赖掌握或计划证据

卡片交互必须像学习产品，而不是像管理系统：

- [ ] 先看题
- [ ] 再作答或动手
- [ ] 再得到反馈
- [ ] 再决定下一张 / 回实战 / 回对话 / 进入复盘

禁止：

- [ ] 一屏同时展示很多张训练卡
- [ ] 先展示治理历史再展示题
- [ ] 卡片只是任务标题，没有题目结构
- [ ] 卡片没有来源，没有产生原因
- [ ] 卡片完成后不知道回流到哪里

### 4.13 单卡训练体验必须像学习产品，不像后台任务系统

训练卡片的体验参考对象是 `不背单词 / 百词斩` 这类低理解成本学习产品，而不是项目管理系统。

用户打开训练页时，必须立即知道：

- 现在只要看哪一张卡
- 这张卡属于实战还是闪记
- 为什么现在练这张卡
- 自己需要输入、选择、排序、判断还是亲手实现
- 卡住时点哪里
- 做完后结果去哪里

实战卡片的视觉节奏必须是：

- [ ] 顶部短标签：实战、来源、难度、预计耗时
- [ ] 主题面：一句目标 + 具体任务
- [ ] 行动区：建议用户自己打开/新建文件、自己实现、自己验证
- [ ] API 提示区：默认折叠或短提示，用户需要时展开
- [ ] 自检区：完成后先自测
- [ ] 回流区：带回对话、进入复盘、生成闪记、加入计划证据

闪记卡片的视觉节奏必须是：

- [ ] 顶部短标签：闪记、知识类型、来源、掌握度
- [ ] 主问题：尽量一屏可读
- [ ] 作答区：打字、选择、排序、填空或判断
- [ ] 提示区：逐级展开
- [ ] 反馈区：答后出现，解释错因或迁移点
- [ ] 复习区：会、模糊、不会，决定下一次出现

必须补充参考图转译规则：

- [ ] 训练页要吸收 `图 3` 的沉浸和单卡专注，但 Trainer 的卡片正文必须比背词产品更工程化、更可执行。
- [ ] 训练页允许克制的深色沉浸主题，但不能因为视觉主题牺牲代码训练题的可读性、状态清晰度和按钮可辨性。
- [ ] 主动作区必须像学习产品一样稳定在当前卡片上下文中，而不是漂浮出第二套无关导航。

训练页不得把以下内容放在当前卡片之前：

- [ ] 训练资产总览
- [ ] 历史完成列表
- [ ] 恢复路线长说明
- [ ] 复习队列全量列表
- [ ] 依赖掌握全图
- [ ] 计划治理摘要大面板

## 5. 五个一级视图的强约束

### 5.1 `对话`

用户来这里是为了：

- 问
- 被教
- 被带
- 被检查自己到底会没有
- 被压缩到下一步
- 基于当前项目继续推进
- 看到教练正在替自己做什么准备

首屏必须优先看到：

- 当前最重要回复
- 当前最小下一步
- 当前验证方式
- 当前上下文摘要
- 当前教练动作 / 当前依据状态

必须满足：

- [ ] 消息区永远是主角
- [ ] 用户发送的是消息，Trainer 回复也首先是消息；任何动作过程、状态提示、资料去向、训练去向都必须附着在消息内部轻量呈现
- [ ] 输入区固定在底部，但默认紧凑
- [ ] 历史恢复默认是轻量摘要，不是长期大列表
- [ ] 空状态必须直接引导用户开始当前项目相关的第一轮
- [ ] 回复必须像“教练在身边”，不是像“网页里的一堆模块”
- [ ] 回复必须同时兼顾“解决当前问题”和“教会用户下次也会”，表达要像人类教师，深入浅出、可长期相处
- [ ] 对话只承载纯对话，不承载计划页、资料页、训练页的完整工作台
- [ ] 对话可以触发生成实战卡片、闪记卡片、资料检索或计划证据，但不能把这些工作台塞进消息流
- [ ] 对话必须能给“计划候选 / 训练候选 / 资料导入 / 项目理解”的轻量、人性化反馈，但不强迫用户立刻跳走
- [ ] 对话必须能给“教练正在做什么”的轻量可见反馈，例如 `查资料中 / 绑定项目中 / 对齐计划阶段 / 生成卡片候选 / 评估刚才结果`
- [ ] 对话允许教练即时追问、即时抽查、即时小测、即时设计卡片或调用已有卡片，但必须保持消息形态，不展开成训练工作台
- [ ] 如果教练在对话中调用了现有卡片或实时设计了一张卡，必须说明 `为什么现在用它`、`继续在对话里完成还是去训练页沉浸完成`
- [ ] 对话必须同时支持“教练主导”和“教练配合”两种推进方式：用户模糊或卡住时更主动，用户清晰推进时更配合
- [ ] 对话中的计划反馈必须明确说明“这是候选，不会自动改正式计划”
- [ ] 对话中的训练反馈必须明确说明“为什么是这张卡、建议去训练页还是继续聊”
- [ ] 对话必须支持最基础的资料输入：上传文件、上传文件夹、提供链接或引用当前工作区
- [ ] 对话收到项目文件夹或工程材料后，必须先给项目类型判断、建议先看哪里和当前不确定点
- [ ] 对话中出现的卡点、目标、误解、API 追问必须能沉淀为训练卡片候选
- [ ] 对话中明确进入计划回合时，才允许进入计划修改流程
- [ ] 对话视觉必须主要吸收 `图 1 / 图 2`：深色克制、消息流主导、底部托盘式输入，但不能复制外部产品的信息架构和品牌语义

#### 5.1.1 `对话` 必须是教练超级入口，不能是孤立聊天框

`对话` 虽然必须保持纯对话体验，但它在系统设计上不能只是一个“回答问题的地方”。
它必须是 `资料 / 计划 / 训练` 三条后台工作流的统一调度前台。
前台看起来应该像一个会教学、会追问、会查证、会带练的人类教练；
后台则持续调度资料、计划和训练闭环。

必须成立：

- [ ] 用户看到的始终是纯对话，不是混合工作台。
- [ ] 对话是用户感知 Trainer 的主窗口，资料/计划/训练的动作都应该先被教练解释成“为什么现在这样做”。
- [ ] Agent 背后必须始终检查当前话语是否触发 `资料依据 / 项目理解 / 计划治理 / 训练编排`。
- [ ] 即使用户只是在聊天，Trainer 也必须判断这轮是否值得沉淀为轻量候选、资料需求、计划证据或训练机会。
- [ ] 任何后台工作流结论都必须回到对话中形成一句人能理解的反馈，而不是静默落库。
- [ ] 任何后台工作流除了落库，还必须形成 `教练动作可见性`，让用户知道 Trainer 正在查什么、整理什么、判断什么、准备什么。
- [ ] 对话要负责“压缩下一步”，而不是把用户扔给另一个页面自己理解发生了什么。
- [ ] 对话里允许 `即时解释 -> 追问 -> 小测 -> 调卡 -> 指向训练` 的连续教学节奏，但每轮只能保留一个主推进方向。

对话背后的统一工作流必须固定为：

1. `识别当前场景`
2. `绑定当前项目上下文`
3. `检查资料是否足够`
4. `检查当前计划阶段是否相关`
5. `判断现在更适合继续解释、生成闪记候选、生成实战候选、导入资料还是进入计划治理`
6. `把判断结果回写为轻量候选、即时教学动作、教练动作可见状态或说明`

用户可见输出必须克制：

- [ ] `主回复`：先回答用户当前问题
- [ ] `教练动作`：用一句人话说明 Trainer 刚在查什么、整理什么、判断什么
- [ ] `即时教学动作`：必要时只允许一个追问、小测、卡片调用或关键确认题
- [ ] `下一步`：只给一个主下一步
- [ ] `轻提示`：最多 0-2 个，例如“已形成训练候选”“这会进入计划候选”“这份资料已入库待拆解”
- [ ] `边界说明`：明确哪些内容不会自动发生，例如“不自动改正式计划”“不自动开始训练”“不自动改项目代码”

明确禁止：

- [ ] 用户一发消息就同时冒出计划大面板、资料大面板和训练大面板
- [ ] 候选对象已经生成，但对话里没有任何解释
- [ ] 对话把后台处理日志、完整文件树、完整证据 diff 全部直接塞给用户
- [ ] 为了体现能力强而让一次对话出现三个以上主方向
- [ ] 为了显得“像训练”就在对话里塞进整套卡片墙或完整训练工作台
- [ ] 教练后台已经做了资料整理、计划对齐或卡片编排，但用户完全看不见发生了什么

明确禁止：

- [ ] 先看到巨大的系统说明
- [ ] 先看到巨大的历史面板
- [ ] 先看到巨大的输入框
- [ ] 对话区像网页社区帖子页
- [ ] 对话区常驻训练卡片列表
- [ ] 对话区常驻资料管理面板
- [ ] 对话区常驻计划编辑器
- [ ] 对话里静默落库计划候选、训练候选或资料处理结果却不给用户反馈
- [ ] 对话里直接塞进完整文件树、资料后台或计划治理表

### 5.2 `计划`

用户来这里是为了：

- 看清总目标
- 看清当前主线
- 看清当前项目子计划
- 看清证据与历史
- 做显式计划动作

首屏必须优先看到：

- 当前总计划目标
- 当前项目子计划与总计划关系
- 当前正式步骤
- 为什么是现在这一步
- 如何验证

必须满足：

- [ ] `计划` 是纯内容视图，没有普通聊天输入
- [ ] `当前正式主线` 必须压过所有历史与治理信息
- [ ] `总计划 / 子计划 / 待吸收证据 / 历史` 必须有明确层级
- [ ] 历史与治理能力必须渐进展开，不能首屏全摊
- [ ] 显式计划动作必须清楚可见，但不能喧宾夺主
- [ ] 计划阶段必须能产生训练目标、实战卡片候选和闪记卡片候选
- [ ] 训练卡片完成结果必须先作为证据进入计划，不得自动改正式计划
- [ ] 只有显式采纳证据或用户明确要求修改计划，训练结果才可改变正式计划
- [ ] 计划页必须能说明某张训练卡为什么服务当前阶段或总计划目标

明确禁止：

- [ ] 计划页像仪表板
- [ ] 计划页像第二个聊天页
- [ ] 计划页首屏被大量治理卡片占满
- [ ] 浏览历史就能误改计划
- [ ] 计划页直接变成训练题列表
- [ ] 闪记答题结果直接改总计划

### 5.3 `资料`

用户来这里是为了：

- 导入资料
- 查资料
- 整理资料
- 让 Trainer 主动抓取和下载有用资料
- 管理跨项目统一资料沙箱
- 把资料沉淀成可复用教学资产

首屏必须优先看到：

- 搜索框
- 当前最相关知识条目
- 资料来源与可用状态
- 最轻量导入入口：`文件 / 文件夹 / 链接`
- 当前资料库作用域：全局资料库 / 当前项目绑定 / 待处理队列

必须满足：

- [ ] 默认是单栏知识库，不是资料管理后台
- [ ] 搜索必须比导入、沙箱、整理更靠前
- [ ] 资料列表必须像知识库条目：标题、摘要、标签、来源、可信/新鲜状态
- [ ] 搜索、筛选、导入必须紧凑
- [ ] 详情必须通过 drill-in 或展开进入
- [ ] 沙箱必须作为次层能力进入
- [ ] 资料库必须是跨项目统一知识库，当前项目资料只是过滤与绑定视图
- [ ] 用户上传 HTML、PDF、Markdown、代码文档、API 文档、README、论文、笔记、链接或文件夹后，必须进入统一解析与索引流程
- [ ] Trainer 可以在资料沙箱内抓取网页、下载资料、整理文件、生成派生笔记、更新索引、归档过期资料和运行受控 skill
- [ ] 沙箱写操作必须只发生在资料沙箱根目录内，并有操作日志、来源链、影响范围和回滚路径
- [ ] 沙箱不得越权修改用户工程空间，不得把资料沙箱操作伪装成用户项目实现
- [ ] 不允许默认并排展示多个重面板
- [ ] 文件夹型资料必须支持基础内容查看：树状锚点、文件级摘要、关键入口和高风险目录提示
- [ ] 资料条目必须能转成计划证据、实战卡片提示、闪记卡片或依赖 API 知识点
- [ ] 资料必须能说明“这条资料服务哪个计划阶段、哪张训练卡、哪个 API / 理论点”
- [ ] 资料视觉必须主要吸收 `图 4 / 图 5`：搜索优先、列表/分组/文件夹浏览清楚、详情后进，但不能退化成云盘或手机文件管理器

资料知识库条目必须有稳定信息结构：

- [ ] `title`：用户能一眼知道是什么
- [ ] `summary`：一句话说明能解决什么问题
- [ ] `source`：来源、路径、URL、导入时间或用户笔记来源
- [ ] `tags`：技术栈、依赖库、API、算法、数学、项目、计划阶段
- [ ] `trust_state`：可信、待验证、过期风险、用户自写、外部引用
- [ ] `freshness`：是否可能过期，是否需要重新查证
- [ ] `linked_plan`：服务哪个总计划或项目子计划
- [ ] `linked_cards`：已产生或可产生哪些实战卡 / 闪记卡
- [ ] `knowledge_atoms`：可拆成卡片的最小知识点
- [ ] `sandbox_path`：资料沙箱内的受控路径或派生文件路径
- [ ] `operation_log`：导入、下载、解析、改写、归档、skill 处理和回滚记录
- [ ] `project_links`：绑定到哪些项目、子计划、训练线和证据对象
- [ ] `derived_artifacts`：摘要、API 表、术语表、卡片候选、索引、网页快照或代码文档切片

资料到训练的转换必须清楚：

- [ ] API 文档优先转成 API 方法卡、参数卡、返回值卡、误用辨析卡和最小实战卡
- [ ] 算法材料优先转成算法理论卡、复杂度卡、步骤排序卡和工程应用实战卡
- [ ] 数学材料优先转成公式卡、条件判断卡、变量含义卡和场景选择卡
- [ ] 工程案例优先转成场景判断卡、架构取舍卡、验证方式卡和迁移实战卡
- [ ] 用户笔记优先转成自述薄弱点卡、复盘卡和复习队列项
- [ ] 资料只能生成候选卡片，候选是否进入训练必须由卡片路由器判断

明确禁止：

- [ ] 默认三栏
- [ ] 默认把列表、详情、沙箱同时并排
- [ ] 资料页像 CMS 后台
- [ ] 资料页像文件管理网站
- [ ] 资料页先展示上传大面板而不是知识库搜索
- [ ] 资料页把整理表单作为首屏主角
- [ ] 资料页把“跨项目统一资料库”做成每个项目一份孤立文件夹
- [ ] Trainer 在资料沙箱无审计、无来源、无回滚地下载或改写内容
- [ ] 资料沙箱 skill 越权读取或写入用户工程代码

### 5.4 `训练`

用户来这里是为了：

- 现在就开始练
- 刷一张实战卡片
- 刷一张闪记卡片
- 回答理论题或场景题
- 做最小实现题
- 复盘
- 回收复习项

首屏必须优先看到：

- 当前唯一卡片
- 为什么现在出现这张卡
- 用户要输入什么、选择什么或自己实现什么
- 完成后如何验证或反馈

必须满足：

- [ ] `练习 / 闪记 / 复盘 / 复习队列 / 理论题` 都属于 `训练`
- [ ] 训练首屏只能有一个主训练对象，且默认是一张卡片
- [ ] 训练页是计划页的具体实施脚手架，不是独立刷题应用
- [ ] 训练页必须分成 `实战卡片` 与 `闪记卡片` 两个清楚入口
- [ ] 一次仅显示一张卡片
- [ ] 训练必须强调“用户自己实现”
- [ ] 当前卡住时必须能明确给出恢复路径
- [ ] 实践暴露的薄弱点必须反向生成闪记与理论题
- [ ] 实战卡片必须包含 Trainer 编写的代码训练题、建议文件/目录、API 提示、交付物、标准答案形态、验证方式、评分标准、回流动作
- [ ] 实战卡片可以建议用户自己新建文件，但不能替用户新建或修改
- [ ] 闪记卡片必须覆盖完整理论知识体系：算法理论、数学理论、公式、工程概念、API 方法、参数、返回值、误用、验证和场景判断
- [ ] 闪记卡片必须有 Trainer 编写的问题、标准答案、验证方式、提示、作答区和反馈
- [ ] 卡片必须显示或可展开显示来源链：对话 / 计划 / 资料 / 实战反馈 / 复习队列 / 依赖掌握
- [ ] 训练视觉必须主要吸收 `图 3`：单卡沉浸、操作低干扰、反馈后置，但必须保留代码训练题结构、coach-only 边界和回流动作

实战卡片首屏结构必须固定为：

- [ ] `为什么现在练`：一句话
- [ ] `题目`：具体到用户要做什么
- [ ] `你自己要打开/新建`：建议文件、目录或模块
- [ ] `API 提示`：方法、参数、返回值、边界、误用
- [ ] `交付物`：用户需要亲手完成什么
- [ ] `先自检`：用户完成后先怎么验证
- [ ] `正确答案形态`：不暴露完整成品代码，但说明合格实现必须满足什么结构或行为
- [ ] `评分标准`：Trainer 后续如何判断用户答案是否通过
- [ ] `带回对话`：把实现说明、错误、测试输出或截图带回给 Trainer

实战卡片的提示层级必须可控：

- [ ] 第 1 层只给方向和约束
- [ ] 第 2 层给 API / 方法提示
- [ ] 第 3 层给伪代码或局部示例
- [ ] 第 4 层给排错线索
- [ ] 不得默认直接给完整最终实现

闪记卡片首屏结构必须固定为：

- [ ] `问题`：一句清楚问题
- [ ] `知识点覆盖`：这题覆盖理论体系中的哪个节点
- [ ] `场景`：必要时给极短上下文
- [ ] `作答区`：打字、选择、排序、填空或判断
- [ ] `提示`：用户主动展开
- [ ] `标准答案 / 评分规则`：Trainer 设计，答后可见
- [ ] `反馈`：回答后出现
- [ ] `掌握标记`：会、模糊、不会
- [ ] `下一步`：下一张、转实战、回对话、加入复习

闪记卡片不得只覆盖 API 背诵：

- [ ] 算法题必须能问复杂度、边界、关键步骤、正确性直觉或适用场景
- [ ] 数学题必须能问定义、公式变量、适用条件、推导直觉或工程意义
- [ ] 公式题必须能问“什么时候能用 / 什么时候不能用”
- [ ] API 题必须能问方法、参数、返回值、副作用、异常、异步行为和误用
- [ ] 工程题必须能问场景选择、验证方式、迁移判断和风险边界

训练页的认知负担必须被压到最低：

- [ ] 不要求用户先理解“训练系统有哪些模块”
- [ ] 不在首屏展示训练历史大列表
- [ ] 不在首屏展示恢复路线大块内容
- [ ] 不在首屏展示依赖掌握全图
- [ ] 只在当前卡需要时展示来源、提示、复盘或跳转

明确禁止：

- [ ] 训练页像很多功能堆起来的大页
- [ ] 训练页只有文本说明，没有工作台感
- [ ] 训练页把多个训练对象同时平铺
- [ ] 训练页默认给用户成品代码
- [ ] 训练页默认展开恢复路线、历史或治理列表
- [ ] 实战卡片只有任务标题，没有具体题面
- [ ] 闪记卡片只有 API 背诵，没有理论和场景题
- [ ] 卡片来源不明，像随机题库

### 5.5 `设置`

用户来这里是为了：

- 确认 Trainer 能不能正常用
- 配 provider / model / API key
- 处理 sidecar / runtime / 清理问题
- 只在必要时进入高级配置

首屏必须优先看到：

- 当前可用 / 不可用状态
- 卡住原因
- 最短配置路径

必须满足：

- [ ] 设置必须是窄栏友好的单流设置页
- [ ] 默认先展示最少必需项
- [ ] 高级项必须折叠到后面
- [ ] 危险动作必须放在底部且明确隔离
- [ ] 不能要求用户先理解内部模型再开始配置

明确禁止：

- [ ] 左导航 + 右内容的网页设置页
- [ ] 表单迷宫
- [ ] 一上来展示所有高级选项
- [ ] 看起来像开发者控制台

## 6. 从四个角色看，什么才算完成

### 6.1 站在项目经理角度

必须满足：

- [ ] 视图边界稳定
- [ ] 主路径清楚
- [ ] 当前版本先修形态，再谈功能堆叠
- [ ] 验收口径明确到“是否像 VS Code 扩展，而不是像网页”
- [ ] 图 1-4 暴露的问题都已经被写进禁止项并逐项验收
- [ ] 训练卡片有明确状态流：待做、作答中、已提交、需复习、转实战、已回流
- [ ] 每张卡片有明确来源和去向，可追踪到计划、对话、资料或实战反馈
- [ ] 训练成果不是“完成数量”，而是能沉淀为能力证据

### 6.2 站在 AI 开发者角度

必须满足：

- [ ] 场景路由稳定
- [ ] 项目 grounding 稳定
- [ ] teaching decision 稳定
- [ ] 计划修改闸门稳定
- [ ] 证据沉淀与正式计划分层稳定
- [ ] 训练回流、闪记回流、依赖掌握回流稳定
- [ ] UI 不会误导用户理解系统状态
- [ ] 卡片生成必须有路由器：来自计划、对话、资料、实战反馈、复习队列、依赖掌握图
- [ ] 卡片必须有 typed schema：实战卡、闪记卡、理论题、API 卡、公式卡、算法卡、误用辨析卡
- [ ] 模型输出必须说明 `why_now`、`source_chain`、`target_skill`、`expected_evidence`
- [ ] 不能让模型随机出题；所有题都必须服务当前学习目标或恢复目标

### 6.3 站在全栈工程师角度

必须满足：

- [ ] extension / webview / server / shared 边界清楚
- [ ] 视图结构先适配窄栏，再做宽栏增强
- [ ] 不能继续往 webview 中堆网页式多栏布局
- [ ] 任何重功能都不能拖慢侧边栏主交互
- [ ] sidecar、provider、缓存、恢复路径在三端都可解释
- [ ] shared 模型必须表达卡片类型、来源链、计划关联、资料关联、依赖关联、状态和回写结果
- [ ] server 必须负责卡片生成、评分、回写、复习调度和计划证据沉淀
- [ ] webview 只负责卡片呈现与用户交互，不把生成逻辑写死在前端
- [ ] extension 只负责上下文与 VS Code 行为边界，不替用户执行项目改动

### 6.4 站在用户角度

必须满足：

- [ ] 第一次打开就知道五个一级视图各做什么
- [ ] 任何时刻都知道现在该点哪里
- [ ] 不需要先理解系统架构才能开始用
- [ ] 计划能随时看，但不会乱改
- [ ] 训练能立刻做，而且知道为什么现在做
- [ ] 资料能立刻用，不像黑洞
- [ ] 长期使用后真觉得这是“教练”，不是“聊天壳子”
- [ ] 训练像刷卡一样轻：一次只看一题，不被系统结构干扰
- [ ] 实战卡知道该自己新建/打开什么文件、做什么、怎么验证
- [ ] 闪记卡不只是背 API，还能练算法、数学、公式、工程判断和真实场景
- [ ] 用户能清楚知道一张卡为什么来自刚才那段对话、当前计划或某份资料

## 7. 产品闭环必须同时成立

本章只定义必须同时成立的产品闭环。设计闭环总模型集中在 `13.15`，深层 Agent 决策协议集中在 `13.16`，数据契约集中在 `9.5`，场景级验收集中在 `11.10`，避免同一规则多处散落。

### 7.1 计划闭环

- [ ] 总计划、项目子计划、项目证据队列同时存在。
- [ ] 对话、资料、训练只能先产生证据或候选，不得直接改正式计划。
- [ ] 正式计划只由明确计划回合、计划页显式动作或用户明确要求改变。
- [ ] 项目子计划证据必须能回流总计划，但总计划评估综合能力，不只统计任务数。

### 7.2 训练闭环

- [ ] 训练题来自计划阶段、对话卡点、资料知识、依赖薄弱点、复盘或复习队列。
- [ ] 训练页默认一次只显示一张闪记卡或实战卡。
- [ ] 用户自己作答、实现、验证并带回结果。
- [ ] Trainer 只负责题面、提示、验证标准、反馈、纠偏和下一步。
- [ ] 训练结果回流到复盘、复习队列、闪记、资料标注和计划证据。

### 7.3 闪记 / 理论题闭环

- [ ] 闪记属于训练，不是新一级视图。
- [ ] 闪记覆盖算法、数学、公式、工程概念、API、参数、返回值、误用、验证和场景判断。
- [ ] 每张卡只训练一个最小知识点，并有题型、标准答案或评分规则。
- [ ] `会 / 模糊 / 不会` 必须影响复习调度。
- [ ] 多次错误必须拆成更小卡或转对话解释；多次正确必须转迁移题或实战卡。

### 7.4 资料闭环

- [ ] 资料默认是知识库：搜索、条目、摘要、标签、来源、可信度、新鲜度。
- [ ] 资料必须拆成知识原子，并保留来源链。
- [ ] 知识原子必须能生成闪记候选、实战候选或计划证据候选。
- [ ] 资料被训练使用后必须留下使用痕迹。
- [ ] 资料错误、过期或冲突时必须标记待复查，并阻断相关训练卡。

### 7.5 理解到实践迁移闭环

- [ ] `理解` 由解释、资料、闪记文本题证明。
- [ ] `记住` 由延迟复习、参数/返回值/公式/误用卡证明。
- [ ] `做出` 由实战卡、最小场景、用户带回验证证明。
- [ ] `迁移` 由不同项目、不同上下文或变形场景证明。
- [ ] 总计划必须综合四层证据，不能用卡片数量或任务完成数替代掌握。

### 7.6 Coach-only 闭环

- [ ] Trainer 只带练，不代做。
- [ ] 实战卡可以建议用户自己新建或打开文件，但不能替用户操作。
- [ ] API 提示可以讲方法、参数、返回值、边界和误用，但不能给完整成品补丁。
- [ ] 任何训练、资料、计划动作都不得绕过用户自实现。

### 7.7 卡片产生机制闭环

- [ ] 卡片可以来自对话、计划、资料、训练反馈、依赖掌握或复习队列。
- [ ] 每张卡必须绑定 `target_skill`、`why_now`、`source_chain` 和 `expected_evidence`。
- [ ] 卡片状态必须覆盖 `candidate -> active -> answered/implemented -> reviewed -> fed_back -> archived`。
- [ ] 不能生成没有来源链、没有去向、无法验证的随机题。

### 7.8 实战卡片闭环

- [ ] 实战卡必须是当前用户可执行的最小工程场景。
- [ ] 实战卡必须给出题面、建议文件/目录、API 提示、交付物、自检和带回要求。
- [ ] 没有真实项目落点时，必须指导用户构建空项目最小场景。
- [ ] 题太大时拆小，缺 API 基础时先闪记，缺资料时先检索，连续卡住时回对话解释。
- [ ] 完成证据进入计划证据队列，不自动修改正式计划。

### 7.9 闪记卡片闭环

- [ ] 闪记入口可以来自实战错误、对话误解、资料知识、依赖薄弱点、计划阶段或到期复习。
- [ ] 答案反馈必须解释错因、迁移意义或实战关联。
- [ ] 与实战强相关的知识必须回到实战卡验证。
- [ ] 与计划强相关的知识只能生成计划证据，不自动改正式计划。

### 7.10 对话 / 计划 / 资料 / 训练联动闭环

- [ ] `对话` 必须是四域闭环的统一前台教练调度面，而不是与其他三域并列但互不理解的聊天区。
- [ ] 对话首先要回答并教会用户当前问题，其次才是调度计划、资料和训练。
- [ ] 对话只承载纯对话、即时教学动作和轻量候选提示。
- [ ] 对话必须能让用户看见教练当前在查资料、对齐计划、编排训练或评估结果，但只以轻量人话状态呈现。
- [ ] 对话可以承载即时追问、小测、调卡和卡片解释，但沉浸式连续刷卡仍然只属于训练视图。
- [ ] 对话触发的计划候选、训练候选、资料导入和项目上下文判断必须有轻量反馈、明确去向和非自动化说明。
- [ ] 计划只承载目标、阶段、证据、候选变更和显式治理动作。
- [ ] 资料只承载知识库、来源、可信度、知识原子和训练/证据候选。
- [ ] 训练只承载单卡作答、实战、复盘、复习和结果回流。
- [ ] 设置只保障 provider、sidecar、权限、恢复和数据边界可用。
- [ ] 四域联动必须遵循 `对话理解并回答 -> 后台判断 -> 教练动作可见反馈 -> 资料/计划/训练写入候选 -> 用户继续对话或显式进入相应视图继续` 的顺序。
- [ ] 如果一轮对话最后既没有回答问题，也没有形成明确下一步、候选或资料需求，就说明联动闭环设计不合格。

### 7.11 资料知识库闭环

- [ ] 资料导入后必须变成可搜索、可引用、可拆解、可训练的条目。
- [ ] 资料库必须跨项目统一，项目资料视图只能是全局资料库的过滤和绑定。
- [ ] 用户上传 HTML、PDF、Markdown、代码文档、API 文档、论文、README、笔记、日志、链接或文件夹后，必须先落 metadata，再异步解析、索引和拆知识原子。
- [ ] Trainer 可以主动浏览网页、下载有用内容到资料沙箱，并写入来源、时间、可信度、新鲜度和处理日志。
- [ ] Trainer 可以在资料沙箱内整理、重命名、归档、改写派生资料、维护索引和运行受控 skill。
- [ ] 资料沙箱写操作必须可审计、可回滚、可追踪影响范围。
- [ ] 资料沙箱权限必须和用户工程空间隔离，任何 skill 或命令都不得越权写项目代码。
- [ ] 文件夹资料必须能产出树状锚点、文件级摘要、项目理解入口和训练候选，而不是只落一个路径。
- [ ] 工程案例必须能生成实战卡候选。
- [ ] 资料可信度、新鲜度和来源必须进入卡片来源链。
- [ ] 资料条目被多个项目使用时，必须复用同一全局资料正文，只新增项目绑定和使用证据。
- [ ] 资料更新、过期、冲突或被 skill 改写派生内容时，必须能反向标记受影响卡片、计划证据和依赖掌握节点。

### 7.12 依赖库 / API 掌握闭环

- [ ] 每个依赖库必须能形成能力图：概念、核心 API、组合模式、参数、返回值、错误、验证、迁移。
- [ ] 每个核心 API 必须能形成闪记卡和最小实战场景。
- [ ] 真实项目没有落点时，Trainer 必须指导用户构建空项目最小场景。
- [ ] 用户在实战中误用 API，必须反向生成误用、参数或返回值卡。
- [ ] 用户能跨项目复用该 API 时，才能提高迁移掌握度。

### 7.13 定制化教练 Agent 闭环

- [ ] Agent 必须持续维护 `trainer_identity / learner_model / master_plan / project_subplans / knowledge_base / training_deck / evidence_graph / dependency_mastery_map`。
- [ ] 主循环固定为 `感知 -> 诊断 -> 选择教学动作 -> 生成学习对象 -> 用户执行 -> 评估 -> 回流 -> 下一轮`。
- [ ] 每轮必须把当前话语放进项目子计划、总计划、最近训练、资料知识、依赖掌握和长期目标中判断。
- [ ] 详细决策协议、触发规则、清晰/模糊需求处理和文件夹路由统一见 `13.16`。

### 7.14 跨系统统一闭环

- [ ] Windows / macOS / Linux 必须共享同一套资料沙箱语义：同一资料、同一 skill、同一卡片来源链在三端解释一致。
- [ ] 路径、编码、换行、大小写、symlink / junction、权限和 shell 差异必须被统一抽象吸收。
- [ ] 资料沙箱写操作、skill 运行、下载、解析、回滚、越权拦截必须有三端验证。
- [ ] 三端能力缺失时必须可降级，例如只索引 metadata、暂停 PDF 深解析或禁用某 skill，而不是破坏主流程。
- [ ] 跨系统差异必须进入诊断日志和用户可理解恢复提示。

### 7.15 中文 / English 双语闭环

- [ ] 用户语言偏好必须影响 UI、对话、资料摘要、计划解释、训练题面、反馈和错误恢复。
- [ ] 资料原文语言、展示语言、术语映射和翻译状态必须进入资料模型。
- [ ] 中文、English、mixed 资料必须进入同一个知识图谱，不能拆成重复知识点。
- [ ] 卡片评分必须理解中英混合答案，不能因语言不同误判。
- [ ] 搜索必须支持中文、英文、API 名、代码符号、缩写和术语别名。
- [ ] 技术名词、代码标识符、路径、命令、API 名称必须按语义保留，不得机械翻译。

## 8. 六个质量目标必须同时成立

### 8.1 功能强大

不是功能数量多，而是：

- 主场景都能接住
- 真能从资料走到实现
- 真能从实现走到训练
- 真能从训练走到长期成长

### 8.2 低理解成本

不是功能少，而是：

- 新用户一眼能懂
- 老用户用得更快
- 默认首屏只有一个主任务
- 高级能力在需要时才出现

### 8.3 人性化交互

不是会说漂亮话，而是：

- 用户卡住时能收缩粒度
- 用户赶时间时能更直接
- 用户探索时能更解释
- 用户失败后能帮忙恢复节奏

### 8.4 真正好用

必须做到：

- 下一步清楚
- 验证方式清楚
- 状态诚实
- 风险动作边界清楚
- 不需要用户自己猜系统在干什么

### 8.5 高级设计

必须体现为：

- 工具感强
- 分层克制
- 密度高但不噪
- 与 VS Code 场景一致
- 长期看不廉价

### 8.6 长期 Trainer

必须做到：

- 跨会话连续
- 跨项目连续
- 总计划可治理
- 资料可沉淀
- 训练可复用
- 掌握度可长期评估

## 9. 工程与实现硬约束

### 9.1 责任边界

必须明确：

- `extension`：VS Code API、工作区上下文、命令与宿主桥接
- `webview`：侧边栏工作台呈现与交互状态
- `server`：规划、记忆、研究、评估、教学决策、资料处理
- `shared`：跨端契约、模型与设计令牌

### 9.2 性能约束

- [ ] 启动必须分层
- [ ] 对话热路径不能等重能力
- [ ] 所有重能力都必须可延迟、可取消、可降级
- [ ] 不能为了“功能强”把 VS Code 侧边栏拖卡
- [ ] 不能让任何一级视图默认加载成网页重页面

### 9.3 跨平台约束

- [ ] Windows / macOS / Linux 都必须可安装、可启动、可恢复
- [ ] sidecar 生命周期必须可控
- [ ] 路径、编码、shell、权限差异必须被显式吸收
- [ ] 资料沙箱路径必须通过 `sandbox_root + virtual_resource_path + platform_path` 三层模型处理
- [ ] 所有资料沙箱文件操作必须验证 resolved path 不逃逸 sandbox root
- [ ] Windows junction / symlink、macOS alias / symlink、Linux symlink 都必须纳入逃逸检测
- [ ] 文件名含中文、空格、emoji、保留字符、大小写差异时必须有稳定处理策略
- [ ] skill manifest 必须声明支持平台、命令模板、输入输出、权限和回滚策略
- [ ] shell 命令必须平台隔离：Windows 不套 POSIX 假设，macOS / Linux 不套 PowerShell 假设
- [ ] 网络下载、PDF/HTML/Markdown/代码文档解析必须在三端产出可比较 metadata

### 9.4 数据与治理约束

- [ ] `trainer_identity` 必须全局唯一
- [ ] `master_plan` 与 `project_subplan` 必须有清晰 schema
- [ ] `evidence_item` 必须先于正式计划吸收
- [ ] 删除、清理、重置都必须有明确范围说明
- [ ] 资料条目必须带 `language / source_language / display_language / translation_state`
- [ ] 中英双语术语映射必须可追踪，不能让同一知识点重复进入掌握度

### 9.5 卡片数据契约

`shared` 必须定义稳定卡片模型，不能让前端、后端、extension 各自猜字段。

基础字段必须包含：

- [ ] `id`
- [ ] `type`: `practice | flash`
- [ ] `status`: `candidate | active | answered | implemented | reviewed | fed_back | archived`
- [ ] `created_from`: `conversation | plan | resource | practice_feedback | dependency_mastery | review_due`
- [ ] `source_chain`
- [ ] `why_now`
- [ ] `target_skill`
- [ ] `difficulty`
- [ ] `plan_links`
- [ ] `project_links`
- [ ] `resource_links`
- [ ] `dependency_links`
- [ ] `expected_evidence`
- [ ] `feedback_targets`
- [ ] `created_at`
- [ ] `updated_at`

实战卡扩展字段必须包含：

- [ ] `scenario`
- [ ] `problem_statement`
- [ ] `suggested_workspace_action`
- [ ] `api_hints`
- [ ] `constraints`
- [ ] `deliverable`
- [ ] `self_check`
- [ ] `trainer_review_input`
- [ ] `stuck_recovery`
- [ ] `reflection_prompt`

闪记卡扩展字段必须包含：

- [ ] `knowledge_type`
- [ ] `question`
- [ ] `context`
- [ ] `answer_mode`
- [ ] `options`
- [ ] `expected_answer`
- [ ] `rubric`
- [ ] `hint_ladder`
- [ ] `feedback`
- [ ] `common_mistakes`
- [ ] `review_schedule`
- [ ] `mastery_delta`

### 9.6 服务端职责

`server` 必须承担教学决策与闭环，不得把核心逻辑塞到 webview。

- [ ] 负责 `card_generation_router`
- [ ] 负责候选卡去重、排序、难度评估
- [ ] 负责从资料中抽取知识原子
- [ ] 负责从实战反馈中生成闪记候选
- [ ] 负责从闪记结果中更新复习队列
- [ ] 负责从训练结果中沉淀计划证据
- [ ] 负责依赖库 / API 掌握图更新
- [ ] 负责跨项目总计划能力画像汇总
- [ ] 负责解释为什么生成、激活或延后某张卡
- [ ] 负责 `global_resource_library`、`resource_sandbox`、`project_resource_links`、`resource_operation_log`
- [ ] 负责网页抓取、资料下载、格式解析、知识原子抽取、索引更新、资料可信度和新鲜度评估
- [ ] 负责资料沙箱内受控写操作、派生资料生成、归档、回滚和影响范围计算
- [ ] 负责资料处理 skill 的 manifest 校验、隔离运行、权限限制、输出审计和风险标注
- [ ] 负责跨系统路径抽象、编码识别、换行归一、大小写冲突处理、symlink / junction 越权防护
- [ ] 负责双语资料处理、语言识别、术语映射、双语摘要、混合语言答案评估和搜索索引

服务端禁止：

- [ ] 默认替用户生成项目补丁
- [ ] 越权写用户工程空间或把资料沙箱产物写进项目代码
- [ ] 无来源、无日志、无回滚地修改资料沙箱内容
- [ ] 运行未通过安全检查或权限范围不清的资料 skill
- [ ] 只在某一个平台上实现资料沙箱关键能力却声称跨系统完成
- [ ] 把中文/英文资料拆成重复知识点导致掌握度重复计算
- [ ] 把普通对话结果直接写入正式计划
- [ ] 生成没有来源链的随机题
- [ ] 生成无法在侧边栏单卡理解的复杂题

### 9.7 Webview 职责

`webview` 只负责侧边栏呈现与交互，不负责核心教学决策。

- [ ] 训练页负责一次展示一张卡
- [ ] 训练页负责作答、完成、跳过、卡住、下一张等交互
- [ ] 训练页负责展示来源链摘要与可展开详情
- [ ] 训练页负责展示提示层级，但不绕过服务端策略
- [ ] 资料页负责知识库式检索与条目呈现
- [ ] 资料页负责展示全局/当前项目作用域、上传入口、网页抓取状态、沙箱操作日志和受控 skill 处理结果
- [ ] 资料页负责展示资料语言、原文/摘要切换、术语映射和翻译状态
- [ ] 全部视图负责按 `preferred_language` 呈现 UI 文案、训练题、反馈和恢复提示
- [ ] 计划页负责内容视图和显式计划动作
- [ ] 对话页负责纯对话和轻量联动提示
- [ ] 设置页负责运行状态和配置

Webview 禁止：

- [ ] 本地拼装随机训练题
- [ ] 在训练页平铺多张卡
- [ ] 把资料、计划、训练工作台塞入对话消息流
- [ ] 在计划页放普通聊天输入
- [ ] 在资料页默认三栏并排
- [ ] 在资料页把沙箱操作做成无审计的文件管理器
- [ ] 强行翻译 API 名、命令、路径、代码标识符
- [ ] 在窄栏里复制网页 dashboard

### 9.8 Extension 职责

`extension` 负责 VS Code 边界和宿主行为。

- [ ] 提供当前工作区、打开文件、选区、语言、项目路径等上下文
- [ ] 只把上下文交给 Trainer 做教学判断
- [ ] 可以帮助用户定位文件或打开用户选择的路径
- [ ] 不得自动创建、修改、删除用户项目文件
- [ ] 不得自动执行会改变项目状态的命令
- [ ] 对危险动作必须提示用户转到 VS Code 自己操作
- [ ] 必须把资料沙箱路径与用户工程路径隔离，所有资料沙箱写操作只能指向受控 sandbox root
- [ ] 必须拦截资料 skill 或 sidecar 请求越权写项目文件、读取 SecretStorage 或执行危险命令
- [ ] 必须把 VS Code 语言环境、用户语言偏好、工作区平台信息传给 server，但不得暴露敏感信息

### 9.9 验证与测试约束

任何实现声称完成本清单，至少必须覆盖：

- [ ] 280px、340px、420px 三档侧边栏视觉检查
- [ ] 对话页纯对话检查
- [ ] 计划页无普通聊天输入检查
- [ ] 资料页知识库单栏检查
- [ ] 训练页一次一张卡检查
- [ ] 实战卡 coach-only 检查
- [ ] 闪记卡多知识类型检查
- [ ] 卡片来源链检查
- [ ] 卡片结果回流检查
- [ ] 计划不被普通对话或普通训练自动修改检查
- [ ] 资料沙箱写操作隔离、审计、回滚和越权拦截检查
- [ ] 跨项目统一资料库与项目绑定检查
- [ ] 网页抓取 / 用户上传 / skill 处理进入资料库闭环检查
- [ ] Windows / macOS / Linux 三端资料沙箱、路径逃逸、解析、skill 隔离检查
- [ ] 中文 / English / mixed 资料、UI、卡片、答案评分和搜索检查
- [ ] 依赖库 / API 从资料到闪记再到实战的闭环检查

### 9.10 状态矩阵输出契约

每次推进实现后，必须按主清单输出状态矩阵。
状态只能是：

- `已实现`
- `半实现`
- `未实现`

状态矩阵至少必须包含：

- [ ] 清单编号
- [ ] 要求摘要
- [ ] 当前状态
- [ ] 证据文件或 UI 入口
- [ ] 已通过的测试或人工验收
- [ ] 半实现 / 未实现的剩余工作
- [ ] 风险或阻塞
- [ ] 下一步落地文件

判定规则：

- [ ] 只有 UI 文案，没有数据流，不能判 `已实现`
- [ ] 只有后端 schema，没有 UI 入口，不能判 `已实现`
- [ ] 只有 mock 数据，没有真实状态流，不能判 `已实现`
- [ ] 只有卡片列表，没有单卡训练体验，不能判 `已实现`
- [ ] 只有训练完成数，没有掌握度和回流，不能判 `已实现`
- [ ] 只有计划摘要，没有显式计划修改闸门，不能判 `已实现`
- [ ] 只有资料上传，没有知识库条目、来源链和卡片生成，不能判 `已实现`
- [ ] 只有 API 解释，没有闪记、实战和迁移，不能判 `已实现`

### 9.11 模型输出约束

任何由 AI 生成的计划、资料沉淀、训练卡片或评估，都必须避免“看起来很完整但不可执行”。

模型输出训练卡时必须包含：

- [ ] `why_now`
- [ ] `source_chain`
- [ ] `target_skill`
- [ ] `user_action`
- [ ] `expected_evidence`
- [ ] `feedback_target`
- [ ] `coach_only_boundary`

模型输出资料沉淀时必须包含：

- [ ] 来源
- [ ] 可信度
- [ ] 新鲜度
- [ ] 可拆知识点
- [ ] 可生成卡片类型
- [ ] 关联计划或项目场景

模型输出计划证据时必须包含：

- [ ] 证据来源
- [ ] 对应项目子计划
- [ ] 对应总计划能力
- [ ] 证据强度
- [ ] 是否需要用户显式采纳

明确禁止：

- [ ] 模型随机出题
- [ ] 模型默认生成最终代码答案
- [ ] 模型把训练结果直接写成正式计划变更
- [ ] 模型把资料摘要当成已经掌握
- [ ] 模型把一次答对当成长期掌握
- [ ] 模型用大段说明替代可执行卡片

### 9.12 跨系统实现契约

跨系统不是发布阶段才检查，而是资料沙箱、skill、sidecar、extension 的基础契约。

必须实现：

- [ ] `PlatformInfo`：记录 OS、架构、shell、路径分隔符、大小写策略、默认编码、权限状态。
- [ ] `SandboxPathResolver`：统一处理 sandbox root、虚拟路径、真实路径、路径规范化、逃逸检测。
- [ ] `SandboxOperation`：所有写操作统一建模为 create / update / rename / move / archive / delete_to_trash / restore / index / skill_run。
- [ ] `SandboxAuditLog`：记录平台、操作者、来源、输入输出、影响对象、回滚点、错误、耗时。
- [ ] `SkillRuntimePolicy`：声明平台支持、命令模板、允许网络、允许文件范围、环境变量白名单和超时。
- [ ] `ParserParityReport`：同一资料在不同系统解析结果的 metadata、hash、knowledge_atoms 差异报告。

实现禁止：

- [ ] 在 server 中硬编码 Windows 或 POSIX 路径假设。
- [ ] 在 webview 中拼接真实文件路径。
- [ ] 用字符串拼接执行资料沙箱危险命令。
- [ ] 只在当前开发机通过就标记跨系统完成。

### 9.13 双语实现契约

双语能力必须作为数据和交互契约实现，不能只靠模型临场翻译。

必须实现：

- [ ] `LanguagePreference`：用户级、会话级、项目级语言偏好，优先级清楚。
- [ ] `LocalizedCopy`：UI 文案、按钮、错误、恢复提示、空状态支持中文和 English。
- [ ] `BilingualResourceMetadata`：资料主语言、源语言、展示语言、摘要、术语表、翻译状态。
- [ ] `TermMap`：中文术语、英文术语、API 名、别名、缩写、代码符号的映射。
- [ ] `BilingualCardContent`：卡片题面、提示、反馈、rubric 支持按语言展示，并保留技术名词原文。
- [ ] `AnswerLanguageEvaluator`：评分时识别语义而不是只匹配语言表面。
- [ ] `CrossLingualSearchIndex`：中文、英文、mixed、代码符号和 API 名可互搜。

实现禁止：

- [ ] 把所有英文技术名词机械翻译成中文。
- [ ] 把中文和英文卡片当成两个互不相关的知识点。
- [ ] 只翻译导航，不翻译训练反馈和错误恢复。
- [ ] 因用户用另一种语言回答而误判为错。

## 11. 最终验收清单

### 11.1 VS Code 侧边栏形态验收

- [ ] 首屏一眼看上去像 VS Code 扩展工具，不像网页页面。
- [ ] 所有一级视图默认都是窄栏单栏主结构。
- [ ] 顶部壳层轻，不抢任务区。
- [ ] 图 5 的宽度感、密度感、工具感已成为统一基线。
- [ ] 本轮 5 张参考图的结构优点已被正确吸收，且不发生机械抄图。
- [ ] 参考图转译后的反模式已不再出现。

### 11.2 对话验收

- [ ] 消息区是绝对主角。
- [ ] 输入区默认紧凑。
- [ ] 当前回复、下一步、验证方式足够靠前。
- [ ] 不需要滚很多屏才开始真正对话。
- [ ] 对话中可以触发卡片候选、资料检索或计划证据，但不会嵌入完整训练/资料/计划工作台。
- [ ] 对话中出现的卡点、误解、API 追问能进入候选卡生成链。
- [ ] 对话普通问答不会修改正式计划。

### 11.3 计划验收

- [ ] 计划是内容视图，不是聊天框。
- [ ] 总计划、子计划、证据、历史层级明确。
- [ ] 当前正式步骤足够靠前。
- [ ] 浏览计划不会误改计划。
- [ ] 计划阶段能产生实战卡和闪记卡候选。
- [ ] 训练结果先进入证据队列，不会自动改正式计划。
- [ ] 总计划能吸收多个项目子计划的训练证据，评估综合目标进度。

### 11.4 资料验收

- [ ] 资料页首屏是资料工作台，不是后台系统。
- [ ] 默认只有一个主面板。
- [ ] 详情与沙箱通过次层进入。
- [ ] 资料库是跨项目统一的，当前项目资料只是过滤视图而不是独立孤岛。
- [ ] Trainer 可以在资料沙箱内抓取、下载、整理、解析和派生资料，但不能写用户工程空间。
- [ ] 资料沙箱操作必须有来源链、操作日志、影响范围和回滚路径。
- [ ] 资料沙箱在 Windows / macOS / Linux 上路径、编码、权限、下载、解析、skill 运行语义一致。
- [ ] 资料支持中文、English、mixed 原文，并能显示语言、原文、摘要、术语映射和翻译状态。
- [ ] 查资料后能回到训练或项目推进主线。
- [ ] 资料条目像知识库：标题、摘要、标签、来源、可信度、新鲜度。
- [ ] 资料能拆成知识原子，并生成闪记候选、实战候选或计划证据。
- [ ] 资料被用于卡片后，卡片来源链能追踪回资料条目。
- [ ] API 文档能进入 API 方法、参数、返回值、误用和实战场景训练。

### 11.5 训练验收

- [ ] 当前训练任务绝对优先。
- [ ] 用户明确知道自己要亲手写什么。
- [ ] 闪记是训练的一部分，不是独立一级视图。
- [ ] 理论题、闪记、实践、复盘、复习队列形成闭环。
- [ ] 训练页能明确说明自己是计划页的具体实施脚手架。
- [ ] 训练页默认一次只显示一张实战卡或闪记卡。
- [ ] 实战卡片包含 Trainer 编写的代码训练题、`why_now`、题面、建议文件/目录、API 提示、交付物、正确答案形态、自检、验证方法、评分标准、带回对话、回流去向。
- [ ] 实战卡片只指导用户自己做，不替用户创建文件、修改代码或给完整成品补丁。
- [ ] 空项目也能通过实战卡构建最小场景，再迁移到真实工程。
- [ ] 闪记卡片覆盖完整理论知识体系：算法、数学、公式、工程概念、API、参数、返回值、误用、场景、验证和迁移。
- [ ] 闪记卡片包含 Trainer 编写的问题、标准答案、验证方式、评分规则、提示和错因反馈。
- [ ] 闪记卡片支持打字、选择、排序、填空、判断、场景选择等题型。
- [ ] 闪记答错能生成更小卡片、解释或实战卡；答对能进入复习或迁移题。
- [ ] 每张卡都有来源链、目标能力、为什么现在出现、完成后去向。

### 11.6 设置验收

- [ ] 首屏先回答“能不能用、卡在哪、先配什么”。
- [ ] 设置默认是单流窄栏布局。
- [ ] 高级项默认折叠。
- [ ] 危险动作隔离且可理解。
- [ ] 设置能展示当前平台、资料沙箱路径、权限状态、skill 支持平台和跨系统降级原因。
- [ ] 设置能切换语言偏好：中文 / English / 跟随 VS Code，并说明影响范围。

### 11.7 长期闭环验收

- [ ] Trainer 是跨项目统一主体。
- [ ] 每个项目有子计划。
- [ ] 子计划推进回流总计划。
- [ ] 依赖库 / API 掌握能从理论走到真实工程。
- [ ] 资料库、网页抓取、用户上传和受控 skill 处理能长期沉淀到同一个跨项目知识图谱。
- [ ] 资料沙箱与训练分项目治理同时成立，不能把项目训练线切碎成多个资料孤岛。
- [ ] 跨系统使用时，资料库、卡片、计划证据和 skill 操作日志能保持一致语义。
- [ ] 中英双语资料、卡片和答案能服务同一长期能力画像。
- [ ] 用户长期感受到 Trainer 在带自己成长，而不是只在聊天。
- [ ] 依赖库 / API 掌握有概念、核心 API、参数、返回值、误用、验证、最小场景和跨项目迁移记录。
- [ ] 多项目训练结果能汇总到同一个长期能力画像。
- [ ] 卡片、资料、计划、对话之间的证据链长期可追踪。

### 11.8 跨系统验收

- [ ] Windows / macOS / Linux 都能安装、启动、恢复 sidecar，并进入同一资料库语义。
- [ ] 三端资料沙箱路径隔离、路径逃逸检测、权限降级、回滚和审计日志都可验证。
- [ ] 三端 HTML / PDF / Markdown / 代码文档解析结果有 parity report。
- [ ] 三端 skill manifest、平台支持、命令模板、网络权限和输出目录都被执行前校验。
- [ ] 三端用户工程空间都不会被资料沙箱写操作或 skill 越权修改。
- [ ] 三端缺少依赖时能降级并提示，不影响对话、计划、已有资料和已有训练查看。

### 11.9 双语验收

- [ ] UI 支持中文 / English / 跟随 VS Code，五个一级视图文案完整。
- [ ] 对话、计划、资料、训练、设置的错误、恢复、空状态和危险动作提示都有中英文案。
- [ ] 英文资料能生成中文解释、中文训练卡和英文术语索引。
- [ ] 中文资料能通过英文 API 名、代码符号或英文关键词搜到。
- [ ] mixed 答案能被评分，代码标识符、路径、命令、API 名不被机械翻译。
- [ ] 同一知识点中英文卡共享 mastery，不重复计数。
- [ ] 280px 下中文长句和英文长词都不溢出、不重叠、不遮挡主动作。

### 11.10 场景级闭环验收脚本

以下不是建议，是每次声称“闭环完成”时必须能模拟通过的验收脚本。

#### 场景 A：对话卡点生成闪记，再进入实战

- [ ] 用户在对话中说“不理解这个 API 的返回值为什么这样用”
- [ ] 对话只给解释和下一步，不嵌入训练工作台
- [ ] 系统生成一个闪记候选，来源链指向这次对话
- [ ] 闪记卡问题聚焦返回值语义，支持打字或选择
- [ ] 用户答错后给出错因，并生成一个更小返回值卡或 API 参数卡
- [ ] 用户答对后生成或推荐一个实战卡，用最小场景验证该 API
- [ ] 实战完成后结果进入复盘和计划证据，不自动改计划

#### 场景 B：资料 API 文档生成卡片，进入空项目最小场景

- [ ] 用户导入或检索一份依赖库 API 文档
- [ ] 资料页像知识库条目展示标题、摘要、标签、来源、可信度、新鲜度
- [ ] 资料被拆成 API 方法、参数、返回值、误用等知识原子
- [ ] 系统生成闪记候选，来源链指向资料条目
- [ ] 系统生成实战候选，要求用户自己创建最小文件或目录
- [ ] 实战卡提供 API 提示和交付物，但不替用户创建文件或写代码
- [ ] 用户完成后把结果带回对话
- [ ] Trainer 评估后把掌握度写入依赖库能力图
- [ ] 系统追问如何迁移到真实项目，并把证据汇总到总计划

#### 场景 C：项目子计划训练结果回流总计划

- [ ] 当前项目有项目子计划
- [ ] 当前阶段需要某个工程能力
- [ ] 计划页生成实战卡和闪记卡候选，但不把训练页搬进计划页
- [ ] 用户完成训练后，结果进入项目子计划证据队列
- [ ] 系统汇总证据到跨项目总计划能力画像
- [ ] 总计划只更新证据和评估，不自动改正式阶段目标
- [ ] 用户显式采纳后，正式计划才变化

#### 场景 D：实战错误反向生成闪记和资料标注

- [ ] 用户完成实战卡但验证失败
- [ ] Trainer 只评估和追问，不替用户改代码
- [ ] 失败原因被结构化成实战反馈
- [ ] 反馈生成闪记候选，例如参数误解、边界条件、公式条件或算法步骤
- [ ] 相关资料条目被标注“需要复查 / 用户易错点”
- [ ] 下一次训练优先出现更小卡片或恢复题
- [ ] 结果不直接改计划，只进入证据队列

#### 场景 E：窄栏 UI 人性化验收

- [ ] 在 280px 宽度下，五个一级视图都不依赖多栏并排
- [ ] 在 340px 宽度下，训练页当前卡片可完整理解主要动作
- [ ] 在 420px 宽度下，只增强密度，不改变主交互模型
- [ ] 顶部壳层不挤压首屏主任务
- [ ] 当前卡片之前不出现历史、治理、恢复路线大块内容
- [ ] 资料页首屏优先搜索与知识条目
- [ ] 对话页首屏优先消息和输入，不出现大面板堆叠

#### 场景 F：计划证据治理、采纳与恢复

- [ ] 用户完成训练、上传资料或在对话中形成学习证据后，证据先进入待治理队列
- [ ] 计划页展示证据来源、影响范围、建议动作和阻塞原因
- [ ] 用户可以 review、defer、搜索、筛选和批量预演证据
- [ ] 正式采纳前必须能 dry-run 预览字段级变化
- [ ] 未 review 的证据不得直接采纳进正式计划
- [ ] 历史恢复必须区分当前项目正式计划、项目子计划、总计划对照
- [ ] 总计划历史默认 compare-only，不能被误当成可直接回滚对象
- [ ] 恢复执行必须顺序返回 succeeded / failed / skipped，失败即停
- [ ] 任何计划变更都必须是显式计划动作，不能由普通浏览、普通对话或普通训练暗改

#### 场景 G：训练资产恢复、复习队列与最小场景

- [ ] 用户打开训练页时，首屏只出现当前一张卡和最短下一步
- [ ] 到期复习、依赖薄弱点、实战失败和计划缺口共同决定下一张卡
- [ ] 复习队列不能随机出题，必须说明 why_now 和 source_chain
- [ ] 依赖/API 弱点优先落到闪记、最小场景或实战卡，而不是只展示掌握分
- [ ] 训练资产恢复必须覆盖 dependency_skill_map、scenario_lab、theory_drill、review_artifact
- [ ] 恢复前必须支持 dry-run，不突变训练状态
- [ ] 多依赖历史恢复必须保留其它可恢复依赖，不能只恢复当前第一条
- [ ] scenario_lab / theory_drill / review_artifact 必须优先恢复最新可恢复快照
- [ ] 恢复训练资产不能伪装成聊天回复，也不能隐藏修改正式计划

#### 场景 H：资料知识库、沙箱治理与大批量导入

- [ ] 用户导入资料时，资料页先展示可搜索知识条目，而不是上传后台
- [ ] 资料必须先落成 metadata、来源、可信度、新鲜度和知识原子
- [ ] 大批量导入时先返回前台可用状态，深度处理进入可取消队列
- [ ] 资料详情和沙箱必须作为次层进入，默认不得三栏并排
- [ ] 沙箱是 Trainer 资料治理空间，不是用户工程空间；Trainer 可以在其中整理、下载、改写派生资料和运行受控 skill
- [ ] 所有沙箱写操作都必须保留来源链、操作日志、影响范围和回滚路径
- [ ] 沙箱越界必须在 webview、extension command、sidecar API 三层都被拦截
- [ ] 资料过期、冲突或不可信时，相关卡片必须暂停或标注待复查
- [ ] 资料必须能回流到闪记、实战、依赖掌握和计划证据，不能只存文件
- [ ] 用户上传的 HTML、PDF、Markdown、代码文档和网页快照都必须进入统一解析和索引链路
- [ ] Trainer 可以浏览网页并把有用内容下载到资料库，但必须保留 URL、时间、来源和许可/限制信息

#### 场景 I：跨系统资料沙箱与 skill 一致性

- [ ] 在 Windows 中资料沙箱路径包含盘符、空格、中文目录时，导入、下载、索引、回滚都不逃逸 sandbox root
- [ ] 在 macOS 中路径大小写差异、权限不足或应用沙箱限制出现时，Trainer 给出降级状态和恢复路径
- [ ] 在 Linux 中 symlink 指向工程目录时，资料 skill 写操作被拦截
- [ ] 同一 HTML / PDF / Markdown / 代码文档样例在三端生成等价 metadata、knowledge_atoms、source_chain
- [ ] skill manifest 标明平台支持；不支持当前平台时不运行，只展示原因和替代处理
- [ ] 三端沙箱操作日志都能追踪来源、命令/动作、输入输出、影响范围和回滚点

#### 场景 J：中文 / English 双语学习闭环

- [ ] 用户偏好为中文时，UI、对话、计划说明、训练反馈用中文，API 名和代码标识符保留原文
- [ ] 用户偏好为 English 时，chat, plan, resource summaries, training prompts, feedback use English with technical names preserved
- [ ] 用户上传英文 API 文档后，资料页生成中文摘要、英文术语索引和可训练知识原子
- [ ] 用户用中文回答英文术语卡，rubric 能识别正确语义，不因语言不同误判
- [ ] 同一知识点的中文卡和英文卡共享 mastery 节点，不重复计数
- [ ] 搜索中文概念能找到英文 API 文档，搜索英文 API 名也能找到中文笔记
- [ ] UI 在 280px 下中文长句和英文长词都不溢出、不重叠、不遮挡主动作

#### 场景 K：provider、sidecar、权限与运行恢复

- [ ] 首次配置 provider 时，设置页只展示最短可用路径和当前连接状态
- [ ] API key 只能进入 SecretStorage，不得在日志、对话、快照或报错中泄露
- [ ] provider 测试失败时，必须说明是 key、base URL、model、网络还是服务端错误
- [ ] sidecar 未启动或 `/health` 失败时，设置页必须给出重启、端口、日志和 smoke 检查入口
- [ ] sidecar 恢复后，webview 快照、训练状态、计划证据和资源索引必须可重新合并
- [ ] workspace trust 或权限不足时，Trainer 必须降级为解释与指导，不执行项目改动
- [ ] 用户仍能继续查看计划、资料摘要和已有训练，不因 provider/sidecar 故障白屏
- [ ] 对话模型不可用时，不能伪造训练评估或计划结论

#### 场景 L：跨项目恢复、打包态一致性与发布验收

- [ ] 用户切换工作区后，Trainer 仍是同一个跨项目教练主体
- [ ] 当前项目子计划、项目训练线和总计划 rollup 必须重新绑定并可解释
- [ ] session restore 不得把上一个项目的卡片、资料或计划误作为当前项目内容
- [ ] 源码态和 bundled 态必须保持关键 server、prompt、pedagogy、resource、provider、router 行为一致
- [ ] 发布前必须验证 extension/webview build、extension host check、server static/test、smoke readiness
- [ ] 性能声明必须有输出通道、构建大小、回归测试或手动记录证据
- [ ] 长对话、流式回复、大资料库、200 文件导入、session restore 都必须保持侧栏可交互
- [ ] 发布态不能出现“源码可用、VS Code 扩展不可用”的假完成

#### 场景 M：打开已有项目并掌握实现方法

- [ ] 用户打开一个已有工程文件夹
- [ ] Trainer 先判断这是已有工程，而不是空项目
- [ ] Trainer 生成项目子计划候选和项目训练线，但不自动改正式计划
- [ ] 训练先出现项目地图卡或关键模块理解卡
- [ ] 后续卡片包含源码走读实战、局部修改实战、验证/回归卡
- [ ] 用户必须自己阅读、修改或验证，Trainer 只给题面、提示和检查标准
- [ ] 完成证据先进入项目子计划，再按质量回流总计划

#### 场景 N：掌握算法或模型实现方法

- [ ] 用户打开算法或模型仓库，或导入相关论文/文档/代码
- [ ] Trainer 区分算法理论、模型结构、数据流、训练流程、实现文件和验证方式
- [ ] 闪记卡覆盖定义、公式、复杂度、边界、模型结构或训练流程
- [ ] 实战卡要求用户自己走读关键函数、复现实验、实现小变体或验证输出
- [ ] 如果用户答错理论题，先回到更小理论卡
- [ ] 如果用户实战失败，生成实现走读卡、资料标注或更小复现实战
- [ ] 掌握证据必须包含理解、记忆、做出和迁移，不只看“跑通一次”

#### 场景 O：idea 落地为代码但 Trainer 不代写

- [ ] 用户只说一个清晰或模糊 idea
- [ ] Trainer 先判断需求清晰度，并给最小澄清或默认假设路径
- [ ] 计划页只生成 idea 项目子计划候选，不自动改正式计划
- [ ] 训练编排为需求澄清卡、边界卡、架构取舍卡、最小切片实战卡、验证卡
- [ ] 实战卡可以建议用户自己创建文件或目录，但不能替用户创建或写代码
- [ ] 用户实现后把结果带回对话，Trainer 评估并生成复盘或下一张卡
- [ ] 总计划只吸收能力证据，不把 idea 完成度等同于工程掌握

#### 场景 P：现有项目深度优化和修改

- [ ] 用户提出“优化、重构、改功能、提高性能、改架构”等请求
- [ ] Trainer 先区分这是纯讨论、理解项目、制定修改计划，还是进入训练
- [ ] 训练必须先出现现状理解卡、风险卡、验证标准卡，再出现修改实战卡
- [ ] 修改实战卡要求用户自己完成最小改动，并带回测试/指标/错误信息
- [ ] 失败时生成更小修改卡、测试理解卡或资料标注
- [ ] 成功时生成复盘、项目子计划证据和总计划能力回流
- [ ] Trainer 不得直接输出完整补丁替用户修改项目

#### 场景 Q：工作中单纯对话与模糊需求处理

- [ ] 用户明确只是想讨论方案、判断思路、比较技术或复盘工作
- [ ] 对话页保持纯对话，不嵌入完整训练、资料或计划工作台
- [ ] Trainer 可以只回答，不强行生成卡片或计划动作
- [ ] 如果发现明显薄弱点，只给轻量候选提示，由用户决定是否进入训练
- [ ] 用户需求清晰时，Trainer 直接给下一步，不过度追问
- [ ] 用户需求模糊时，Trainer 最多给 1-3 个澄清点或一个默认最小路径
- [ ] 任何普通对话都不能暗改正式计划

## 13. 设计理论闭环与实施防错原则

本章用于防止后续实施时“功能看起来都有，但学习、计划、资料、训练没有真正闭环”。
任何实现方案必须先通过本章，再进入开发。

### 13.1 第一性原则

Trainer 的第一性原则不是聊天，也不是做题，而是：

`让用户在真实工程语境中形成可迁移的认知与动手能力。`

因此所有功能都必须服务以下链路：

`目标 -> 诊断 -> 资料 -> 闪记 -> 实战 -> 验证 -> 反馈 -> 复盘 -> 证据 -> 计划 -> 复习 -> 迁移 -> 总计划评估`

如果某个功能无法说明它服务链路中的哪一环，就不应该进入首屏。

### 13.2 学习理论闭环

Trainer 的训练理论必须同时覆盖四层学习：

- `知道`：用户能说清概念、API、参数、公式或算法为什么这样。
- `记住`：用户能在无提示或弱提示下回忆关键用法。
- `做出`：用户能在具体文件、模块或最小场景里亲手实现。
- `迁移`：用户能把同一能力迁到另一个项目、模块、依赖或问题。

对应产品机制必须是：

- [ ] `知道` 由对话解释、资料知识原子、理论卡支撑。
- [ ] `记住` 由闪记卡、复习队列、掌握度调度支撑。
- [ ] `做出` 由实战卡、最小场景、自检和教练反馈支撑。
- [ ] `迁移` 由项目子计划、依赖能力图、跨项目证据和总计划评估支撑。

缺任何一层，不能声称 Trainer 已经完成长期训练闭环。

### 13.3 认知负担理论

Trainer 必须主动降低用户理解成本。
降低理解成本不是减少能力，而是控制同一时刻出现的信息量。

固定规则：

- [ ] 每个一级视图首屏只能有一个主任务。
- [ ] 训练页每次只能有一张当前卡。
- [ ] 资料页首屏只解决“查什么、哪条有用、来源是否可信”。
- [ ] 计划页首屏只解决“现在目标是什么、为什么这一步、怎么验证”。
- [ ] 对话页首屏只解决“当前回复、下一步、输入”。
- [ ] 任何历史、治理、恢复、依赖图、复习队列都必须次层展开。

认知负担禁区：

- [ ] 同一屏同时解释系统架构、计划、训练、资料和历史。
- [ ] 让用户先理解内部状态机再开始学习。
- [ ] 用很多大卡片制造“功能完整”的错觉。
- [ ] 用过多标签、芯片、指标替代清晰动作。

### 13.4 信息架构理论

五个一级视图必须是互补关系，不是重复关系。

| 视图 | 信息架构职责 | 不能承担 |
|---|---|---|
| 对话 | 解释、澄清、追问、压缩下一步、触发候选 | 计划编辑器、资料后台、训练工作台 |
| 计划 | 总目标、项目子计划、正式步骤、证据、显式计划动作 | 普通聊天、随机训练列表 |
| 资料 | 知识库搜索、条目、来源、可信度、知识原子、受控沙箱治理 | 文件管理后台、无审计沙箱、越权项目操作 |
| 训练 | 实战卡、闪记卡、复盘、复习队列、掌握度 | 网页式任务中心、卡片墙 |
| 设置 | 可用性、provider、sidecar、危险动作隔离 | 学习内容、训练内容、计划内容 |

任何视图如果开始承担另一个视图的完整工作台职责，必须重构。

### 13.5 状态机理论

所有核心对象必须有状态机，不能只有 UI 展示。

计划状态机：

`draft_evidence -> reviewed_evidence -> proposed_plan_change -> explicit_acceptance -> formal_plan -> history`

卡片状态机：

`candidate -> active -> answered/implemented -> reviewed -> fed_back -> scheduled/archived`

资料状态机：

`imported -> indexed -> knowledge_atoms -> linked_to_cards/evidence -> used -> stale/verified`

依赖掌握状态机：

`understood -> recalled -> practiced -> applied -> transferable`

复习状态机：

`new -> due -> answered -> rescheduled -> strengthened/needs_recovery`

对话超级入口候选状态机：

`created -> surfaced -> accepted/continued_in_chat -> dismissed/deferred -> blocked/expired -> archived`

硬规则：

- [ ] 没有状态机的对象不能进入长期闭环。
- [ ] 状态变化必须有触发来源。
- [ ] 状态变化必须能解释为什么发生。
- [ ] 状态变化必须能回滚或至少能审计。
- [ ] 正式计划状态变化必须经过显式动作。
- [ ] 对话侧候选对象不能只有“生成了”这一瞬间，必须能追踪它是否被看见、被接受、被忽略、被阻断或自然过期。
- [ ] `coach_visible_status` 不是普通日志，它也必须有生命周期，避免同一条状态长期悬挂或重复刷屏。
- [ ] `micro_drill_prompt` 与 `card_invocation` 必须能区分“在对话里完成了”“中断了”“已升级为训练页正式卡”“因资料不足被阻断”。
- [ ] `dismissed` 与 `expired` 必须区分：前者是用户或系统明确不要，后者是时间或上下文已过期。
- [ ] `blocked` 必须写明阻断原因，例如资料不可信、项目上下文未定、当前阶段不相关、已有更高优先级卡。

#### 13.5.1 候选对象统一生命周期协议

对话超级入口产生的候选对象至少包括：

- `project_context_candidate`
- `resource_import_candidate`
- `evidence_candidate`
- `flash_candidate`
- `practice_candidate`
- `coach_visible_status`
- `micro_drill_prompt`
- `card_invocation`

所有候选对象都必须回答同一组问题：

1. `为什么产生`
2. `现在展示给谁`
3. `用户是否已经看见`
4. `用户是否接受`
5. `如果没接受，是忽略、延期、阻断还是过期`
6. `它最终沉淀成了什么正式对象`

最小统一字段必须包含：

- [ ] `candidate_id`
- [ ] `candidate_type`
- [ ] `source_chain`
- [ ] `why_now`
- [ ] `project_scope`
- [ ] `status`
- [ ] `status_reason`
- [ ] `surfaced_at`
- [ ] `expires_at`
- [ ] `accepted_into`
- [ ] `blocked_by`
- [ ] `accepted_at`
- [ ] `continued_in_chat_at`
- [ ] `deferred_at`
- [ ] `dismissed_at`
- [ ] `blocked_at`
- [ ] `expired_at`
- [ ] `archived_at`
- [ ] 上述生命周期时间锚点必须是对象级真相，而不是只散落在事件账本里；允许某些字段为空，但一旦发生对应状态迁移，就必须只写一次并保留。

状态转换硬规则：

- [ ] `created -> surfaced`：只有真正回到用户前台或进入可治理队列才算 surfaced。
- [ ] `surfaced -> continued_in_chat`：只适用于 `micro_drill_prompt`、`card_invocation` 这类允许在对话中继续完成的对象。
- [ ] `surfaced -> accepted`：意味着用户显式进入资料/计划/训练下一步，或明确采纳该候选。
- [ ] `surfaced -> dismissed`：意味着用户明确忽略、关闭或拒绝。
- [ ] `surfaced -> deferred`：意味着候选保留但暂不执行，需要未来重新 surfaced。
- [ ] `surfaced -> blocked`：意味着系统发现权限、可信度、上下文或优先级问题。
- [ ] `surfaced -> expired`：意味着上下文已变化到不适合继续引用原候选。
- [ ] `accepted -> archived`：意味着它已经转成正式对象或完成闭环，不再作为活跃候选出现。
- [ ] `accepted / continued_in_chat / dismissed / expired / archived` 是关闭态；除显式 `archive` 外，不得被普通 `accept / defer / dismiss / block` 重新打开或重复触发接力事务。
- [ ] 关闭态被重复点击时，服务端必须返回原状态、写入拒绝原因和事件账本，不得再次写计划、资料、训练或微训练 handoff。
- [ ] `accept` 必须写入 `accepted_at`；若实际进入 `continued_in_chat`，还必须同步写入 `continued_in_chat_at`。
- [ ] `defer / dismiss / block / expire / archive` 必须分别写入 `deferred_at / dismissed_at / blocked_at / expired_at / archived_at`。
- [ ] `deferred / blocked` 是可恢复态；同一候选再次 surfaced 时必须保留原 `candidate_id`、阻断/延期解释和创建时间，只允许刷新 `why_now / status_reason / expires_at / updated_at`。
- [ ] `deferred / blocked` 再次 surfaced 时，不得抹掉已有 `deferred_at / blocked_at` 历史锚点；关闭态再次以新候选 resurfaced 时，必须使用新 `candidate_id` 和新生命周期时间锚点。
- [ ] `dismissed / expired / archived` 在同一上下文中不得反复弹出；只有 `why_now` 发生实质变化时，才允许以新候选重新 surfaced。
- [ ] `expire` 与 `archive` 必须是显式可审计动作：`expire` 表示上下文不再适合引用，`archive` 表示生命周期已解决或人工收纳；二者都必须进入统一事件账本。
- [ ] 对话气泡必须显示关闭态、阻断态和延期态的简短说明，但不得增加复杂治理工作台或把 `过期 / 归档` 暴露成高频按钮。
- [ ] `accepted / continued_in_chat / dismissed / expired / archived` 在对话气泡中只能作为结果状态展示：允许显示标题、状态和简短说明；不得继续显示普通动作按钮、`为什么`、`去哪里继续` 或任何会让用户误以为仍可重复接力的 affordance。
- [ ] `deferred / blocked` 仍可显示 `为什么`、`去哪里继续` 与普通轻动作，但必须按状态禁用已经成立的动作，例如 `deferred` 禁用再次稍后、`blocked` 禁用再次受阻。

### 13.6 证据链理论

Trainer 的任何判断都必须能追踪证据。

证据链最少包含：

- `source_type`：对话、计划、资料、实战、闪记、复习、依赖掌握。
- `source_id`：具体消息、资料、卡片、项目、计划阶段或复习项。
- `why_now`：为什么现在出现。
- `target_skill`：服务哪个能力点。
- `expected_evidence`：用户完成后应该产生什么证据。
- `feedback_target`：结果回流到哪里。

以下判断如果没有证据链，必须禁止：

- [ ] 生成训练卡。
- [ ] 改变掌握度。
- [ ] 推荐计划调整。
- [ ] 判断用户已掌握。
- [ ] 判断资料可信。
- [ ] 判断某依赖/API 已可迁移。

### 13.7 教练行为理论

Trainer 的行为必须像教练，不像代工者。

教练可以：

- [ ] 观察项目和用户目标。
- [ ] 提问澄清。
- [ ] 压缩下一步。
- [ ] 解释概念、API、参数、返回值和误用。
- [ ] 给局部示例、伪代码、验证思路。
- [ ] 要求用户自己打开或新建文件。
- [ ] 评估用户带回的结果。
- [ ] 把薄弱点生成卡片和复习。

教练不能：

- [ ] 替用户创建文件。
- [ ] 替用户修改代码。
- [ ] 替用户提交补丁。
- [ ] 默认给完整可粘贴答案。
- [ ] 把一次答对当作长期掌握。
- [ ] 把训练结果自动写成正式计划。

如果“帮助用户更快完成”和“让用户真正学会”冲突，Trainer 必须优先让用户真正学会。

### 13.8 卡片理论

卡片不是 UI 装饰，而是最小学习对象。

一张合格卡片必须同时满足：

- [ ] 只有一个主问题或一个主工程动作。
- [ ] 有明确来源链。
- [ ] 有明确为什么现在出现。
- [ ] 有明确目标能力。
- [ ] 有明确用户动作。
- [ ] 有明确完成标准。
- [ ] 有明确回流去向。

实战卡的理论目标是让用户 `做出`。
闪记卡的理论目标是让用户 `记住并理解`。
两者必须互相反作用：

- [ ] 实战暴露薄弱点，生成闪记。
- [ ] 闪记连续掌握，生成实战验证。
- [ ] 实战验证通过，进入计划证据。
- [ ] 闪记长期稳定，进入依赖掌握度。

卡片内容责任必须归 Trainer：

- [ ] Trainer 负责根据计划、资料、依赖和用户表现编写卡片内容。
- [ ] Trainer 负责为闪记卡设计理论问题、标准答案、评分规则和错因解释。
- [ ] Trainer 负责为实战卡设计代码训练题、正确答案形态、验证方法和评分标准。
- [ ] Trainer 不能把出题责任推给用户。
- [ ] Trainer 不能只展示资料摘录然后要求用户自己想题。
- [ ] Trainer 不能把实战卡写成“去实现某功能”这种无验收标准的任务。

训练页理论隐喻必须固定为：

`计划页给路线，训练页发卡片；闪记补理论，实战练代码；结果回计划。`

如果训练页不能解释当前卡片对应哪个计划阶段、理论缺口或实战能力，它就不是合格训练页。

### 13.9 资料理论

资料不是附件仓库，也不是只读预览区。
资料是跨项目统一知识库，是 Trainer 可以自主管理的受控资料沙箱。

资料必须完成三次转化：

1. `来源转化`：文件、URL、笔记变成可搜索资料条目。
2. `知识转化`：资料条目拆成知识原子。
3. `训练转化`：知识原子变成闪记、实战、计划证据或依赖能力项。

资料还必须完成一次治理：

4. `沙箱治理`：网页抓取、用户上传、格式解析、派生笔记、索引、归档、skill 处理都在受控沙箱中可审计、可回滚、可追踪影响范围。

资料条目如果不能被检索、引用、拆解、转卡或沉淀，就只是文件列表，不是 Trainer 资料库。
资料沙箱如果不能被 Trainer 安全管理，就只是附件仓库，不是教练 Agent 的知识工作区。

### 13.10 计划理论

计划不是任务清单，而是学习治理结构。

计划必须同时回答：

- 用户长期要达成什么综合能力。
- 当前项目贡献哪个子目标。
- 当前阶段为什么是现在这一步。
- 什么证据能证明这一步完成。
- 哪些训练结果只是证据，哪些可以被采纳成正式计划变化。

计划理论硬规则：

- [ ] 总计划评估综合能力，不只统计任务完成数。
- [ ] 子计划推进必须能回流总计划。
- [ ] 训练结果默认是证据，不是计划变更。
- [ ] 计划变化必须显式采纳。
- [ ] 浏览、训练、资料学习都不能暗改正式计划。

### 13.11 UI 设计理论

Trainer 的高级感来自“克制、层级、工具性”，不是来自装饰。

侧边栏 UI 必须遵守：

- [ ] 先主任务，后解释。
- [ ] 先当前对象，后历史。
- [ ] 先用户动作，后系统治理。
- [ ] 先单栏，后增强。
- [ ] 先短文本，后展开详情。
- [ ] 先 VS Code 工具感，后品牌表达。

视觉禁区：

- [ ] 网页 dashboard。
- [ ] 管理后台。
- [ ] 卡片墙。
- [ ] 多栏并排。
- [ ] 大面积介绍文案。
- [ ] 固定大头部挤压主任务。
- [ ] 看起来“很丰富”但用户不知道下一步。

### 13.12 实施前置判定

任何新功能开工前必须回答 10 个问题：

- [ ] 它服务哪一个学习闭环环节？
- [ ] 它属于哪个一级视图？
- [ ] 它会不会吞并另一个视图的职责？
- [ ] 它的主状态机是什么？
- [ ] 它产生或消费什么证据？
- [ ] 它会不会让计划被隐式修改？
- [ ] 它会不会让 Trainer 替用户动手？
- [ ] 它在 280px 侧边栏里首屏主任务是否仍清楚？
- [ ] 它失败时用户知道怎么恢复吗？
- [ ] 它完成后如何回流到长期能力画像？

任一问题无法回答，不能进入实现。

### 13.13 反回归原则

后续任何改动如果导致以下情况之一，必须视为设计回归：

- [ ] 对话页开始承载完整训练工作台。
- [ ] 计划页出现普通聊天输入。
- [ ] 资料页退化成文件管理后台。
- [ ] 训练页一屏显示多张卡。
- [ ] 闪记变成新的一级视图。
- [ ] 实战卡开始替用户写代码。
- [ ] 资料学习或训练结果自动改正式计划。
- [ ] 卡片没有来源链。
- [ ] UI 在 340px 下出现横向溢出、重叠或主任务不可见。
- [ ] 总计划无法吸收项目子计划证据。

### 13.14 理论闭环完成定义

只有同时满足以下条件，才能说 Trainer 从设计理论上闭环：

- [ ] 用户能从对话进入计划、资料或训练，但不会混淆它们。
- [ ] 用户能查资料，并把资料转成知识、卡片和计划证据。
- [ ] 用户能刷闪记，真正记住理论、API、参数、公式和误用边界。
- [ ] 用户能做实战卡，亲手完成最小工程动作。
- [ ] 用户能把实战结果带回 Trainer 接受评估。
- [ ] Trainer 能把薄弱点反向生成闪记、复习和更小实战。
- [ ] Trainer 能把项目子计划证据汇总到总计划。
- [ ] Trainer 能评估依赖/API 是否从理解走到可迁移。
- [ ] Trainer 始终不替用户改代码。
- [ ] 所有这些都能在 VS Code 窄侧边栏中低理解成本完成。

### 13.15 设计闭环总模型

任何功能、页面、卡片、接口或模型输出，必须能落在同一个闭环模型中：

`用户输入 -> Agent 识别场景 -> 绑定项目/总计划 -> 选择教学动作 -> 生成学习对象 -> 用户自执行 -> Trainer 评估 -> 证据回流 -> 下一轮`

这个模型是实施防错的最高判断标准。
如果一个改动不能说清自己处在哪一环、消费什么证据、产生什么证据、回流到哪里，就不能进入核心实现。

| 闭环环节 | 设计问题 | 必须有的实现痕迹 |
|---|---|---|
| 用户输入 | 用户是清晰需求、模糊需求、纯对话、资料导入、计划治理还是训练反馈？ | intent / scenario 分类 |
| 场景识别 | 是掌握项目、算法/模型、idea 落地、API 掌握、优化修改还是运行恢复？ | scenario_type |
| 项目绑定 | 当前是空项目、已有项目、算法/模型仓库、idea 文件夹、资料文件夹还是不确定？ | project_context_classification、project_id |
| 总计划绑定 | 当前动作贡献哪个长期能力？ | master_plan_goal、learner_model_delta |
| 教学动作 | 当前主动作是解释、闪记、实战、资料检索、复盘还是计划治理？ | next_teaching_action |
| 学习对象 | 生成的是卡片、知识原子、证据、复盘还是候选计划变化？ | typed object + source_chain |
| 用户自执行 | 用户要自己答题、读代码、建文件、修改、验证还是带回结果？ | learner_owned_step |
| Trainer 评估 | 如何判定通过、部分通过、失败、误解或迁移不足？ | rubric、validator、review_artifact |
| 证据回流 | 结果进入复习、资料标注、项目子计划、总计划还是依赖图？ | feedback_targets |
| 下一轮 | 下一步是更小卡、迁移卡、复习、实战、计划采纳还是纯对话？ | next_step_hint |

强制规则：

- [ ] 一个 UI 区块如果不能对应闭环环节，就应该删除或降级。
- [ ] 一个后端对象如果没有来源链和回流目标，就不能作为核心对象。
- [ ] 一个模型回复如果只有解释，没有下一步或不说明为何不进入下一步，就不完整。
- [ ] 一个训练卡如果不能说明计划/资料/对话/复习来源，就不是合格训练。
- [ ] 一个计划变化如果没有显式采纳，就不能成为正式计划。
- [ ] 一个实战动作如果由 Trainer 代做，就破坏闭环。

### 13.16 定制化教练 Agent 设计理论

Trainer 必须被设计成一个长期一致的教练 Agent，而不是多个局部功能的集合。

Agent 的设计核心是：

`同一个 Agent，在多个项目中持续理解同一个用户，并用对话、资料、计划、训练四类内容持续调节用户的理论和实践成长。`

前台上，它要像一个会教学、会追问、会查证、会安排训练的人类教师；
后台上，它要把这些动作稳定写进资料、计划、训练闭环。

因此，Agent 必须具备四种能力：

- `理解用户`：知道用户长期目标、薄弱点、学习节奏、常错模式。
- `理解项目`：知道当前项目结构、子计划、工程场景、依赖库/API。
- `理解知识`：知道资料中的理论、公式、算法、API、工程案例是否可信且可训练。
- `治理资料`：能在跨项目资料沙箱内抓取、下载、解析、整理、索引、运行受控 skill，并把资料变成可训练知识。
- `理解训练`：知道什么时候该解释、什么时候该闪记、什么时候该实战、什么时候该复盘。
- `理解教学时机`：知道什么时候该主导、什么时候该配合、什么时候该当场追问、小测、调卡，什么时候只给一个下一步。

#### 四个学习内容域的统一合约

`对话 / 资料 / 计划 / 训练` 不是四个孤立页面，而是同一个 Agent 的四类学习内容域。
每个内容域都必须有明确输入、Agent 处理方式、输出对象和禁止边界。

| 内容域 | 用户如何使用 | Agent 如何使用 | 必须输出 | 禁止承担 |
|---|---|---|---|---|
| 对话 | 说目标、问题、卡点、错误、训练结果、疑问、节奏偏好，也可附带文件、文件夹或链接 | 识别意图、薄弱点、情绪、计划意图、资料需求、训练反馈、项目上下文输入，并决定是否需要当场追问、小测或调卡 | conversation_signal、gap_candidate、card_candidate、evidence_candidate、resource_import_candidate、project_context_candidate、coach_visible_status、micro_drill_prompt、card_invocation、next_step_hint | 承载完整训练工作台、暗改计划、替用户写代码 |
| 资料 | 上传 HTML/PDF/Markdown/代码文档/API 文档/笔记，也可让 Trainer 检索网页或整理资料 | 抽知识原子、判断可信度/新鲜度、绑定计划阶段、管理资料沙箱、运行受控 skill、生成训练候选 | resource_record、knowledge_atom、flash_candidate、practice_candidate、resource_annotation、resource_operation_log | 退化成文件管理器、只摘要不转训练、无审计改写沙箱、越权写用户工程 |
| 计划 | 查看总计划、项目子计划、阶段目标、证据缺口、采纳候选 | 约束训练优先级、判断证据是否足够、治理总计划与子计划关系 | plan_state、plan_gap、evidence_queue、proposed_plan_change、rollup_delta | 普通聊天、浏览即修改、训练结果自动改正式计划 |
| 训练 | 一次刷一张闪记或实战卡，提交答案、卡住、跳过、带回验证结果 | 执行计划脚手架、评估理论/实践/迁移掌握、生成复习与复盘 | active_card、attempt_record、practice_review、mastery_delta、review_queue、plan_evidence_candidate | 随机题库、卡片墙、替用户实现、脱离计划阶段 |

设置不属于学习内容域，它是运行保障域：

- [ ] 设置只保证 provider、sidecar、权限、数据边界和恢复路径可用。
- [ ] 设置不得承载训练、计划、资料或对话主内容。
- [ ] 当设置异常影响学习闭环时，只能给降级策略和恢复入口，不能伪造学习结果。

#### Agent 每轮决策协议

Agent 每次响应或生成学习对象前，都必须执行同一套决策协议，避免“用户说什么就只回答什么”。

1. `识别入口`：判断用户来自对话、资料、计划、训练还是设置异常，并区分是否携带文件、文件夹、链接或验证结果。
2. `识别意图`：区分解释请求、计划请求、资料请求、训练请求、实战反馈、运行恢复、闲聊。
3. `融合上下文`：读取当前项目子计划、跨项目总计划、最近训练结果、资料知识原子、依赖掌握图和用户长期画像。
4. `诊断缺口`：判断是理论不会、记忆不稳、API 不熟、工程实践不会、验证不会、迁移不会，还是资料/计划/运行环境问题。
5. `选择主动作`：只能选择一个当前主动作，例如解释、生成闪记、生成实战、查资料、进入复盘、加入计划证据、进入计划治理。
6. `写入对象`：把结果写到对应对象，不能只停留在自然语言回复。
7. `反馈用户`：用一句低理解成本反馈说明“为什么这样做、下一步去哪里、不会自动越权什么”。

必须满足：

- [ ] 一次响应只能有一个首要下一步，最多两个次要动作。
- [ ] 任何自动生成的卡片、证据、资料标注都必须有 `source_chain` 和 `why_now`。
- [ ] 计划变化必须进入计划治理动作，不得混在普通对话回复里生效。
- [ ] 实战动作必须要求用户自己完成，Trainer 只提供题面、提示、验证和反馈。
- [ ] 资料沙箱写动作必须进入资料治理对象，写明沙箱路径、来源、操作日志、回滚点和影响范围。
- [ ] 如果上下文不足，Agent 应该生成最小澄清问题或最小资料需求，而不是假装闭环。

#### 教练式回复协议

`对话` 中的每一轮回复都必须像教师，不像搜索结果或系统通知。

每轮回复尽量按以下顺序完成：

1. `先回答`：先解决用户眼前的问题或困惑。
2. `再教会`：用深入浅出的方式补上关键概念、边界、原理或判断方法。
3. `再说明动作`：告诉用户 Trainer 刚刚查了什么、整理了什么、判断了什么。
4. `再压缩下一步`：只给一个最值得做的主下一步。
5. `必要时微训练`：只允许一个追问、小测、卡片调用或训练建议。

必须满足：

- [ ] 回答要同时服务 `可懂 / 可学 / 可继续`，不能只像客服答复。
- [ ] 能用一个关键追问确认理解时，不应该堆一大段理论。
- [ ] 能用一道小题确认掌握时，优先小题而不是长篇说教。
- [ ] 任何教练动作都必须解释它的目的、去向和不会自动发生什么。
- [ ] 长期语气必须稳定、克制、有人味，不像流程机器人。

#### 教练超级入口 UI 契约

`对话` 作为超级入口，前台必须稳定呈现同一套轻量结构。
它不是自由发挥的消息拼装区。

每轮回复可见结构最多包含：

1. `主回复`
2. `教练动作`
3. `主下一步`
4. `轻量候选`
5. `边界说明`

各区块硬规则：

- [ ] `主回复` 必须始终存在，且优先解决用户当前问题。
- [ ] `教练动作` 最多 1 条，说明 Trainer 正在查什么、整理什么、判断什么、准备什么。
- [ ] `主下一步` 最多 1 条，不能同时给多个主方向。
- [ ] `轻量候选` 最多 2 条，每条都必须有 `为什么` 和 `去哪里继续`。
- [ ] `边界说明` 只在会发生误解时出现，例如“不自动改正式计划”“不自动改项目代码”。

显示/折叠规则：

- [ ] `教练动作` 默认贴近当前回复，不做常驻全局面板。
- [ ] 已完成或已过期的 `教练动作` 必须自动收敛成历史标签或摘要，不得长时间常驻。
- [ ] 相同类型且同原因的动作提示必须去重。
- [ ] 用户明确忽略的候选不得在同一上下文中反复弹出，除非 `why_now` 发生变化。
- [ ] 对话历史中的旧动作只保留最小审计摘要，不保留工作台式详情。

禁止形态：

- [ ] 回复上方常驻多栏状态面板
- [ ] 一条消息下挂三块以上运营式卡片
- [ ] 对话区出现完整计划 diff、完整资料树或完整训练列表
- [ ] 对话消息看起来像后台控制台

#### 主导型与配合型教练模式

Trainer 既要能主导，也要能配合。
主导不是越权，配合也不是被动。

| 模式 | 适用场景 | 教练表现 | 不变边界 |
|---|---|---|---|
| 主导型 | 用户模糊、卡住、分散、长期停滞、不知道下一步 | 主动压缩路径、主动提关键问题、主动查资料、主动给卡片候选或最小训练动作 | 不暗改计划、不替用户写代码、不强推多条路线 |
| 配合型 | 用户目标清晰、正在推进、只需判断/解释/校验 | 快速回答、快速校验、轻量提示资料/计划/训练去向 | 仍持续诊断薄弱点，仍保持闭环和边界说明 |

必须满足：

- [ ] Agent 可以在主导型和配合型之间切换，但必须让用户感知切换原因。
- [ ] 主导型只意味着更主动地教学和压缩路径，不意味着替用户执行工程动作。
- [ ] 配合型只意味着更贴近用户当前节奏，不意味着停止资料、计划和训练联动判断。

#### 纯对话前台与后台工作流协同协议

`纯对话` 不是“什么都不做”，而是“用户只看到对话，后台照常做闭环判断，但只以轻量反馈回到消息流”。

后台协同协议必须固定为：

| 后台阶段 | 必须读取 | 允许写入 | 用户在对话里应该看到什么 |
|---|---|---|---|
| turn classification | 当前消息、最近几轮上下文、当前项目身份 | conversation_signal | 一句准确回应当前问题的主回复 |
| project grounding | 当前工作区、文件夹分类、已有项目摘要、当前项目子计划 | project_context_candidate、workspace_understanding_request | “我把这轮理解为已有项目/idea/API 学习/纯讨论” |
| resource grounding | 全局资料库、当前项目绑定资料、外部来源缺口 | resource_query、resource_import_candidate | “这个问题已有资料依据 / 还缺一份资料 / 我会先入库再继续” |
| plan alignment | 当前总计划、项目子计划、待吸收证据、阶段缺口 | evidence_candidate、proposed_plan_change | “这会进入计划候选，但不会自动改正式计划” |
| training scheduling | 当前阶段、薄弱点、最近答题/实战、复习队列 | flash_candidate、practice_candidate、review_goal、card_invocation、micro_drill_prompt | “这更适合出一张闪记/实战卡” / “我先当场问你一道小题” |
| response packaging | 上述所有判断 | coach_visible_status、next_step_hint、optional_candidate | 一个主下一步，一个轻量教练动作说明，最多两个轻量候选提示 |

必须满足：

- [ ] 后台可以同时判断四域，但前台必须只呈现一个主结论。
- [ ] 当用户只想讨论时，后台最多形成轻量候选，不得强推跳视图。
- [ ] 当用户明确需要推进时，后台必须把候选写成结构化对象，而不是只留在文字里。
- [ ] 资料、计划、训练任何一域被触发后，都必须能回到对话里用一句话解释“为什么现在触发它”。
- [ ] 对话是总调度面，不代表对话能直接治理资料、计划或训练的全部细节。
- [ ] 如果当场一问一答比跳转训练页更自然，Agent 可以先在对话里完成一个微训练回合。
- [ ] 如果需要连续刷卡或沉浸式练习，Agent 必须明确把主战场切回训练页。

#### 对话内微训练与正式训练边界协议

对话内允许微训练，但微训练不是正式训练页的替代品。

`微训练` 只允许以下形式：

- [ ] 一个关键追问
- [ ] 一道即时小题
- [ ] 一次已有卡片的当场调用
- [ ] 一次即时设计的单题卡

必须升级到训练页的条件：

- [ ] 需要连续两题及以上
- [ ] 需要沉浸式刷卡或复习队列调度
- [ ] 需要标准化评分、hint ladder、恢复路线或正式 mastery 更新
- [ ] 需要在项目上下文内形成正式实战卡
- [ ] 需要复盘链路、计划证据链或训练资产恢复

对话内微训练的记账规则：

- [ ] 对话内单次追问或小测默认只记为 `micro_drill_prompt` 和 `conversation_signal`，不直接视为正式训练完成。
- [ ] 只有当微训练被明确升级、采纳或绑定到正式卡片时，才进入正式训练对象链。
- [ ] 对话内调用已有卡片时，必须说明“这是预调用”还是“已切换为正式当前卡”。
- [ ] 微训练失败默认先回到解释或更小问题，不立即当作完整训练失败。
- [ ] 微训练成功默认只证明局部理解，不默认更新完整 mastery。

#### 清晰需求与模糊需求分流协议

用户在工作中可能非常清晰，也可能只模糊表达一个方向。
Trainer 必须同时照顾两类输入。

| 需求清晰度 | 判断标准 | Agent 动作 | 用户反馈 | 禁止行为 |
|---|---|---|---|---|
| 清晰需求 | 有明确对象、目标、约束或期望产物，例如“帮我掌握这个项目的鉴权模块” | 直接确认目标、绑定项目/计划、给下一张训练卡或纯对话答案 | “我按 X 目标推进，下一步是 Y” | 继续问一堆不必要问题 |
| 半清晰需求 | 有方向但缺范围，例如“帮我优化这个项目” | 给 2-3 个可选切入点，推荐一个最小切入点 | “可以从性能/结构/测试切入，我建议先做 X” | 假设用户要全项目重构 |
| 模糊需求 | 只有意图或情绪，例如“这个项目我看不懂”“我想做个工具” | 先诊断场景，生成最小澄清问题或探索卡 | “先确认你是想理解、修改、做 idea，还是学 API” | 强行生成完整计划或大量卡片 |
| 纯对话需求 | 用户明确只是讨论、分析、判断、复盘 | 只进行对话，可给轻量候选但不强制落库 | “我先只分析，不生成训练或改计划” | 把每次对话都变成训练任务 |

必须满足：

- [ ] 模糊需求最多先问 1-3 个关键澄清点，不能把用户带入问卷。
- [ ] 模糊需求也可以先给“默认最小路径”，但必须标注是假设。
- [ ] 清晰需求不能被过度流程化，必须快速进入下一步。
- [ ] 单纯对话可以不写计划、不生成卡片、不进入训练，但可保留为轻量 conversation_note。
- [ ] 当纯对话暴露明显薄弱点时，只能给轻量候选提示，是否进入训练由用户或明确动作触发。

#### 打开文件夹到训练编排的 Agent 路由

Agent 打开文件夹后的路由不能只看当前文件夹，也不能只看总计划。
必须同时看 `当前文件夹类型 + 用户主场景 + 总计划能力缺口 + 当前项目子计划`。

路由顺序：

1. `识别文件夹类型`：空项目、已有工程、算法仓库、模型仓库、idea 文件夹、资料文件夹、不确定。
2. `识别用户主场景`：掌握已有实现、idea 落地、API 掌握、深度优化修改、纯对话。
3. `绑定项目治理对象`：project_id、project_subplan、project_training_lane、resource_scope。
4. `绑定总计划对象`：master_plan_goal、learner_model、dependency_mastery_map、cross_project_gaps。
5. `生成训练编排`：先候选，不自动强推；用户打开训练页时一次只激活一张当前卡。
6. `回流证据`：项目内证据先归项目，跨项目重复能力再进入总计划弹性评估。

必须满足：

- [ ] 空项目中的训练卡必须指导用户自己搭最小场景。
- [ ] 已有项目中的训练卡必须先做理解与风险识别，再做修改。
- [ ] 算法/模型项目必须把理论、实现、复现、迁移拆开训练。
- [ ] idea 项目必须先训练需求边界和最小切片，不直接跳完整工程。
- [ ] 纯对话模式不得强行打开训练页或生成当前卡。

#### 四域互相触发规则

四域之间的触发必须有固定方向和边界，不允许随意跳转或堆功能。

| 触发 | 触发条件 | 生成对象 | 展示位置 | 用户看到的反馈 |
|---|---|---|---|---|
| 对话 -> 资料 | 回答需要来源、API 文档、用户项目材料或现有知识库依据 | resource_query、source_request | 对话轻提示 + 资料页结果 | “这个问题需要资料依据，我会先查资料/需要你补一份资料” |
| 对话 -> 网页资料 | 当前资料库缺依据且问题需要外部来源 | web_research_job、resource_import_candidate | 对话轻提示 + 资料处理状态 | “我会把有用来源下载进资料库，并保留来源和可信度” |
| 对话 -> 项目上下文 | 用户附加项目文件夹、引用工作区或要求“先看这个项目/目录” | project_context_candidate、workspace_understanding_request | 对话轻提示 + 资料/项目摘要 | “我先判断这是什么类型的项目，再决定计划和训练路径” |
| 对话 -> 闪记 | 用户暴露概念、公式、算法、API、参数、返回值或误用不熟 | flash_candidate | 对话轻提示 + 训练候选 | “这个卡点适合做成一张闪记” |
| 对话 -> 实战 | 用户会说但不会做、想练工程实现、错误来自实践边界 | practice_candidate | 对话轻提示 + 训练候选 | “下一步不是继续解释，而是做一张最小实战卡” |
| 对话 -> 即时小测 / 调卡 | 教练判断当场追问、当场抽查或调用已有卡更高效 | micro_drill_prompt、card_invocation | 对话消息本身 | “我先问你一个关键问题，确认你是真懂还是只听懂” |
| 对话 -> 计划 | 用户明确说要改计划、调整目标、复盘完成证据 | proposed_plan_change、evidence_candidate | 对话轻提示 + 计划治理 | “这是计划候选，采纳后才会改正式计划” |
| 用户上传 -> 资料 | 用户上传 HTML/PDF/Markdown/代码文档/API 文档/笔记/网页快照/文件夹 | resource_import_job、resource_record、knowledge_atoms_pending | 资料条目 + 待处理状态 | “资料已进入知识库，深度拆解会排队处理” |
| 网页 -> 资料 | Trainer 浏览网页后判断来源有教学价值 | downloaded_resource、source_metadata、trust_state | 资料条目 + 操作日志 | “这条网页已保存为资料，后续可生成卡片” |
| skill -> 资料 | 资料解析、索引、去重或知识抽取需要专门工具 | skill_manifest、sandbox_run、derived_artifact | 资料沙箱日志 + 条目更新 | “skill 只在资料沙箱运行，已记录影响范围” |
| 资料 -> 闪记 | 资料中存在需要记忆的理论、API、公式、参数、误用 | flash_candidate、knowledge_atom | 资料条目 + 训练候选 | “这份资料已拆出可刷的知识卡” |
| 资料 -> 实战 | 资料中存在可落地 API、工程案例、算法应用或空项目场景 | practice_candidate、scenario_lab | 资料条目 + 训练候选 | “这份资料可以转成最小实战场景” |
| 资料 -> 计划 | 资料支撑当前阶段、证明完成、暴露资料缺口或冲突 | evidence_candidate、resource_trust_state | 资料标注 + 计划证据队列 | “资料可作为证据，但不会自动改计划” |
| 计划 -> 训练 | 当前阶段有理论、实践、依赖或迁移证据缺口 | flash_deck、practice_card、review_goal | 计划轻入口 + 训练当前卡 | “今天这张卡服务当前阶段” |
| 训练 -> 对话 | 用户答错、卡住、提交实战结果或需要解释 | review_prompt、clarification_prompt | 训练反馈 + 对话入口 | “把结果带回对话，我会评估并降级/复盘” |
| 训练 -> 资料 | 训练暴露资料过期、资料缺失、示例不清或误用高频 | resource_annotation、source_gap | 训练反馈 + 资料标注 | “这个错误会反标到资料，后续卡片会避开不可信来源” |
| 训练 -> 计划 | 训练结果形成理论、实践或迁移证据 | plan_evidence_candidate | 训练反馈 + 计划证据队列 | “结果进入证据队列，显式采纳后才影响正式计划” |
| 训练 -> 总计划 | 多项目多次证据足以更新长期能力画像 | mastery_rollup、master_plan_signal | 计划总览 | “这个项目贡献到长期能力 X” |

#### 用户端最短路径设计

用户不应该学习系统结构才能用 Trainer。
用户只需要在任何入口获得一个明确的下一步。

| 用户状态 | 最短路径 | Agent 必须降低的理解成本 |
|---|---|---|
| 我不知道该学什么 | 打开计划 -> 看当前阶段 -> 进入训练当前卡 | 不展示全量路线图，先给今天一张卡 |
| 我不懂一个概念 | 对话提问 -> 得到解释 -> 生成闪记候选 | 不让用户自己决定是否整理知识点 |
| 我忘了 API | 训练刷闪记 -> 答错看提示 -> 进入最小实战 | 不让用户在资料、计划、训练之间来回找入口 |
| 我会说不会做 | 对话或计划 -> 生成实战卡 -> 用户自己实现 -> 带回结果 | 不给成品代码，只给题面、约束和验证 |
| 我资料很多很乱 | 资料搜索/导入 -> 知识原子 -> 卡片候选 | 不展示文件后台，先展示可用知识 |
| 我做失败了 | 训练/对话带回失败 -> 复盘 -> 更小卡或解释 | 不继续加新内容，先恢复节奏 |
| 我想确认掌握了 | 计划/训练 -> 理论 + 实战 + 迁移证据检查 | 不用完成数量代替掌握证据 |

#### 理论与实践统一的掌握证据

Trainer 不能只让用户“听懂”，也不能只让用户“写过一次”。
掌握必须由四类证据共同构成：

| 掌握层级 | 证据 | 主要来源 | 不足时的回退动作 |
|---|---|---|---|
| 理解 | 能用自己的话解释概念、公式、API 语义 | 对话、闪记文本题 | 解释回合、更小概念卡 |
| 记住 | 能在延迟复习中答对关键定义、参数、返回值、误用 | 闪记、复习队列 | 降低卡片粒度、增加提示层级 |
| 做出 | 能在文件、模块或最小场景中亲手实现 | 实战卡、scenario_lab、用户带回验证 | 更小实战卡、API 提示、资料回查 |
| 迁移 | 能跨项目或新场景使用同一知识/API | 项目子计划、总计划 rollup、迁移实战 | 生成跨项目迁移题或真实项目落点 |

必须满足：

- [ ] 闪记答对只能证明记忆或理解，不能直接证明工程能力。
- [ ] 实战通过只能证明当前场景能力，不能直接证明跨项目迁移。
- [ ] 迁移掌握必须来自不同项目、不同上下文或明确变形场景。
- [ ] 总计划评估必须综合四层证据，不能只统计卡片数量或任务完成数。

#### 对话反馈机制

对话不是训练页，但对话必须是闭环的反馈入口。

对话回复必须能出现以下轻量反馈：

- [ ] `我识别到一个理论卡点，已生成闪记候选`
- [ ] `这更适合变成一张实战卡，题目是...`
- [ ] `这条资料可以作为当前阶段证据，但不会自动改计划`
- [ ] `你这次失败暴露的是参数/返回值/边界条件问题，我会压成卡片`
- [ ] `你已经连续答对，可以进入实战验证`
- [ ] `这次实战结果可以进入项目子计划证据`

对话回复不能：

- [ ] 把完整训练工作台塞进消息
- [ ] 长篇解释所有系统状态
- [ ] 未经用户显式要求改正式计划
- [ ] 替用户写代码完成实战

#### 最强教练 Agent 的判定标准

Trainer 只有在以下能力同时成立时，才算“强大的教练 Agent 工具”：

- [ ] 能在对话中发现用户真实薄弱点，而不是只回答字面问题
- [ ] 能把资料转成可训练知识，而不是只摘要
- [ ] 能把计划转成当天可做的训练卡，而不是只展示路线
- [ ] 能把训练结果转成计划证据、复习队列和资料标注
- [ ] 能跨项目维护同一个用户能力画像
- [ ] 能区分理论不会、记忆不稳、实践不会、迁移不会
- [ ] 能在用户卡住时降低粒度，而不是继续推进新内容
- [ ] 能在用户已经掌握时提高难度或迁移场景
- [ ] 能保持 coach-only，不替用户动手
- [ ] 能让用户每天低成本打开侧栏就知道“现在刷哪张卡、为什么、做完回哪里”

### 13.17 全量使用场景矩阵

Trainer 必须针对所有核心使用场景设计闭环，而不是只覆盖单一聊天或单一训练场景。
每个场景都必须回答：用户从哪里进入、Agent 判断什么、触发什么功能、写入什么对象、如何反馈给用户、禁止什么越界。

| 场景 | 用户入口 | Agent 判断 | 触发动作 | 写入对象 | 用户反馈 | 禁止行为 |
|---|---|---|---|---|---|---|
| 用户想学一个新技术 | 对话 | 是否有长期目标、项目落点、资料来源 | 建议计划阶段、资料检索、闪记卡组、最小实战 | 总计划证据、项目子计划候选、训练候选 | “先看计划阶段，再刷理论卡，最后做最小实战” | 直接给大段教程后结束 |
| 用户打开一个文件夹 | 任意视图 | 是空项目、已有工程、算法/模型仓库、idea 文件夹、资料文件夹还是不确定 | project_context_classification、绑定项目子计划候选 | project_context、project_subplan_candidate、project_training_lane | “我先判断这是哪类项目，再决定训练路径” | 默认从零开始或沿用旧项目上下文 |
| 用户想掌握已有项目 | 对话/计划/训练 | 是项目结构理解、关键模块理解、修改能力还是迁移能力 | 项目地图卡、源码走读卡、局部实战卡、复盘卡 | project_understanding、practice_card、plan_evidence_candidate | “先读懂结构，再练一个最小修改点” | 只总结 README 或直接改代码 |
| 用户想掌握算法实现 | 对话/资料/训练 | 是理论、复杂度、边界、实现步骤还是工程应用缺口 | 算法闪记、步骤排序卡、实现走读实战、变体迁移卡 | algorithm_mastery、flash_deck、practice_review | “先确认理论和边界，再走读实现” | 只给算法概念不连接代码 |
| 用户想掌握模型实现 | 对话/资料/训练 | 是模型结构、数据流、训练流程、评估或调参缺口 | 模型结构卡、数据流卡、训练流程实战、复现实战 | model_implementation_mastery、scenario_lab、plan_evidence_candidate | “先掌握模型路径，再复现一个最小训练/推理动作” | 只讲论文或只跑结果 |
| 用户想把 idea 落成代码 | 对话/计划 | 需求是否清晰、边界是否明确、是否有最小切片 | 需求澄清卡、架构取舍卡、最小切片实战卡、验证卡 | idea_plan_candidate、project_subplan_candidate、practice_card | “我不会直接写完整项目，先帮你切出可实现的一刀” | 一次性生成完整项目代码 |
| 用户想在现有项目做深度优化/修改 | 对话/计划/训练 | 是性能、结构、可维护性、测试、架构还是业务修改 | 现状理解卡、风险卡、测试指标卡、修改实战卡、回归复盘 | project_change_candidate、risk_evidence、practice_review | “先确认现状和验证标准，再让你自己做最小修改” | 跳过理解和测试直接给补丁 |
| 用户只是工作中单纯对话 | 对话 | 是否只是讨论、判断、解释、比较、复盘，不需要生成训练对象 | 纯回答、轻量候选提示、可选 conversation_note | conversation_note、optional_candidate | “我先只讨论，不生成卡片或改计划” | 每次对话都强行转训练 |
| 用户附带项目文件夹但只想先聊聊 | 对话 | 是先理解项目、先分类，还是已经准备进入训练 | 项目 first-look、资料入库、可选项目理解候选 | project_context_candidate、resource_record、workspace_understanding_request | “我先判断这是什么项目，再决定是否进计划或训练” | 直接强推计划或训练 |
| 用户上传资料但暂时只想理解 | 对话/资料 | 是先解释重点、先拆知识点，还是先绑定当前项目 | 资料入库、重点解释、轻量候选 | resource_record、knowledge_atoms_pending、optional_candidate | “资料先入库，我先讲重点，后续可再转训练或计划证据” | 只提示上传成功，不说明后续用途 |
| 用户把训练结果带回对话 | 对话/训练 | 是通过、部分通过、误解、迁移不足还是资料问题 | review、计划证据候选、闪记或更小实战候选 | review_artifact、plan_evidence_candidate、flash_candidate、practice_candidate | “我先评估这次结果，再决定复盘、降级还是纳入计划证据” | 只说继续下一题 |
| 用户需求非常清晰 | 对话/计划/训练 | 对象、目标、约束和产物是否明确 | 直接绑定场景，给下一步或当前卡 | task_intent、active_card_candidate、next_step_hint | “按这个目标推进，下一步是...” | 过度追问拖慢用户 |
| 用户需求很模糊 | 对话 | 缺目标、缺对象、缺范围还是缺验收 | 1-3 个澄清点、默认最小路径、诊断卡 | clarification_state、assumption_path、conversation_signal | “我先按最小假设推进，你也可以选另一个方向” | 强行制定完整计划 |
| 用户问一个概念 | 对话 | 是普通解释还是理论薄弱点 | 解释 + 生成闪记候选 | conversation_gap、flash_candidate | “这个概念我会压成一张闪记” | 只解释不沉淀 |
| 教练判断需要当场验证理解 | 对话 | 是继续解释更好，还是一道小题/一个追问更快确认掌握 | 发起微型问答、调用已有卡或即时设计一张卡 | micro_drill_prompt、card_invocation、flash_candidate | “我先问你一个关键问题，确认你是否真的掌握了” | 把整套训练工作台塞进消息 |
| 用户想在对话里直接来一题 | 对话/训练 | 是临时抽查、当前卡调用，还是已经适合进入沉浸训练 | 调用现有卡片摘要、生成即时卡或引导跳训练页 | card_invocation、attempt_candidate、active_card_candidate | “先在这里做一道，连续刷卡去训练页” | 在对话里展开卡片墙 |
| 用户问 API 用法 | 对话/资料 | 是否需要文档依据、参数/返回值是否薄弱 | 资料检索、API 闪记、最小实战 | resource_knowledge、flash_candidate、practice_candidate | “先记 API 语义，再做最小场景” | 给完整代码替用户实现 |
| 用户看不懂错误 | 对话 | 是概念错、API 错、工程边界错还是验证错 | 解释、误用闪记、更小实战卡 | practice_feedback、flash_candidate、review_artifact | “错误会回收到卡片和复盘” | 直接改代码 |
| 用户上传文档 | 资料 | 是否可信、是否过期、可拆哪些知识点，是否绑定当前项目 | 索引、知识原子、闪记候选、实战候选 | global_resource_library、knowledge_atoms、card_candidates、project_resource_links | “这份资料已进入全局资料库，并标注当前项目用途” | 只存文件不拆解，或按项目复制成孤岛 |
| 用户上传 API 文档 | 资料 | 核心 API、参数、返回值、误用、场景、版本差异 | API 卡、参数卡、返回值卡、误用卡、最小实战 | dependency_mastery、flash_candidate、practice_candidate、resource_record | “API 会进入依赖掌握图和跨项目资料库” | 只摘要文档 |
| 用户上传项目资料 | 资料 | 与当前项目子计划和总计划的关系 | 项目知识条目、计划证据候选、实战卡候选 | resource_record、project_resource_links、plan_evidence_candidate | “这份资料服务哪个阶段已标注，正文仍属于全局资料库” | 资料与计划断开 |
| 用户要求 Trainer 查资料 | 对话/资料 | 当前资料库是否已有依据，是否需要网页检索或下载 | 全局资料检索、网页浏览、下载到沙箱、可信度标注 | web_research_job、downloaded_resource、resource_operation_log | “我会把有用来源保存到资料库，后续用于卡片和计划证据” | 只在对话里临时引用，不入库不可追踪 |
| Trainer 需要 skill 管理资料 | 资料/设置 | 是否已有安全 manifest、是否只作用于资料沙箱、是否需要网络或命令权限 | 下载/启用受控 skill、隔离运行、写操作日志、生成派生资料 | skill_manifest、sandbox_run_log、derived_artifacts | “这个 skill 只处理资料沙箱，影响范围如下” | skill 越权读取密钥或写用户项目 |
| 用户打开计划 | 计划 | 当前阶段、证据缺口、训练缺口 | 展示总计划/子计划/证据，不自动训练 | none 或 explicit_plan_action | “当前应该补哪些训练证据” | 浏览即改计划 |
| 用户要求改计划 | 对话/计划 | 是否明确进入计划回合 | 生成计划变更候选、等待显式采纳 | proposed_plan_change | “这是候选，采纳后才改正式计划” | 普通对话暗改计划 |
| 当前计划阶段需要理论 | 计划 -> 训练 | 哪些理论是阶段前置条件 | 生成闪记卡组 | flash_deck、plan_link | “这些理论卡服务当前阶段” | 随机刷无关题 |
| 当前计划阶段需要实践 | 计划 -> 训练 | 哪个最小工程动作能证明能力 | 生成实战卡 | practice_card、expected_evidence | “这张代码题用于证明阶段能力” | 给任务标题无验收 |
| 用户打开训练 | 训练 | 当前最该练实战还是闪记 | 展示唯一当前卡 | active_card | “当前只需完成这一张” | 一屏卡片墙 |
| 用户答错闪记 | 训练 | 是不会、模糊、误解还是记忆失败 | 错因反馈、更小卡、解释回合或实战验证 | flash_attempt、review_queue | “错因是什么，下一张怎么补” | 只标错不解释 |
| 用户答对闪记 | 训练 | 是单次记住还是稳定掌握 | 调整复习间隔、生成迁移题或实战卡 | mastery_delta、review_schedule | “下一次何时复习 / 是否进入实战” | 一次答对标记掌握 |
| 用户完成实战 | 训练 -> 对话 | 是否符合标准答案形态和验证方法 | 评估、复盘、计划证据候选、闪记补漏 | practice_review、evidence_item、flash_candidate | “哪里通过、哪里要补、回流到哪里” | 自动改正式计划 |
| 用户实战失败 | 训练 -> 对话 | 根因是理论、API、参数、边界、验证还是场景 | 生成更小实战、闪记、资料标注 | review_artifact、flash_candidate、resource_annotation | “先退到哪张卡或哪个最小场景” | 继续推更难题 |
| 用户切换项目 | 任意视图 | 当前项目子计划与总计划关系 | 切换项目上下文，保持统一 Agent 画像 | project_subplan_context、master_plan_rollup | “当前项目贡献哪个长期能力” | 把 Trainer 当新 Agent |
| 用户长期复习 | 训练 | 哪些理论/API/误用到期 | 复习队列、闪记卡、迁移题 | review_queue、flash_deck | “今天先刷哪些卡，为什么” | 只按时间随机复习 |
| 用户想证明学会了 | 计划/训练 | 是否有理论、实战、迁移三类证据 | 生成评估任务或迁移实战 | mastery_evidence、transfer_candidate | “还缺哪类证据才能算掌握” | 用完成数量代替能力 |
| 用户只想快速推进 | 对话/训练 | 是否可以压缩解释但保持 coach-only | 给最小下一步、验证标准、回带要求 | conversation_hint、practice_candidate | “先做这一刀，做完带结果回来” | 为了快而代写 |
| 用户卡住很久 | 对话/训练 | 是否需要降级粒度或恢复节奏 | 更小闪记、更小实战、解释回合、暂停计划推进 | recovery_route、review_artifact | “先退到这个最小动作” | 继续加新内容 |
| 用户资料过期或冲突 | 资料/训练 | 资料可信度、新鲜度是否不足 | 标注待复查、触发重新检索、暂停相关卡 | resource_trust_state、card_blocker | “这条资料暂不用于训练” | 用过期资料出题 |

### 13.18 旧文档回收的异常、恢复与发布使用场景矩阵

以下场景来自保留状态矩阵、架构、验证、性能与开发流程文档。它们不能覆盖本主清单，但必须被吸收到主清单，避免实现只覆盖顺流程学习。

| 场景 | 用户入口 | Agent / 系统判断 | 触发动作 | 写入对象 | 用户反馈 | 禁止行为 |
|---|---|---|---|---|---|---|
| 计划证据进入待治理队列 | 训练/资料/对话 -> 计划 | 是训练结果、资料证据、对话目标还是复盘结论 | 生成 pending evidence，等待 review/defer/adopt | plan_evidence_candidate、evidence_source_chain | “这条证据可用于计划，但不会自动改计划” | 直接写正式计划 |
| 用户 review / defer 证据 | 计划 | 证据是否可信、是否属于当前项目、是否影响总计划 | 更新证据治理状态、保留审计轨迹 | evidence_review_state、audit_event | “已审阅/已延后，原因和影响范围如下” | 把 defer 当删除 |
| 用户采纳计划变化 | 计划 | 是否已 review、是否有 dry-run、是否存在冻结/冲突 | 正式采纳、写历史、回流总计划评估 | formal_plan_history、project_subplan_history、master_rollup | “采纳后变化是这些字段” | 未预览直接变更 |
| 用户恢复计划历史 | 计划 | 恢复目标是 formal、subplan 还是 master compare-only | 顺序恢复 allowed 步骤，失败即停 | restore_orchestration_result | “这几步已恢复，后续因失败/阻塞跳过” | master 历史直接回滚 |
| 用户打开训练恢复路线 | 训练 | 哪些训练资产有可恢复快照 | dry-run 展示 dependency / scenario / theory / review 恢复步骤 | training_restore_preview | “这只是预演，不会改变训练资产” | 恢复路线默认压过当前卡片 |
| 用户执行训练资产恢复 | 训练 | 依赖图、最小场景、理论题、复盘工件是否允许恢复 | 顺序执行恢复，选择最新可恢复快照 | dependency_skill_map_history、scenario_lab_history、theory_drill_history、review_artifact_history | “恢复后当前卡片为什么变化” | 误恢复旧版本或丢失其它依赖 |
| 复习队列到期 | 训练 | 到期项是否阻塞当前计划阶段 | 生成唯一当前闪记或迁移题 | review_queue、active_card | “今天先刷这一张，因为它阻塞当前阶段” | 复习队列全量列表压首屏 |
| 没有真实工程场景 | 训练 | 是否可在空项目构建最小场景 | 生成 scenario_lab 实战卡，要求用户自己创建/修改文件 | scenario_lab、practice_card | “请你自己在这个最小文件中实现，Trainer 只给题面和检查方式” | Trainer 创建文件或写代码 |
| 资料沙箱治理 | 资料 | 用户是在理解来源、对比内容、整理资料、处理过期资料还是让 Trainer 管理资料 | 预览、风险标注、派生资料生成、归档、重命名、索引更新、受控 skill 运行 | resource_preview_state、resource_annotation、resource_operation_log、derived_artifact | “这是资料沙箱操作，不会写入你的工程代码，所有变化可追踪可回滚” | 无日志改写、硬删、越权写项目、webview 禁用但 API 仍能越权 |
| 大批量资料导入 | 资料 | 批量数量、大小、索引成本、是否影响热路径 | 先写 metadata，深处理排队，可取消 | resource_import_job、knowledge_atoms_pending | “资料已可搜索，深度拆解仍在队列中” | 等全部处理完才可用 |
| provider 配置失败 | 设置 | key、base URL、model、网络、限流或服务端错误 | 展示最短修复路径、保留安全日志 | provider_status、diagnostic_event | “当前不可用的原因是 X，下一步只需改 Y” | 泄露 API key 或把错误丢给用户猜 |
| sidecar 未启动或健康检查失败 | 设置/任意视图 | sidecar 进程、端口、health、依赖环境是否异常 | 重试连接、显示日志入口、降级只读 | sidecar_status、runtime_recovery_state | “Trainer 暂时只能查看已有内容，恢复后会重新合并状态” | 白屏或丢失用户训练状态 |
| workspace trust / 权限不足 | 任意视图 | 当前是否允许读取上下文、打开文件、执行命令 | 降级为解释、题面、手动步骤 | permission_state、safe_mode_event | “当前权限不足，我只给指导，不碰项目文件” | 绕过 VS Code 权限边界 |
| 长对话 / 流式回复 | 对话 | 热路径是否被 markdown、历史、重能力拖慢 | recent window、懒加载、chunk 合并 | performance_marker | “回复继续流式输出，历史可按需展开” | 每次渲染全量历史 |
| 大资料库搜索 | 资料 | 搜索是否影响输入流畅度 | metadata-first、detail-on-demand、deferred search | resource_search_state | “先返回匹配条目，详情按需展开” | 默认水合全部正文和沙箱 |
| 重新打开 VS Code / 切换项目 | 任意视图 | 全局身份、项目子计划、workspaceState、SQLite/Qdrant 是否一致 | runtime rehydrate、项目绑定、状态合并 | trainer_identity、project_context、workbench_snapshot | “已切到当前项目，哪些内容来自总计划，哪些来自本项目” | 把上个项目卡片当当前项目 |
| 源码态和打包态不一致 | 发布/验证 | bundled server、prompt、provider、resources、routers 是否同步 | hash / py_compile / smoke / package verification | release_readiness_evidence | “源码态与 VS Code 扩展态一致性证据如下” | 只测源码不测 VS Code 扩展 |
| 性能声称完成 | 发布/验证 | 是否有 build size、输出通道或回归测试证据 | 记录性能证据并绑定验收 | perf_evidence、verification_record | “这个优化有这些可复现证据” | 无证据宣称更快 |

### 13.19 场景触发优先级

当多个场景同时出现时，Agent 必须按优先级选择，不允许随机响应。

优先级从高到低：

1. `安全与边界`：不能替用户改代码、不能暗改计划、不能使用不可信资料。
2. `运行可用性`：provider、sidecar、权限、workspace trust 异常时先给降级和恢复路径。
3. `用户当前阻塞`：用户卡住、验证失败、概念不清时先恢复。
4. `计划当前阶段`：当前训练必须服务计划阶段。
5. `资料可信来源`：需要知识依据时先检索和引用资料。
6. `理论薄弱点`：理论不稳先闪记或解释。
7. `实践薄弱点`：能说不会做时先实战卡。
8. `复习节奏`：到期但不阻塞当前阶段的复习排后。
9. `迁移提升`：掌握稳定后再做跨项目迁移。
10. `发布与性能`：完成声明必须在功能闭环之后补齐证据。

### 13.20 视图间反馈文案规范

为了让用户感到这是一个统一 Agent，而不是多个页面跳转，跨视图反馈必须统一。

推荐反馈句式：

- `我把这个卡点记录成闪记候选，因为它影响当前计划阶段。`
- `这份资料可以拆成 3 个知识点，其中 1 个适合闪记，1 个适合实战。`
- `这张实战卡来自当前项目子计划，完成后会进入计划证据队列。`
- `你这次答错不是坏事，它暴露的是返回值语义，我会降低成更小卡。`
- `你已经连续掌握这个知识点，下一步应该进入真实工程验证。`
- `这条证据不会自动改计划，只有你显式采纳后才会影响正式计划。`

禁止反馈句式：

- [ ] `我已经帮你改好了`
- [ ] `我直接更新了你的计划`
- [ ] `随便练一道`
- [ ] `资料已上传完成` 但不说明如何用于训练或计划
- [ ] `你已经掌握了` 但没有证据链
- [ ] `这是答案，直接复制`

### 13.21 统一事件账本理论

Trainer 不能靠 UI 状态和零散字段维持长期闭环。
所有重要变化都必须进入统一事件账本，才能支持审计、恢复、跨项目汇总和状态重建。

事件账本不是用户要看的主界面，而是实现层的事实来源。

必须有的事件类型：

- [ ] `conversation_signal_recorded`：对话中识别到目标、卡点、误解、计划意图或资料需求。
- [ ] `coach_visible_status_published`：把 Trainer 当前查资料、绑定项目、对齐计划、编排训练或评估结果的轻量可见状态回写到会话层。
- [ ] `conversation_micro_drill_issued`：教练在对话中发起即时追问、小测或单题抽查。
- [ ] `conversation_card_invoked`：教练在对话中调用已有卡片，或实时设计一张当场可用卡片。
- [ ] `project_context_classified`：打开文件夹后完成项目类型与项目治理对象绑定。
- [ ] `resource_imported`：用户上传或 Trainer 下载资料进入全局资料库。
- [ ] `resource_sandbox_operation_applied`：资料沙箱发生整理、改写、归档、索引、skill 运行或回滚。
- [ ] `knowledge_atom_extracted`：资料、对话或实战反馈被拆成知识原子。
- [ ] `card_candidate_created`：生成闪记或实战候选卡。
- [ ] `active_card_selected`：卡片路由器选择当前唯一训练卡。
- [ ] `flash_attempt_recorded`：用户完成闪记作答。
- [ ] `practice_submission_recorded`：用户带回实战实现说明、测试输出、错误或截图。
- [ ] `practice_review_created`：Trainer 评估实战结果。
- [ ] `review_queue_updated`：复习队列更新。
- [ ] `dependency_mastery_updated`：依赖/API 掌握图更新。
- [ ] `plan_evidence_created`：对话、资料或训练结果进入计划证据队列。
- [ ] `plan_change_proposed`：生成计划变更候选。
- [ ] `plan_change_accepted`：用户显式采纳计划变化。
- [ ] `master_rollup_updated`：项目证据汇总到总计划能力画像。
- [ ] `runtime_degraded`：provider、sidecar、权限、平台或依赖异常导致降级。

每个事件必须至少包含：

- [ ] `event_id`
- [ ] `event_type`
- [ ] `occurred_at`
- [ ] `actor`：user / trainer / system / skill
- [ ] `scope`：global / project / resource_sandbox / training / plan
- [ ] `project_id`：可为空，但如果事件发生在项目上下文内必须存在
- [ ] `source_chain`
- [ ] `payload_ref`
- [ ] `before_state_ref`
- [ ] `after_state_ref`
- [ ] `reversibility`：reversible / append_only / irreversible
- [ ] `audit_note`

事件账本硬规则：

- [ ] 正式计划、掌握度、资料沙箱、训练队列的变化必须能从事件重建。
- [ ] 普通 UI 展开/折叠不进入核心事件账本，避免噪声。
- [ ] 任何无法解释来源的事件不能改变核心对象。
- [ ] 事件失败必须记录失败原因和是否可重试。
- [ ] 事件账本不等于聊天记录，不能用自然语言聊天替代结构化事件。

### 13.22 核心对象不变量

不变量是实现时不能被任何功能打破的底线。
只要某个 PR、接口或模型输出破坏任一不变量，即使 UI 看起来正确，也必须判为失败。

全局不变量：

- [ ] 一个用户只有一个 `trainer_identity`。
- [ ] 一个用户只有一个跨项目 `master_plan`。
- [ ] 每个项目最多一个当前正式 `project_subplan`，历史可以多版本。
- [ ] 资料正文属于 `global_resource_library`，项目只保存绑定关系。
- [ ] `training_card` 必须有 `source_chain / why_now / target_skill / feedback_targets`。
- [ ] `plan_evidence` 在显式采纳前不能变成正式计划变化。
- [ ] `mastery_score` 不能由单次答题直接判定为掌握。
- [ ] `practice_card` 不能让 Trainer 替用户写项目代码。
- [ ] `resource_sandbox` 写操作不能逃逸沙箱根目录。
- [ ] `skill` 不能读取 SecretStorage，不能写用户工程空间。

视图不变量：

- [ ] 对话页不能承载完整训练、资料或计划工作台。
- [ ] 计划页不能有普通聊天输入。
- [ ] 资料页不能默认三栏并排，不能变成无审计文件管理器。
- [ ] 训练页首屏只能有一个当前主训练对象。
- [ ] 设置页不能承载学习业务内容。
- [ ] 五个一级视图不能新增第六个一级视图来逃避职责边界。

数据不变量：

- [ ] 所有跨对象引用必须可解析或标记为 orphaned，不得静默丢失。
- [ ] 删除必须优先归档或回收站，核心证据不得硬删。
- [ ] 任何 `formal_*` 对象必须有历史记录。
- [ ] 任何 `candidate_*` 对象必须有来源和生成原因。
- [ ] 中英双语知识节点必须共享 mastery，不得重复计数。
- [ ] 同一资料跨项目复用时不得复制成多个不一致正文。

### 13.23 Agent 自治权限分级

Trainer 必须有高度自主性，但自主性必须分级。
“能自己做”和“能碰用户工程”是两件事，不能混淆。

权限等级固定为：

| 等级 | 名称 | Trainer 可做 | 需要用户显式动作 | 禁止 |
|---|---|---|---|---|
| L0 | 只读解释 | 回答、解释、总结、澄清、生成轻量候选 | 无 | 写任何持久对象 |
| L1 | 证据记录 | 记录 conversation_signal、候选卡、资料查询需求 | 采纳计划、执行实战 | 改正式计划、改项目代码 |
| L2 | 资料沙箱自治 | 上传/下载/整理/解析/索引/归档资料，运行受控 skill | 删除不可恢复内容、启用高风险 skill | 写用户工程空间、读取密钥 |
| L3 | 训练治理 | 选择当前卡、更新复习队列、生成评估和掌握度增量 | 用户提交答案或实战结果 | 代写实战代码 |
| L4 | 计划候选治理 | 生成计划证据、计划变更候选、dry-run | 正式采纳计划变化 | 暗改正式计划 |
| L5 | 用户工程动作 | 打开文件定位、提示用户自己创建/修改/运行 | 用户在 VS Code 中亲自执行 | Trainer 自动创建/修改/删除项目文件 |

权限升级规则：

- [ ] 默认从最低权限开始。
- [ ] 每次跨等级动作必须有明确触发条件和用户可理解反馈。
- [ ] L2 资料沙箱自治不等于 L5 用户工程动作权限。
- [ ] L4 计划候选永远不能自动升级为正式计划变化。
- [ ] provider key、SecretStorage、系统凭据永远不能被资料 skill 读取。
- [ ] 高风险 skill、外部网络下载、批量删除、不可逆归档必须有隔离、预览或显式确认机制。

### 13.24 失败恢复矩阵

Trainer 不是只在顺利路径下工作。
失败恢复必须设计在主流程里，不能等实现时临时补弹窗。

| 失败类型 | 典型表现 | Trainer 必须做 | 写入对象 | 禁止 |
|---|---|---|---|---|
| 用户需求不清 | “我想学这个”“帮我优化” | 给 1-3 个澄清点或默认最小路径 | clarification_state | 直接生成大计划 |
| 资料不可信 | 来源过期、冲突、无版本 | 标注 trust_state，暂停相关卡 | resource_annotation、card_blocker | 用不可信资料出题 |
| 资料解析失败 | PDF 无文本层、HTML 抓取失败 | metadata 先可用，深解析排队或降级 | resource_import_job | 整个资料不可见 |
| skill 失败 | 平台不支持、依赖缺失、越权被拦截 | 记录 sandbox_run_log，给替代处理 | skill_run_result | 静默失败或越权重试 |
| 训练答错 | 概念错、API 错、边界错 | 错因反馈，生成更小卡或解释 | flash_attempt、review_queue | 只标红不解释 |
| 实战失败 | 测试失败、实现偏离、无法验证 | 评估失败点，降级实战或生成闪记 | practice_review | 直接替用户改代码 |
| 计划证据冲突 | 证据弱、项目不匹配、影响总计划 | 放入待治理队列，支持 defer / review | evidence_queue | 直接覆盖正式计划 |
| 跨项目混淆 | 上个项目卡片出现在当前项目 | 重绑定 project_context，冻结可疑卡 | project_context_event | 当作正常训练继续 |
| sidecar/provider 故障 | health 失败、模型不可用 | 降级查看已有内容，给恢复路径 | runtime_degraded | 伪造评估或白屏 |
| 跨系统差异 | 路径、权限、编码、shell 差异 | 平台诊断，降级或给替代路径 | platform_diagnostic | 只在当前系统硬跑 |
| 双语误判 | 用户中文答英文题被判错 | 语言识别和语义复评 | answer_review_event | 按字符串误判 |

恢复硬规则：

- [ ] 失败不应该让用户丢失当前训练上下文。
- [ ] 失败必须告诉用户“还能做什么”，不能只报错。
- [ ] 失败恢复不能绕过 coach-only 边界。
- [ ] 恢复动作不能暗改计划。
- [ ] 恢复后的下一张卡必须解释为什么变化。

### 13.25 实施追踪矩阵

每个从清单落地到代码的功能，都必须有追踪矩阵。
没有追踪矩阵，就无法判断“实现了”还是“只是看起来像”。

每个实施项必须填写：

- [ ] `checklist_ids`：对应本清单编号。
- [ ] `user_scenario`：服务哪个真实场景。
- [ ] `domain_objects`：涉及哪些核心对象。
- [ ] `state_transitions`：触发哪些状态变化。
- [ ] `events`：写入哪些事件。
- [ ] `invariants_checked`：检查哪些不变量。
- [ ] `permissions`：涉及哪个自治权限等级。
- [ ] `ui_entry`：在哪个一级视图出现。
- [ ] `server_entry`：哪个服务或 API 负责决策。
- [ ] `shared_contract`：哪些共享类型必须存在。
- [ ] `failure_recovery`：失败后如何恢复。
- [ ] `tests`：单元、集成、UI、跨系统、双语或手动验收。

判定规则：

- [ ] 没有状态变化，不能声称闭环。
- [ ] 没有事件，不能声称可恢复或可审计。
- [ ] 没有不变量检查，不能声称安全。
- [ ] 没有 UI 入口，不能声称用户可用。
- [ ] 没有服务端决策，不能把核心逻辑塞进 webview。
- [ ] 没有测试或验收脚本，不能进入 `已实现`。

### 13.26 单一事实源矩阵

Trainer 不能让同一个核心对象在 webview、extension、server、mock 数据和模型回复中各自生成一份。
每个对象必须有一个权威事实源，其他层只能投影、缓存或提交事件。

| 对象 | 权威事实源 | 可缓存层 | 允许写入方 | 禁止 |
|---|---|---|---|---|
| `trainer_identity` | server / persisted profile | extension、webview | 初始化和迁移流程 | 按项目重新创建 |
| `master_plan` | server / plan store | webview | 显式计划采纳事件 | 普通对话或训练直接写 |
| `project_subplan` | server / plan store | webview、extension | 项目治理事件、显式采纳 | 切换文件夹时覆盖 |
| `global_resource_library` | server / resource store | webview | resource_import / sandbox_operation | 项目视图复制正文 |
| `resource_sandbox` | server + extension path guard | webview 只读投影 | 受控 sandbox operation | webview 直接写真实路径 |
| `knowledge_atom` | server / extraction pipeline | webview | resource/conversation/practice extraction | 模型回复临时生成后不入库 |
| `training_card` | server / card router | webview | card_generation_router | webview 本地拼题 |
| `active_card` | server / card router | webview | active_card_selected event | 前端随机切卡 |
| `attempt_record` | server / training store | webview optimistic cache | 用户提交作答事件 | 本地评分后直接改 mastery |
| `mastery_score` | server / mastery engine | webview | evidence-based mastery update | 单次答对直接掌握 |
| `evidence_item` | server / evidence graph | webview | evidence creation / review events | UI 勾选直接改正式计划 |
| `provider_secret` | VS Code SecretStorage | none | extension secret APIs | server、webview、skill 读取 |

硬规则：

- [ ] webview 可以乐观显示，但必须能被 server 快照纠正。
- [ ] mock 数据只能服务开发预览，不能被当成完成证据。
- [ ] 模型输出必须转成结构化对象后才进入事实源。
- [ ] extension 只负责宿主边界和路径权限，不负责教学决策事实源。
- [ ] 任何本地缓存都必须有版本、来源和失效策略。

### 13.27 当前训练卡路由算法

训练页一次只能显示一张当前卡，所以 `active_card` 的选择必须可解释。
不能因为“看起来有卡”就随机展示。

候选卡评分至少包含：

- [ ] `plan_relevance`：是否服务当前总计划或项目子计划阶段。
- [ ] `blocking_power`：是否解除用户当前阻塞。
- [ ] `evidence_gap`：是否补足理论、实践、验证或迁移证据缺口。
- [ ] `recency_need`：是否到期复习或近期重复错误。
- [ ] `resource_trust`：来源资料是否可信且新鲜。
- [ ] `difficulty_fit`：难度是否适合用户当前掌握状态。
- [ ] `project_fit`：是否属于当前 project_training_lane。
- [ ] `transfer_value`：是否能提升跨项目迁移能力。
- [ ] `recovery_priority`：是否是失败后的恢复卡。

阻断条件必须优先于评分：

- [ ] 来源资料不可信或过期未标注时，不得激活相关卡。
- [ ] 实战卡缺少题面、交付物、验证方法或 coach-only 边界时，不得激活。
- [ ] 闪记卡缺少标准答案、rubric 或 hint_ladder 时，不得激活。
- [ ] 当前项目上下文不确定时，不得激活项目修改类实战卡。
- [ ] 用户明确处于纯对话模式时，不得强制激活训练卡。
- [ ] provider / sidecar 不足以评估时，不得伪造当前卡评估。

active_card 输出必须包含：

- [ ] `selected_card_id`
- [ ] `selection_score`
- [ ] `why_this_card`
- [ ] `why_not_others`
- [ ] `blocked_candidates`
- [ ] `fallback_action`
- [ ] `next_after_completion`

### 13.28 掌握度评估模型

掌握度不是完成率。
Trainer 必须用证据模型评估用户是否真正掌握。

掌握度必须分层：

| 层级 | 证据 | 不能替代 |
|---|---|---|
| 理解 | 用户能解释概念、公式、API 语义和边界 | 看过资料 |
| 记忆 | 用户能在弱提示下回忆核心用法、参数、返回值 | 刚看完答案 |
| 做出 | 用户能在最小场景或项目文件中亲手实现并验证 | 复制示例 |
| 迁移 | 用户能在新项目、新模块或新问题中识别落点并应用 | 同题重复做对 |

mastery 更新必须遵守：

- [ ] 单次答对只能增加短期信心，不能直接标记掌握。
- [ ] 单次实战通过只能证明当前场景可做，不能证明迁移。
- [ ] 重复答错必须降低粒度，不能只降低分数。
- [ ] 资料阅读只能产生理解候选，不能直接提高 mastery。
- [ ] 计划证据必须区分强证据、弱证据、冲突证据和待复核证据。
- [ ] 跨项目成功迁移才允许显著提升 transfer mastery。
- [ ] `transferable` 必须由显式迁移证据对象驱动，至少包含 `source_workspace_id`、`target_workspace_id`、`verified_result`，且 `source != target`。
- [ ] `mark_transferable` 只能表示“记录迁移证据并请求教练判定”，不能是前端直接升级 mastery 的一键动作。
- [ ] 若迁移证据不足，系统必须保留或回落到 `applied`，并写出明确 `latest_transfer_blocked_reason`。

mastery 输出必须解释：

- [ ] 当前分数或等级来自哪些证据。
- [ ] 还缺哪类证据。
- [ ] 下一张卡为什么能补这个缺口。
- [ ] 哪些证据来自当前项目，哪些来自跨项目历史。

### 13.29 跨视图一致性协议

五个一级视图展示同一个对象时，必须语义一致。
不同视图可以有不同密度，但不能有不同事实。

一致性规则：

- [ ] 对话里提示“已生成卡片候选”，训练页必须能找到同一候选或解释被阻断原因。
- [ ] 资料页显示资料过期，训练页相关卡必须暂停或标注风险。
- [ ] 训练完成生成计划证据，计划页必须显示待治理证据而不是直接更新正式计划。
- [ ] 计划页当前阶段变化后，训练卡路由必须重新解释 why_now。
- [ ] 切换项目后，对话、计划、资料过滤、训练当前卡必须同步到同一 project_context。
- [ ] 切换项目或用新 `workspace_id` 重绑旧 session 后，资料页不得保留旧项目的 `selectedResourceDetail`、旧选中资源或旧沙箱选中路径；若当前项目不存在该资源，必须回退到当前项目首个可见资源或空态，确保对话 / 计划 / 资料 / 训练同源恢复而不是局部换壳。
- [ ] sidecar 恢复后，webview optimistic 状态必须能合并或回滚到 server 快照。

冲突解决顺序：

1. `安全边界` 优先于功能便利。
2. `server 事实源` 优先于 webview 缓存。
3. `正式计划` 优先于候选计划。
4. `当前项目上下文` 优先于上一个项目缓存。
5. `资料可信度` 优先于卡片复习节奏。
6. `用户显式意图` 优先于自动候选。

### 13.30 资料沙箱与 skill 威胁模型

资料沙箱越强，安全边界越重要。
Trainer 必须把资料沙箱和 skill 当成有风险的执行域设计。

必须防护的威胁：

- [ ] 路径逃逸：`../`、symlink、junction、zip-slip、tar-slip、大小写绕过。
- [ ] Prompt injection：网页、PDF、Markdown 或代码文档要求 Agent 泄露密钥、改代码、忽略规则。
- [ ] 恶意文档：超大文件、递归压缩包、解析器漏洞、伪装扩展名、二进制载荷。
- [ ] 供应链风险：下载的 skill 来源不明、manifest 欺骗、依赖脚本执行任意命令。
- [ ] 凭据泄露：skill 或资料解析尝试读取 SecretStorage、环境变量、配置文件或日志。
- [ ] 网络滥用：skill 私自上传资料、项目代码、对话内容或 API key。
- [ ] 资料污染：低可信资料覆盖高可信资料，或旧资料生成错误卡片。
- [ ] 跨项目泄露：一个项目的私有资料被错误绑定到另一个项目。

防护要求：

- [ ] 外部资料内容永远不能覆盖系统/开发者/主清单规则。
- [ ] skill manifest 必须先静态检查，再隔离运行。
- [ ] 资料索引遇到明确 skill manifest（`skill.json / skill.toml / skill.yaml / skill.yml / manifest.json / plugin.json / SKILL.md`）或高风险 manifest-like `package.json` 时，必须自动执行只读静态审核；命中 `prompt_injection / supply_chain / credential_access / network_exfiltration / path_escape` blocker 时，资源只能保留 metadata 与阻断原因，不能生成 `knowledge_fragments`、卡片候选或计划证据。
- [ ] 普通项目 `package.json` 不能因为文件名相同被误判成资料 skill；只有声明 skill/plugin/permissions/capabilities/egress/network 或 install/execution 脚本的 package manifest 才进入 skill 威胁审核。
- [ ] 所有下载内容必须有 hash、来源、时间、大小、类型和 trust_state。
- [ ] 压缩包进入资料索引、解压或深解析前，必须先执行只读 archive dry-run；dry-run 只读取 archive metadata，不落盘、不解压、不运行 archive 内任何内容。
- [ ] archive dry-run 必须覆盖 `../` 父级逃逸、绝对路径、Windows 盘符路径、UNC 路径、symlink / hardlink / junction-like 条目、zip-slip、tar-slip、超大未压缩体积、过多条目、递归/不支持 archive 类型和可执行/脚本载荷。
- [ ] archive dry-run 命中 blocker 时，资源只能保留 metadata、阻断原因、policy 和 audit 事件；不得生成 `knowledge_fragments`、闪记/实战卡候选或计划证据。
- [ ] archive dry-run 的阻断必须进入统一事件账本：`event_type=sandbox_operation_blocked`，`sandbox_policy=trainer.resource_sandbox.archive_dry_run.v1`，并按 `path_escape / malicious_document / supply_chain / credential_access / network_exfiltration` 等 threat category 汇总到资料页可见边界。
- [ ] 任何资料 skill 运行前必须先执行只读 runtime preflight；preflight 不执行命令、不读取 SecretStorage、不读取 provider key、不写用户工程，只判断运行策略是否满足隔离边界。
- [ ] skill runtime policy 必须声明 `platform`、`command_templates`、`network_allowlist`、`env_whitelist`、`output_paths` 与 `timeout_ms`；缺任一关键项、当前平台不支持、manifest audit 已阻断或策略不完整时，一律不得运行。
- [ ] skill runtime command template 必须是声明式模板，不得包含 `bash -c / sh -c / powershell / cmd.exe`、包安装、下载上传、动态执行、破坏性命令、shell 连接符或凭据变量引用。
- [ ] skill runtime command template 还必须收束为“资料沙箱内可审计文件脚本入口”，不能声明 `python -c`、`py -c`、`python -m`、`node -e`、`node --eval` 等 inline / module 解释器执行形态；runtime command 的网络、子进程与 supply-chain 审计只对真实脚本文件生效，不能把模块名或动态字符串伪装成已审计脚本。
- [ ] skill runtime 网络默认禁止；只有显式文档/资料来源域名 allowlist 可通过，`* / all / any / 0.0.0.0 / localhost / 私网 / file:// / ftp:// / ssh://` 等一律阻断。
- [ ] runtime preflight 不能只信任 manifest 与 `network_allowlist` 字段；对 `command_templates` 实际引用的脚本文件也必须执行只读网络意图审计。若脚本体包含 `requests / httpx / urllib / aiohttp / fetch / axios / socket / http.client / https://` 等网络原语，但 `runtime_policy.network_allowlist` 为空，则必须在 preflight 阶段以 `network_exfiltration` 阻断，并把被审计脚本路径写入 `audited_paths`。
- [ ] skill runtime 环境变量只允许无凭据的最小白名单，任何 `API_KEY / TOKEN / SECRET / PASSWORD / OPENAI_* / GITHUB_* / NPM_* / AWS_*` 等凭据形态必须阻断。
- [ ] skill runtime 输出目录必须解析在资料沙箱根目录之下，不能指向沙箱根、用户工程、绝对逃逸、父级逃逸、symlink/junction 逃逸或未受控目录。
- [ ] skill runtime 输出路径校验不能只看最终 resolve 结果；必须同时检查声明路径链上的目录段，任何已存在的 symlink / junction / reparse point 都必须在 preflight 阶段阻断，避免危险脚本先写出沙箱再事后发现。
- [ ] runtime preflight 的阻断必须进入统一事件账本：`event_type=sandbox_operation_blocked`，`sandbox_policy=trainer.resource_sandbox.skill_runtime.v1`，并用 `skill_runtime_network_egress / skill_runtime_env_access / skill_runtime_output_escape / skill_runtime_command / skill_runtime_manifest_blocked` 标记具体阻断面。
- [ ] skill run 请求必须是 preflight 之后的受控状态机外壳，服务端每次重新执行 preflight，不能信任 webview / extension 传入的“已通过”状态。
- [ ] skill run 未通过 preflight 时必须返回 `status=blocked`、`execution_status=blocked_by_preflight`、`execution_performed=false`，并写入 `sandbox_operation_blocked`，不得执行命令、不得创建派生产物。
- [ ] skill run 通过 preflight 且 `dry_run=true` 时，只能返回 `status=ready`、`execution_status=dry_run_ready`、`execution_performed=false`，并把 `command_templates / normalized_output_paths / derived_artifact_paths / impact_scope / operation_log` 作为审计事实返回。
- [ ] skill run 通过 preflight 且 `dry_run=false` 时，必须进入真实隔离执行器：禁止 shell，使用 argv-only 执行，工作目录锁定在资料沙箱内，环境变量只来自安全白名单，输出只允许写入声明的 `normalized_output_paths`，超时后必须返回 `execution_timeout`，非零退出返回 `execution_failed`，未产出声明文件返回 `execution_output_missing`。
- [ ] 真实隔离执行器不能复用通用 `run_command()` 或任何 `shell=True` 路径；命令模板必须先解析为 argv，再替换 sandbox placeholder，确保含空格、中文、盘符或平台差异的路径不会被 shell 或字符串拼接破坏。
- [ ] `dry_run=false` 遇到 `network_allowlist` 时默认必须 `executor_blocked`，直到存在可验证的逐次运行 egress enforcement；通过 preflight 不能自动获得网络执行权。唯一窄例外是 `python_socket_guard` 与 `node_socket_guard`：命令必须是 argv-only Python 或 Node.js 文件入口，脚本必须真实存在于资料沙箱内，脚本路径必须已经由 runtime preflight 写入 `audited_paths`，allowlist 必须是显式域名；shell、子进程、未审计脚本和 OS/容器级联网仍必须阻断。
- [ ] `/sandbox/skill/run` 必须返回 `SandboxSkillEgressDecision` 作为逐次运行 egress 判定对象，至少包含 `policy=trainer.resource_sandbox.skill_egress_enforcement.v1`、`status`、`allowed`、`enforcement_available`、`requested_hosts`、`allowed_hosts`、`blocked_hosts`、`enforcement_mode`、`verified_command_paths`、`limitations`、`reason_code`、`reason` 与 `operation_log`。无网络请求为 `not_required`；`dry_run=true` 且 allowlist 非空只能是 `dry_run_deferred`，表示结构校验通过但没有授予真实网络执行权；`dry_run=false` 且 allowlist 非空默认是 `blocked_missing_enforcement`，但不能再把所有阻断原因压成一个模糊桶：非受支持入口必须返回 `reason_code=network_egress_non_python_entrypoint` 或 `network_egress_unsupported_node_entrypoint`，未审计或不存在的 Python/Node.js 脚本路径必须返回 `reason_code=network_egress_unaudited_command_path`，只有无法进一步细分时才保留 `reason_code=network_egress_enforcement_missing`；只有已审计 Python/Node.js 脚本进入窄 guard 时才可返回 `status=allowed / enforcement_available=true / enforcement_mode=python_socket_guard|node_socket_guard`。
- [ ] `SandboxSkillEgressDecision` 不能只表达“让不让跑”，还必须表达“当前命中哪条 lane、真正需要哪种执行器、为什么不可用”。最小实现级契约至少包含 `lane` 与 `required_executor`：已审计 Python/Node.js 窄通道分别返回 `lane=audited_python|non_python / required_executor=python_socket_guard|node_socket_guard`；一般非 Python 联网请求必须明确返回 `lane=non_python / required_executor=os_container_egress`；尚无真实 OS/容器隔离时，能力缺口必须返回 `reason_code=network_egress_os_container_executor_unavailable` 或等价可机读原因，而不是继续把所有情况压回模糊 missing。
- [ ] `python_socket_guard` 必须通过临时 `sitecustomize.py` 只对本次 Python subprocess 注入，patch `socket.create_connection / socket.socket.connect / socket.getaddrinfo`，未命中 allowlist 的 host 必须在 DNS/连接前抛出阻断；临时 guard 目录必须在成功、失败、超时和输出缺失路径中都清理。该模式只能声明为窄 Python socket guard，不得伪装成全系统 egress isolation。
- [ ] `node_socket_guard` 必须通过每次运行的 `node --require <guard.cjs>` preload 只对本次 Node.js subprocess 注入，至少 patch `dns.lookup`、`net.Socket.connect`、`http/https request|get` 与 `globalThis.fetch`；未命中 allowlist 的 host 必须在发起 DNS/连接前抛出阻断。guard 文件必须在成功、失败、超时和输出缺失路径中都清理；该模式只能声明为窄 Node.js socket guard，不得伪装成全系统 egress isolation。
- [ ] `python_socket_guard` 的能力边界必须诚实且跨系统一致：当前只授予 `socket.create_connection / socket.socket.connect / socket.getaddrinfo` 这组受支持 direct socket API 的逐次执行权；`connect_ex`、`sendto` 等低级 socket API 不能假装“也被 guard 覆盖”。若脚本体出现这些未稳定支持的 API，runtime preflight 必须以 `network_exfiltration` blocker 硬阻断，而不是等到不同平台的运行时行为自行分叉。
- [ ] `node_socket_guard` 的能力边界也必须诚实且跨系统一致：当前只授予受支持的单进程 Node.js 核心网络路径逐次执行权；`child_process`、`worker_threads`、`cluster`、替代 runtime 或未受支持的扩散面不能假装“也被 guard 覆盖”。若脚本体出现这些模式，runtime preflight 必须以 `network_exfiltration` 或 `supply_chain` blocker 硬阻断。
- [ ] 即使命中 `python_socket_guard` 窄例外，runtime command 审计仍必须对脚本体执行子进程/二次执行逃逸扫描；凡出现 `subprocess.*`、`os.system / os.popen / os.exec* / os.spawn* / os.posix_spawn*`、`asyncio.create_subprocess_*`、`multiprocessing.*`、`ProcessPoolExecutor`、`pty.spawn` 等模式，必须在 preflight 阶段以 `supply_chain` blocker 硬阻断，返回 `blocked_by_preflight`、`execution_performed=false`、`command_results=[]`，不得等到运行时再补救。
- [ ] Windows 深路径下的 skill 执行不能因为 VSIX 安装态全局存储路径过长而退化成 `executor_blocked` 或假失败。若沙箱 cwd 超过普通 Win32 路径限制，执行器必须显式走兼容策略，例如优先使用短路径别名、否则对已审计 Python 入口改写为绝对解释器 + 非 shell 包装执行，对已审计 Node.js 入口改写为绝对脚本路径；`python_socket_guard` 的 `PYTHONPATH` 注入与 `node_socket_guard` 的 preload 路径都必须使用可被子进程真实加载的路径表示，确保 source / bundled / 已安装 VSIX 三态结果一致。
- [ ] Skill 隔离执行器的基础运行环境必须与用户声明的 `env_whitelist` 分离：像 `PATH / SYSTEMROOT / WINDIR` 这类仅用于让 Python/Node 在 Windows 上稳定启动的最小平台基线变量必须由执行器强制注入，不能要求每个 skill 自己声明，也不能向 SecretStorage/provider key 扩张。
- [ ] skill run 的 ready 事实必须进入统一事件账本：`event_type=resource_sandbox_operation_applied`，`sandbox_operation=skill_run_ready`，`sandbox_policy=trainer.resource_sandbox.skill_run_gate.v1`；该事件只表示“运行请求已被安全 gate 接受”，不表示命令已经执行。
- [ ] skill run 的 executed 事实必须进入统一事件账本：`event_type=resource_sandbox_operation_applied`，`sandbox_operation=skill_run_executed`，`sandbox_policy=trainer.resource_sandbox.skill_isolated_executor.v1`；该事件只表示“服务端隔离执行器在资料沙箱内写入声明派生产物”，不表示写入用户工程。
- [ ] 资料页只能以只读方式投影 `blocked_by_preflight / executor_blocked / dry_run_ready / executed` 四类事实，展示 policy、path、target、command preview 与 reason；其中 `executor_blocked` 明确表示“结构性 preflight 已通过，但仍未获得网络执行权”；webview 不提供 run / execute / write / delete / rename 的 skill 入口。
- [ ] 资料沙箱能力状态必须由服务端 `SandboxCapabilitySummary` 作为唯一事实源返回，覆盖 `platform`、`permission_state`、`path_guard_status`、`archive_audit_status`、`skill_manifest_status`、`skill_runtime_status`、`network_execution_status`、`output_boundary_status` 与 `cross_system_degradation`；webview / extension 只能只读投影，不能本地推断安全能力。
- [ ] `network_execution_status` 在没有 OS/容器级逐次运行 egress enforcement 前必须保持 `degraded`；即使存在 `python_socket_guard` / `node_socket_guard` 窄路径，也只能说明“已审计 Python/Node.js 脚本有受限 socket guard”，不能把它伪装成“任意 skill 可联网执行”。
- [ ] `network_execution_status` 不能只靠 `summary / reasons / reason_code` 传达能力边界；服务端必须同时返回机器可读的 network facts，并且每条 lane 事实都至少包含 `status`、`current_enforcement`、`next_requirement`。最小覆盖面必须包括 `audited_python`、`unaudited_python`、`non_python`、`child_process`、`os_container` 五条 lane，让 `资料 / 设置` 只读 UI 直接投影“当前由哪一层约束、下一层还缺什么”，而不是在前端二次猜测自然语言摘要。
- [ ] 每条 `network_facts` lane 还必须补齐机器可读解释层，至少包含 `reason_code`、`reason` 与 `required_executor`。尤其 `os_container` lane 不能只有 `status=missing / current_enforcement=missing`；必须显式表达“当前缺的是 `os_container_egress` 执行器、为什么缺、因此哪些一般联网请求仍被阻断”，确保服务端、账本、资料页和设置页使用同一真相而非各自猜测。
- [ ] `设置` 页只能展示资料沙箱的只读能力摘要，用于解释平台、权限、路径、归档、skill manifest/runtime、输出边界和网络降级；它不能变成新的 admin console，也不能提供执行、放权、绕过 preflight 或修改用户工程的入口。
- [ ] `资料` 页的沙箱能力块必须与 `设置` 页同源，轻量展示当前平台与网络降级原因，并继续保持知识库 + 受控沙箱定位；能力显示不能遮挡资源列表、沙箱树或 skill gate 事实。
- [ ] 高风险文件先只落 metadata，不直接深解析。
- [ ] 网络上传默认禁止，除非 skill manifest 明确且用户许可。
- [ ] 资料产生的建议必须经过 Trainer 规则过滤，不能直接成为计划或卡片。
- [ ] 安全拦截必须写入 audit log，并给用户可理解反馈。

### 13.31 分层 Definition of Done

Trainer 的完成不能只看“页面能打开”。
每个功能必须满足分层 DoD，才能进入 `已实现`。

设计 DoD：

- [ ] 映射到明确用户场景和清单编号。
- [ ] 不吞并其他一级视图职责。
- [ ] 符合 VS Code 280px-420px 窄栏主路径。
- [ ] 保持 coach-only 和计划显式采纳边界。

数据 DoD：

- [ ] 有共享类型或 schema。
- [ ] 有状态机和事件。
- [ ] 有 source_chain、why_now、feedback_targets。
- [ ] 有不变量检查和迁移/恢复策略。

后端 DoD：

- [ ] 教学决策在 server，不在 webview。
- [ ] 有候选生成、筛选、阻断、解释和失败恢复。
- [ ] 有权限分级和安全边界。
- [ ] 有单元或集成测试覆盖核心路径。

前端 DoD：

- [ ] 单栏、单主任务、无重叠、无横向溢出。
- [ ] 当前动作、下一步、失败恢复清楚。
- [ ] 不本地拼装核心教学对象。
- [ ] 中英双语和窄栏长文本可用。

验证 DoD：

- [ ] 至少覆盖一条成功路径、一条失败路径、一条恢复路径。
- [ ] 对计划、资料、训练、对话联动有端到端证据。
- [ ] 对跨系统或双语相关能力有针对性验收。
- [ ] 状态矩阵能给出 `已实现 / 半实现 / 未实现` 和证据。

发布 DoD：

- [ ] 源码态和打包态关键行为一致。
- [ ] provider、sidecar、权限不足时可降级。
- [ ] 没有禁飞线命中项。
- [ ] 已知风险明确写入状态矩阵。

## 14. 一句话完成定义

`Trainer 是一个以 VS Code 窄侧边栏为第一约束、以本轮 5 张参考图转译后的克制工具风格为视觉与交互参考、跨项目统一主体、计划可治理、资料可沉淀、训练可落地、坚持 coach-only、长期可跟随的代码教练工作台。`

只要还有任何一级视图依然主要像网页而不是像 VS Code 扩展，它就还没有完成。
