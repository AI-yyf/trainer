# Trainer Coach-First 产品定义总纲

> 历史阶段说明：本文属于早期三视图产品定义阶段，不再代表当前顶层 IA。  
> 当前 Trainer 顶层契约请以 [docs/ui-contract.md](../ui-contract.md) 为准：`Coach / Plan / Resources / Training / Settings`。  
>
> 状态：产品定义文档  
> 日期：2026-04-30  
> 目标：明确 Trainer 的理想产品定位、用户心智、能力边界与核心设计原则，作为后续界面设计、功能设计和实现改造的上位依据。

---

## 1. 一句话定义

Trainer 不是一个“带很多模块的 AI 面板”，而是一个嵌入 VS Code 的、具备长期记忆和训练能力的`代码教练`。

用户前台只需要面对一个教练；检索、研究、评估、计划、记忆、诊断这些能力都应该沉到底层，在每一次发送中自动协同工作。

---

## 2. 理想 Trainer 的核心形态

理想的 Trainer 应该同时满足四件事：

1. `前台极简`
用户看到的主入口只有教练对话，少量必要视图，以及一个足够完整但不打扰主线的设置面板。

2. `后台很强`
每次发送都能自动读取当前代码、判断用户意图、检索资料、组织上下文、必要时进行多轮分析，并把结果收敛为高价值回复。

3. `计划独立`
训练计划不是一次性消息，而是长期结构，因此必须拥有独立视图，承担训练路径、阶段进展、任务队列和薄弱点追踪。

4. `能力隐式编排`
研究、记忆、评估、检索、诊断这些能力不应作为大量显式入口堆在界面上，而应由教练在后台按需调用。

---

## 3. 用户真正需要的不是“模块”，而是“教练”

用户不会天然想使用一个“研究模块”或“记忆模块”。

用户真正会表达的是：

- 我在学什么
- 我想掌握什么
- 我现在写的代码卡住了哪里
- 请你基于我当前项目给我提炼几个值得实现的 idea
- 我需要一个更小的提示
- 我需要你 review 当前实现
- 我需要你给我出题
- 我需要你帮我规划接下来几周怎么练

因此，Trainer 的主产品模型必须是：

`用户与教练对话 -> 教练判断任务 -> 教练调用底层能力 -> 教练给出推进结果`

而不是：

`用户先理解多个模块 -> 自己决定是否进入研究/记忆/评估 -> 再和系统交互`

---

## 4. 正确的用户心智模型

用户使用理想 Trainer 时，应该形成如下心智：

1. 我在和一个代码教练对话。
2. 这个教练能读取我当前正在写的代码和必要上下文。
3. 我不用手动选择一堆模式，它会自己判断现在需要做什么。
4. 如果需要长期结构，我去看计划视图。
5. 如果需要配置模型、语言、回复风格，我去设置视图。
6. 更复杂的分析、资料检索和多轮研究，是教练在背后帮我做的事，不需要我先理解它的内部术语。

---

## 5. 顶层产品结构

理想 Trainer 的顶层结构应该稳定为三个视图：

- `对话`
- `计划`
- `设置`

只有这三个需要被明确暴露为一级入口。

### 5.1 对话

对话是绝对主入口，也是最高频视图。它承载：

- 日常提问
- 基于当前项目提炼可实现的 idea
- 下一步引导
- 代码讲解
- 提示逐步展开
- 代码评审
- 出题与练习
- 深入分析结果的回流
- 计划更新的即时反馈

### 5.2 计划

计划必须独立存在，因为它承担的是训练结构，而不是即时回复。它应承载：

- 长期目标
- 当前阶段
- 当前阶段目标
- 训练任务队列
- 最近完成情况
- 近期薄弱点
- 下一次训练动作

### 5.3 设置

设置是完整的系统配置面板，负责：

- 模型与 API 配置
- 语言切换
- 回复风格
- 工作区偏好
- 长期记忆开关与清理
- 配置文件入口

---

## 6. 哪些能力应该隐藏到底层

以下能力不该成为大量显式 UI 入口，而应成为教练的后台能力层：

- 上下文读取
- 检索资料
- 代码库搜索
- 最佳实践对比
- 深度分析
- 计划生成
- 评审与检查
- 诊断聚合
- 长期记忆写入与召回

这些能力的存在方式，应该是：

- 默认自动工作
- 必要时轻量提示
- 结果导向展示
- 用户可在设置中干预，但不在主界面抢主线

---

## 7. “研究”在理想 Trainer 中的正确位置

研究不是一个应该与教练并列的主产品。

研究的正确定位是：

`教练的深度模式 / 后台分析模式`

它适合的场景包括：

- 一个问题跨多个文件或多轮分析
- 需要比较两到三种实现方案
- 需要查资料、查最佳实践、查生态现状
- 需要形成一个可追踪的复杂结论

但在用户视角里，它不应该首先呈现为：

- theme
- thread
- approval
- role rotation

这些是系统内部编排语义，不应成为默认用户心智。

用户更容易理解的表达应是：

- 已深入分析
- 已检索资料
- 已比对方案
- 已形成建议
- 待你确认

因此，研究能力应从一级导航中降级，优先以消息流中的轻量分析结果块呈现。

---

## 8. 长期记忆在理想 Trainer 中的正确位置

长期记忆非常重要，但不该是吵闹的功能。

用户需要的是“教练记得我”，而不是“我自己管理一套记忆系统”。

理想 Trainer 的长期记忆应该包含六类内容：

1. `Learner Profile`
- 学习目标
- 当前背景
- 每周投入时间
- 偏好的教学方式
- 偏好的技术栈与语言

2. `Skill Memory`
- 已掌握的概念
- 半掌握概念
- 明显薄弱点
- 最近是否在改善

3. `Behavior Memory`
- 经常犯的错误
- 常见跳步模式
- 容易忽略的边界条件
- 容易卡住的理解层级

4. `Plan Memory`
- 当前训练阶段
- 历史计划
- 已完成的关键任务
- 阶段性目标演进

5. `Conversation Memory`
- 长期有效的偏好
- 已确认的重要技术判断
- 近期连续上下文摘要

6. `Retrieval Memory`
- 在发送时自动召回与当前问题最相关的历史训练片段

这套记忆应尽量安静地存在于后台，只有摘要和控制入口进入 UI。

---

## 9. 教学能力是 Trainer 的核心，而不是附加项

理想 Trainer 不能只是“懂代码”，还必须`懂教学`。

也就是说，它不是把答案说出来就结束，而是要持续判断：

- 用户当前理解在什么层级
- 现在最适合直接讲、提问、提示、拆步骤，还是出题
- 用户是不会，还是会但没形成稳定能力
- 当前更应该帮助“完成当前任务”，还是帮助“真正学会”

### 9.1 理想 Trainer 应具备的教学能力

理想教练至少要具备以下教学能力：

1. `分层讲解能力`
- 能判断用户适合概念层、实现层还是调试层解释
- 能把同一个问题拆成更小理解单元

2. `苏格拉底式引导能力`
- 不总是直接给答案
- 能通过问题把用户带到正确思路

3. `脚手架式教学能力`
- 先给最小提示
- 不够再加一层
- 再不够再给接近完整方案

4. `任务型教学能力`
- 能把知识点转成练习题、改错题、填空题、小挑战

5. `反思驱动能力`
- 练完后能帮用户总结：
  - 这次学到了什么
  - 错在什么
  - 下次如何更快识别

### 9.2 教学能力在产品中的正确表现

这些能力不该变成很多显式按钮，而应融入教练的默认行为。

对用户而言，最理想的感受是：

- 我说一句话，教练自然知道应该怎么教我
- 它不会一上来把答案糊我脸上
- 它知道什么时候该鼓励我自己想，什么时候该直接救我

### 9.3 理想教练必须做强的五类核心工作流

为了避免 Trainer 重新退化成“会聊天但不会带练”的工具，理想教练至少必须做强以下五类核心工作流：

1. `Idea Implementation Coaching`
- 用户告诉教练一个想法
- 教练把想法拆成可实现的最小版本、步骤和验证路径
- 再持续带着用户把代码做出来

2. `Project Idea Mining`
- 教练基于当前项目主动发现值得做的功能、重构、测试和工程化机会
- 把真实项目机会转化为训练机会

3. `Completed Project Adaptation Guidance`
- 当用户面对一个已经完成或已有雏形的项目时
- 教练能跟随用户的目标和审美，指导如何按用户心意改造现有项目
- 重点不是重新写一个新项目，而是判断：
  - 应该先动哪一层
  - 哪些模块要保留
  - 哪些边界最容易破坏
  - 如何以最小风险逐步改造成用户真正想要的样子

4. `Principle Explanation`
- 教练不只告诉用户“改哪里”
- 还要解释背后的原理、权衡和为什么这样设计
- 让用户形成可迁移的理解，而不是只完成一次修改

5. `Project Sourcing`
- 当当前工作区不适合某个训练主题，或用户想基于外部项目训练时
- 教练可以主动检索、筛选、建议合适的公开项目或模板仓库
- 必要时再进入下载、对比、挑选和后续训练规划

这五类工作流都应属于教练的后台能力编排，而不是前台多开几个模式页。

---

## 10. 基于遗忘曲线的复习机制是长期训练闭环的重要组成

理想 Trainer 不应只帮用户“当下会了”，还应帮助用户“之后记得住”。

因此，它应该具备基于艾宾浩斯遗忘曲线的复习机制。

### 10.1 为什么这很重要

很多编程学习的问题，不是“没学过”，而是：

- 学过但不会迁移
- 学过但下一周就忘
- 会做一道题，但不会举一反三

所以 Trainer 必须把“复习”纳入训练系统，而不是只做即时问答。

### 10.2 理想的复习机制

系统应把知识点、错误模式和关键经验视为“待复习对象”，并为它们安排复习节奏。

至少包括：

1. `概念复习`
- 比如异步、闭包、状态管理、数据库事务

2. `错误模式复习`
- 比如总是漏边界条件、总是跳过验收标准、总是先写实现后补规格

3. `项目实践复习`
- 把曾经做过的真实项目问题作为复盘素材

### 10.3 遗忘曲线在 Trainer 中的正确落点

它不该表现为一个独立的“复习科学页面”，而应体现为：

- 计划视图中自动出现“该复习的内容”
- 教练偶尔主动提醒某个知识点该回顾了
- 下一题生成时考虑最近该复习的主题
- 长期记忆里保存每个知识点最近一次成功/失败记录

### 10.4 复习机制的结果

Trainer 最终应能做到：

- 不只记住你想学什么
- 还记住你什么快忘了
- 不只给你新题
- 还会在对的时候把旧知识重新拉回来

---

## 11. 情绪支持不是“会说好听话”，而是稳定的陪练体验

理想 Trainer 还必须具备`情绪价值`，但这里的情绪价值不是廉价夸奖，而是稳定、可信、让人愿意继续练下去的陪伴体验。

### 11.1 用户在训练过程中的真实情绪

编程训练里最常见的情绪并不是单纯“开心”或“难过”，而是：

- 卡住后的挫败
- 看不懂后的焦虑
- 改了很多次还没过的烦躁
- 自我怀疑
- 做出来之后希望被看见

理想 Trainer 必须识别这些状态，并调整自己的说话方式。

### 11.2 情绪支持的正确方式

1. `降低羞耻感`
- 让用户敢问基础问题
- 不让用户因为不会而有被评价感

2. `给出可执行的安定感`
- 不空泛安慰
- 用更小、更明确的下一步降低压力

3. `承认进步`
- 用户做对时要让他感觉被看见
- 但不能浮夸

4. `在高压时切换风格`
- 当用户明显急躁时，回复应更短、更聚焦、更救火
- 当用户在学习模式时，回复可更具引导性

### 11.3 情绪价值在产品中的正确位置

情绪支持不是单独功能入口，而应成为教练人格和回复策略的一部分。

也就是说：

- 设置里可以允许用户选择更直接或更引导的风格
- 但真正的情绪价值来自消息里的语气、节奏和分寸

---

## 12. 每一次发送，理想 Trainer 应该自动做什么

每一次发送，都应该触发一条隐式能力链：

```mermaid
flowchart LR
  A["用户输入"] --> B["识别意图"]
  B --> C["读取当前代码上下文"]
  C --> D["召回相关记忆"]
  D --> E["判断用户当前理解与情绪状态"]
  E --> F["必要时检索资料/代码库"]
  F --> G["判断是否需要评审/规划/出题/讲解/复习"]
  G --> H["生成符合教学策略的教练回复"]
  H --> I["更新记忆、复习节奏与计划"]
```

这个流程必须默认自动发生，不能要求用户频繁手动切换多个显式模式。

---

## 13. 理想 Trainer 的输出类型

理想教练的输出，不应该是大而泛的长篇回答，而应该优先落入以下高价值类型：

- `基于当前项目提炼的 idea`
- `基于现有项目的改造路线`
- `下一步`
- `更小的提示`
- `概念解释`
- `原理解释与设计取舍`
- `代码评审`
- `练习题`
- `计划更新`
- `深入分析结论`
- `待确认决策`

也就是说，Trainer 的每次回复都应该服务于推进，而不是服务于“看起来很智能”。

---

## 14. 当前项目应坚持的非目标

为避免产品继续长歪，必须明确以下非目标：

- 不做一个“功能越多越好”的 AI 仪表盘
- 不把研究、记忆、诊断都做成一级主入口
- 不为了“功能强”而增加大量显式按钮
- 不重复造新的资料检索 UI 轮子
- 不把用户暴露在系统内部编排术语里
- 不把“情绪价值”误做成夸夸机器人
- 不把“遗忘曲线”误做成独立复杂页面
- 不把“教学法”做成用户必须手动切换的一堆模式
- 不把“专注控制模式 / 强制退出限制”当成核心产品前提
- 如果未来要尝试专注约束，也只能作为实验能力，而不是阻塞主线体验

---

## 15. 当前代码基础与理想方向的映射

当前仓库其实已经具备很多底层能力雏形：

- `planner_service`
- `memory_service`
- `evaluator_service`
- `provider_service`
- `research_service`
- `resource_service`
- `SemanticMemory / Qdrant`

这说明项目真正缺的，不再是底层抽象数量，而是`产品收束能力`。

理想方向不是继续造更多模块，而是：

- 把现有底层能力收束到教练主线
- 让计划成为唯一明确的结构化副视图
- 让设置成为完整配置面板
- 让研究、记忆、检索、评估成为后台服务层
- 在教练策略层加入教学法、复习调度和情绪调节能力

---

## 16. 成功标准

如果 Trainer 达到理想状态，用户会有这些感受：

- 一进来就知道主入口是和教练对话
- 不需要理解复杂内部模块也能自然上手
- 每次发送都感觉“系统真的懂我当前代码和训练目标”
- 它不仅能回应我的想法，还能从当前项目里主动提出值得我实现的 idea
- 它也能在一个已经完成的项目上，顺着我的意图指导我如何渐进式改造
- 每次发送都感觉“它知道我该怎么学，而不只是知道答案”
- 它会在合适的时候让我复习，而不是只给我新内容
- 它会在我卡住时给我稳定感，而不是机械输出
- 计划视图能清楚告诉我长期结构
- 设置足够完整，不会被逼着去命令面板找配置
- 深度能力很强，但界面仍然安静、克制、像专业工具

---

## 17. 最终结论

理想 Trainer 的本质不是“聊天框 + 一堆 AI 模块”，而是：

`一个懂代码、懂教学、懂复习节奏、懂陪伴体验的长期陪练型代码教练`

它的正确产品结构应该是：

- `对话`负责当前推进
- `计划`负责长期结构
- `设置`负责系统配置
- `研究 / 检索 / 记忆 / 评估 / 诊断 / 教学策略 / 复习调度 / 情绪支持 / 项目机会提炼 / 已完成项目改造指导 / 项目来源筛选`沉到底层，为每一次发送服务

这是后续所有界面设计、功能设计和实现改造的第一原则。
