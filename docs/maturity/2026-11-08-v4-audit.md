## 2. 本轮修复（代码 + 回归测试）

### 2.1 自由聊天不再被 “review” 字样劫持

`shared/src/sendIntelligence.ts` 之前把普通 prose 中的 `review/check/看看/检查` 推断为 `review`，路由到 `/turn`，会触发当前文件评估和计划推进。现在只有 `/review` 或显式 `intentHint` 进入 review；普通对话留在 `/session/message`。测试：`sendIntelligence.test.js` 断言 “Please review this change…” 为 coach。

### 2.2 资料删除正确失效训练证据

`attempt_store.py` 的 `mark_evidence_source_deleted` / `clear_evidence_source_deleted` 之前拿资源哈希对比 `artifact_hash`（学习者产物哈希），真实证据把资源哈希放在 `resource_content_hash`，导致删除通常不失效。现在优先比较 `resource_content_hash`，回退 `artifact_hash`。新增回归：`test_evidence_source_deletion.py::test_resource_delete_uses_cited_resource_hash_not_learner_artifact_hash`。

### 2.3 Skill “被选中但未应用” 不再算恢复成功

`SkillRegistry.record_usage` 之前无条件清零 `consecutive_failures`。现在只有 `applied=True` 才清除失败 streak；仅被选中不改变失败状态。测试：`test_skill_lifecycle.py::test_selection_without_application_does_not_clear_failure_streak`。

### 2.4 FSRS 到期日回流到可见复习队列

`schedule_live_training_card_fsrs_after_verify` 现在把 FSRS `next_due` 写到已有 `MasteryRecord.next_review_at`（不新建掌握、不改分数）；`ReviewScheduler` 的 due 派生会读到它。失败验证仍不写 FSRS：Try 与 Verify 共用 `/evaluate/current-file` 且请求没有 phase 字段，无法证明失败是“复习失败”还是“尝试失败”，因此没有猜测；需要先增加显式 `training_phase` 契约。

## 4. 2026-11-08 追加：显式 training_phase

`EvaluateCurrentFileRequest` 新增可选 `training_phase`（learn/try/verify/reflect/return）。Host 在训练验证路径发送 `verify`；显式 `verify` 时即使报告失败也写 FSRS `AGAIN`，其余情况保留旧的 pass-only 规则，避免把 Try 失败误记成复习失败。

`schedule_live_training_card_fsrs_after_verify` 的 `next_due` 写回已有 `MasteryRecord.next_review_at`；`ReviewScheduler` 的 due 分支读取该日期并据此计算 `interval_days`，因此通过/失败的 Verify 都会进入可见复习队列。测试：`test_live_training_fsrs_on_verify.py`（显式失败 + due 队列命中）；host payload 测试：`evaluationCommands.test.js` 断言 `training_phase=verify`。真实 GUI 复核需要一张 live training card；当前 provider 额度为 429/2056，无法生成卡片，因此 GUI 验证待额度恢复，未标记 PASS。

`MasteryRecord` 新增 `review_source`（`fsrs` / `heuristic`）。`update_mastery` 现在保留 FSRS 拥有的 `next_review_at`，不再被后续分数更新覆盖；`ReviewScheduler` 的 mastery 分支只接受 `review_source="fsrs"` 且带日期的记录，启发式 mastery 不再伪装成到期复习。测试：`test_review_scheduler.py` 覆盖 FSRS 日期保留、启发式记录跳过。

复习队列动作 `process_mastery_review` 已改用 FSRS 评分：MasteryRecord 持久化 `fsrs_stability/difficulty/reps/lapses/state`，队列动作按 AGAIN/HARD/GOOD/EASY 计算下一次 due，固定评分间隔表不再参与。

`ReviewQueueItem.evidence_basis` 明确区分 `fsrs_recall`（mastery 到期）与 `no_recall_evidence`（weakness/reflection/plan）；Training 复习列表对后者显示“无回忆证据/No recall evidence”，不展示 FSRS 间隔。测试：`test_review_scheduler.py` 覆盖两类标记，`test_review_scheduler_fsrs.py` 覆盖评分影响间隔。

## 5. 2026-11-08 追加：Goal 服务端实体化

**状态所有权**：`GoalService` + SQLite `goal_sessions` 是唯一真源；`WorkbenchSnapshot.goal` 回传，GoalBar 只渲染与操作。webview 的 `applyServerGoal` 在 VS Code 内以服务端快照覆盖本地乐观状态；localStorage 仅保留给 browser preview。

**模型**：`GoalSession` 记录 `goal_id/workspace_id/session_id/title/concept/capability/plan_id/stage_id/status/source/current_position/latest_activity/activities/activity_count/evidence_count/started_at/updated_at/last_activity_at/completed_at`。状态只允许 `active|paused|completed`；完成目标不清除任何能力证据。

**自动识别**：`detect_goal_candidate` 只匹配明确的能力学习表达（如“我想真正学会实现 PPO”“系统学习强化学习”“I want to learn how to build a compiler”“帮我制定学习 PPO 的计划”）。“PPO 是什么”“Can you explain PPO?”、普通闲聊、`/review` 均不创建目标。自动识别只在 coach 意图/coach 视图且没有当前目标时发生；已有目标不会被自动识别替换。

**交互与持久化**：`POST /goal/action`（start/pause/resume/complete）、`GET /goal/current`、`GET /goal/list`。显式新目标会暂停旧焦点但保留历史；同一标题幂等；恢复会暂停其它 active 目标以保持单一焦点。`publish_goal` 把当前目标同步到该工作区所有 live session 快照。

**自动进度**：只从真实活动记录，不记普通聊天：

- `/evaluate/current-file`、`/evaluate/snippet`：按内容哈希幂等记录 `evaluation` 活动与证据引用。
- `/training/attempt/evidence`：记录 `training_attempt`，引用 `attempt:{id}`。
- `/training/verification/attest`：记录 `verification`，按 `idempotency_key` 幂等。

活动只写入 active 目标；重复 `event_key` 不增加计数。目标只是学习焦点，不升级 mastery、不改 FSRS、不覆盖掌握证据。

**测试**：`server/tests/test_goal_session.py` 17 项（识别边界、普通问题不建目标、自动识别不替换、重启恢复、快照、暂停/恢复/完成、旧目标保留、评估活动幂等、训练证据、工作区隔离、空标题拒绝）；`extension/tests/goalCommands.test.js` 5 项（host 请求体、服务端 null 目标镜像、非法动作/空标题/未信任工作区、sidecar 不可用 fail-closed）；`workbenchData.test.js` 2 项（`/session/start` 的 camelCase 与 `/snapshot` 的 snake_case Goal 快照恢复/清除）。本机 server 全套 **3919 passed / 0 failed**，extension suite exit 0，tsc clean，pyright clean。

## 6. 2026-11-08 追加：Evidence 三套存储统一

**问题（代码事实）**：同一条学习证据存在三种互不兼容的形状：

- `AttemptStore` SQLite `training_evidence`：`trust_level`、`artifact_hash`、`resource_*`、`result`；
- handoff `EvidenceRecord`：`verified`/`verification_source`，没有 schema 版本与资源版本字段；
- memory `EvidenceItem`：`verified`/`verification_source`，采用队列生命周期字段。

读取方必须分别解释，且 handoff 证据的持久化字段与内存模型不一致。

**统一契约**：新增 `server/app/evidence/contract.py`：

- `UnifiedEvidence`（schema 1）：`evidence_id/source_store/source_id/workspace_id/card_id/concept/summary/content/result/trust_level/verified/verification_source/artifact_hash/resource_id/version/content_hash/location/git_sha/assistance_level/limitations/created_at/verified_at/schema_version/fingerprint/duplicate_of`。
- 信任统一为 `self_reported | model_review | static_analysis | controlled_check`；结果统一为 `passed | failed | partial | unknown`。
- 三个适配器：`evidence_from_attempt`、`evidence_from_handoff`、`evidence_from_memory`。
- `fingerprint` 以 artifact hash 优先，否则用 workspace+card+内容哈希+结果；`finalize_unified_evidence` 按信任优先级标记 `duplicate_of`，不删除重复来源。
- 新只读 API：`GET /evidence/records?workspace_id=…&limit=…`，按时间倒序返回统一记录。

**存储层补齐**：

- `AttemptStore` 写入 `schema_version=1`，新增 `list_workspace_evidence(workspace_id, limit)`（SQL 层强制工作区隔离）。
- handoff `EvidenceRecord` 增加 schema/trust/result/artifact/resource/attempt 引用字段；`_handoff_payload` 升为 version 3 并完整序列化这些字段，`_handoff_from_payload` 对称解析，避免重启丢失。
- `EvidenceItem` 增加 schema/source_store/trust_level/artifact/resource/canonical 字段；入队时按 `verified` 写入 `trust_level`。
- `MemoryService.latest_handoff_evidence` 从持久化 handoff 读取证据，不再复制第二份。

**行为测试**：`server/tests/test_evidence_unification.py` 4 项：

1. 三套存储归一化、信任/结果/资源版本字段、handoff+memory 去重链接；
2. 工作区隔离与 limit 钳制；
3. handoff 证据跨重启保留统一字段；
4. 时间倒序与结果归一。

**边界**：原始存储仍按生命周期存在（AttemptStore 负责受控执行证据，handoff 负责卡片回传，memory 负责采纳队列）；统一的是契约与读取面，没有新增第四套数据库或第二套掌握评分。
