# Trainer 开发总提示词（最终版）

你正在推进 `H:\trainer_final` 的 Trainer。你的任务不是空谈设计，而是把它持续打造成“跨项目统一的最强代码教练”，并一路推进到真正成熟可用。

## 0. 任务定义

Trainer 不是写业务代码的代理，也不是聊天壳。它是一个长期可用、coach-first、运行在 VS Code 侧栏里的教学系统。

你的目标只有一个：把 Trainer 做成“低理解成本、强教学、可恢复、可验证、可长期演进”的统一教练。

## 1. 唯一真相来源

优先依据以下文件：

- `docs/trainer-ideal/README.md`
- `docs/trainer-ideal/trainer-product-design-spec.md`
- `docs/plans/2026-05-07-trainer-teaching-quality-closure-checklist.md`
- `docs/verification/2026-05-09-trainer-closure-status-matrix.md`

真相优先级如下：

1. 当前实现真相
2. 实测证据
3. `docs/trainer-ideal/*`
4. 计划与验证文档
5. 其他旧文档、旧脚本、旧产物

如果文档和代码、测试、真实运行结果冲突，以“当前实现真相 + 实测证据”为准。

## 2. 产品不变量

1. Trainer 本质是教练，不是代替用户写业务代码的代理。
2. `对话` 是超级入口，界面重心必须始终保持纯对话中心。
3. 对话必须有人味，能教学、能追问、能按用户水平调整表达，还要轻量可见地展示“教练正在做什么”。
4. 对话必须自然联动 `资料 / 计划 / 训练`，但不能变成堆叠式后台。
5. `训练` 必须是一张一张刷的沉浸式卡片流，清晰区分 `闪记卡片` 与 `实战卡片`，必要时保留复盘、场景等子模式，但它们只能是训练内部子模式。
6. `资料` 必须是跨项目统一知识库 + 受控沙箱，像高级文件管理器，逻辑清楚，AI 能管理，人能查看、打开、下载、复用。
7. `计划` 必须是总计划 + 分项目子计划，主从关系清楚，低理解成本，能被对话驱动调整，并能真实推进训练。
8. `i18n` 必须是硬能力，不是补丁。至少支持 `zh-CN`、`en-US`、`es-ES`、`fr-FR`、`de-DE`、`ja-JP`、`ko-KR`、`pt-BR`，并且所有核心视图、状态提示、错误提示、设置、训练卡片文案都必须有统一回退策略。
9. 所有设计必须适配 VS Code 侧栏场景，长期可用，自适应主题，不花哨，不堆符号，不重复，不重叠，不靠说明文案撑设计。

## 3. P0 真相与闭环

1. 文档状态和代码现实可能漂移，必须用真实验证纠偏。
2. provider 连通性不能假阳性；空内容、reasoning-only、截断回复都不能被误判为“教练可用”。
3. 训练记忆、掌握度、learning outcome、teaching asset、teaching strategy 必须有唯一可信真源，不能出现重复定义、覆盖、失真。
4. `resume / restore / restart / updatePlan` 不能只是切 view 或重新拉 summary，必须是可治理、可恢复、可续接的教练状态流。
5. i18n 不能只做两种语言的表面切换，必须覆盖八语言范围，并且所有语言都要通过同一套真源和回退链路。
6. 所有核心状态变化必须能落到可追踪事件，不允许前端自己发明核心真相。

## 4. P1 产品结构

1. 对话必须真的是超级入口，而不是挂着对话皮的系统控制台。
2. 训练必须收敛成单卡沉浸流，不允许膨胀成多面板训练后台。
3. 资料必须收敛成高级文件管理器 + 受控沙箱，不允许变成杂乱运营后台。
4. 计划必须是总计划 + 分项目子计划的治理系统，不是纯展示文本。
5. i18n 必须覆盖八语言范围，且语言切换不能破坏布局、状态、回退和可用性。
6. UI 架构必须逐步去中心化，避免单个超大 `App` 文件和超大样式文件继续失控。
7. 必须消灭中文乱码、样式漂移、窄侧栏换行抖动、按钮/文案层级混乱。

## 5. 状态与真源治理

1. `provider`、`memory`、`mastery`、`learning outcome`、`teaching asset`、`teaching strategy` 必须各自只有一个可信真源。
2. 前端只能展示和驱动状态，不能自行制造最终真相。
3. 所有可恢复状态必须经由后端或统一事件账本同步，不能只靠 view 切换或 summary 重刷。
4. `resume` 表示延续当前教练上下文。
5. `restore` 表示从持久化真源重建状态。
6. `restart` 表示开启新的教练会话，但必须保留审计轨迹。
7. `updatePlan` 只能在明确的计划治理语义下发生，不能被普通聊天偷偷改写。

## 6. 视图职责

### 对话

- 永远保持纯对话中心。
- 允许即时追问、即时小测、即时卡片建议、即时资料联动。
- 轻量可见地展示教练正在做什么，但不把工作台塞进对话。
- 对话中的动作提示必须是短、轻、可理解的状态，不是后台日志。

### 计划

- 只做总计划 + 子计划治理。
- 计划可以被查看、理解、调整、冻结、恢复，但不能被普通聊天偷偷改写。
- 计划必须能显示主线、子线、进度、阻断、证据、回流关系。

### 资料

- 只做统一知识库 + 受控沙箱。
- 资料要像高级文件管理器，但要比文件管理器更会沉淀知识、生成卡片、回流计划。
- 能搜索、打开、下载、复用、追溯来源，但不能变成业务后台。

### 训练

- 只做单卡沉浸流。
- 至少清晰区分闪记卡和实战卡。
- 卡片必须能追溯到计划、资料和掌握度，完成后能回流。
- 子模式只能服务于单卡训练，不得把训练扩展成多面板控制台。

### 设置

- 只做系统可用性、provider、模型、语言、训练偏好、环境限制。
- 语言设置必须面向八语言范围，且有统一回退，不允许仅服务中英双语。
- 不承载业务正文，不伪装后台。

## 7. 开发节奏

1. 先读代码、读相关文档、跑验证，再下判断。
2. 先确认真相，再做实现，不要反过来。
3. 每次优先选择“最能提升产品可信度和完成度的下一步”。
4. 小步快跑，但每一步都必须可验证。
5. 改完必须跑相关 build / tests / diagnostics / 必要的交互验证。
6. 涉及 UI 时，必须从真实人类使用路径检查：首屏理解成本、操作路径、状态反馈、异常反馈、信息层级、可恢复性、一致性。
7. 如有必要，可以使用真实 provider 做烟测，模拟真实用户对话与训练场景，但测试结论必须回到产品闭环，而不是停在接口层。

## 8. 优先级顺序

1. 先修系统真相问题和假阳性问题。
2. 再修训练记忆 / 掌握度 / learning outcome 主闭环。
3. 再修计划治理和恢复续接协议。
4. 再修训练 / 资料 / 计划 / 对话 四大视图的结构收敛。
5. 最后再做视觉和交互精修。

如果中途发现更底层的阻断点，可以调整，但必须说明原因，并且继续优先处理最接近闭环的部分。

## 9. UI 与实现底线

1. 不要把“设计想法”直接塞进 UI 就当完成。
2. 不要只提建议不落地。
3. 不要生成概念性功能壳、演示壳、占位壳。
4. 不要为了显得高级而增加理解成本。
5. 不要把训练做成控制台，不要把资料做成后台，不要把计划做成一堆文本说明。
6. 不要出现低级问题：乱码、字体层级混乱、不对齐、重复按钮、重复信息、状态逻辑冲突、功能重叠、交互绕、视图首屏抖动。
7. 不要问用户明显下一步要不要继续。你应自主判断并继续推进。
8. 不要引入新依赖，除非确实无法用现有能力完成且风险已说明。
9. 优先删除、收敛、复用、补边界，而不是加新层。

## 10. 验证要求

1. 先验证真相，再验证实现。
2. 真实 provider 不能假阳性。
3. 训练、资料、计划、对话都要有端到端闭环证据。
4. UI 改动要做真实侧栏场景检查，特别是窄宽度、主题切换、长文本、空状态、错误态。
5. i18n 改动要做多语言回退检查，至少覆盖八语言中的首选语言与回退语言。
6. 任何看起来像“只是文案”的设计，必须确认它是否真的改善了理解和操作，否则删掉。
7. 任何状态宣称都必须有证据，不接受“看起来像已经好了”。

## 11. 每轮固定输出

每一轮都要输出下面 6 项，不要跑题：

1. 当前你认为最关键的问题是什么。
2. 你这轮具体改了什么。
3. 你为什么先改这个。
4. 你跑了什么验证，结果是什么。
5. 还有什么风险 / 缺口。
6. 下一步你会继续推进什么。

## 12. 绝不做的事

1. 不做形而上的设计口号。
2. 不做只有概念、没有实现的壳。
3. 不做与当前实现真相冲突的假完成态。
4. 不做会破坏跨项目统一主体的碎片化设计。
5. 不做把 VS Code 侧栏伪装成网页后台的设计。
6. 不做“看起来高级但实际上更难懂”的交互。

## 13. 最高标准

最高级的设计，是把巧思放进极简的设计和完美的交互中。

Trainer 的目标不是“功能看起来完整”，而是“真正成熟、低理解成本、人性化、强教学、长期可用”。
